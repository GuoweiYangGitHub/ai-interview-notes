# 江中智能助手 · 运维与故障兜底
> 探针、限流、幂等、租约、优雅停机和常见故障处理；再用一次 4–5 万 token 的排查复盘说明「现象 → 根因 → 处理」。

## 探针

| 探针 | 含义 |
| --- | --- |
| `GET /live` | 进程可服务 |
| `GET /ready` | PostgreSQL 与工具目录可用；未就绪 503 |
| `GET /health` | 兼容旧检查，返回 `{ok:true}` |

## 运行时保护

| 能力 | 默认值 | 行为 |
| --- | --- | --- |
| 按身份限流 | 60 次/分钟 | 超限 429 + `Retry-After`；进程内计数 |
| 请求幂等 | 24h | 同键同体重放；不同体 409 |
| 消息幂等 | 24h | 同 `messageId` 重放；处理中 409；内容冲突 |
| 会话锁 | 10s | 超时 409 `session_busy` |
| 会话 TTL | 7 天 | 过期 409 `session_expired` |
| 轮次心跳/租约 | 10s / 60s | 中断后需放弃轮次 |
| 后台 run worker | 1s 轮询 / 30s 租约 / 10s 心跳 | 单进程；取消通过心跳发现 |
| 记忆 worker | 1s 轮询 | 失败重试，超过上限置 dead |
| 优雅停机 | 15s | SIGTERM 后 `/ready` 503、停止新请求、等待在途、关连接池 |
| 模型超时 | 60s | `maxRetries: 0`，不自动重试 |
| 整轮上限 | 20 次模型 / 10 次工具 / 1h | 超限按现有结果收尾 |
| 请求体上限 | 256 KiB | 超限 413 |
| 审阅恢复探测 | 30s | `ReviewManager` 后台恢复 |
| 记忆保留 | 30 天 | `MEMORY_RETENTION_DAYS` |

## 启动顺序

1. 读取 `config/env.ts`；缺少模型、`DATABASE_URL` 或认证配置直接失败。
2. `SessionStore.setup()` 建表/补列；清理过期会话。
3. 按 `MEMORY_ENABLED` 初始化记忆库与 worker；失败只关闭记忆，不阻止启动。
4. 初始化审阅记录器；失败不阻止助手启动，后台恢复。
5. 发现中台 MCP 工具目录（最多重试 5 次）；没有只读工具时告警。
6. 装配图、后台 run store/worker、HTTP app。
7. 启动监听；收到 SIGTERM/SIGINT 进入排空。

## 常见故障与处理

| 现象 | 根因 / 先看 | 处理 |
| --- | --- | --- |
| 启动报 `DATABASE_URL` / `AUTH_USERS_JSON` | `.env` 缺配置 | 补齐后重启 |
| 启动报 `AUTH_MODE=gateway` 配置 | `GATEWAY_*` 不全 | 配 `GATEWAY_BASE_URL` 或 `OPENAI_BASE_URL` |
| `pnpm start` 卡在 PostgreSQL | Docker Desktop 未启动 | 启动 Docker；或 `pnpm db:up` 后重试 |
| 7777/7776/7778/7779 被占用 | 旧进程未退出 | `netstat -ano` 找到并关闭；`pnpm start` 会预检端口 |
| 聊天 401 | 令牌不匹配 | Demo 设置里换令牌；开发默认令牌只在本机 |
| 聊天 429 | 按身份限流 | 等 `Retry-After`；测试用例显式关闭限流 |
| 聊天 409 `session_busy` | 同会话并发 | 等上一轮结束或新建会话 |
| 聊天 409 `session_interrupted` | 轮次中断未放弃 | 调用 abandon-turn 后继续 |
| 后台 run 一直 queued | worker/数据库异常 | 看 `assistant_runs` 状态与网关日志 |
| 场景动作显示「仅模拟」 | 方法不是 3 个真实动作 | 只有 `focus_device` / `fly_to_device` / `highlight_alarm` 真正改变 ThingJS |
| 场景未就绪 | ThingJS 登录/本地库/WebGL | 检查 `public/libs/thingjs2.0`、网络与 WebGL |
| `getReader is not a function` | 全局 fetch 被 ThingJS 覆盖 | 确认 `window.__nativeFetch` 在 ThingJS 之前捕获 |
| 审阅台 503 | `TRACE_ENABLED` 未开 | 设 `true` 并重启；初始化失败看日志 |
| 标注接口 503 | 审阅未启用/迁移缺失 | 开启 `TRACE_ENABLED`；检查 `review_annotations` 迁移 |
| 评测批次 404 | 批次号/路径不对 | 批次号必须是报告目录名；检查 `eval/reports` |
| 裁判 403 `model not allowed` | `JUDGE_MODEL` 未开通 | 开通模型或临时换同系列可用模型；不得静默回退 |
| 基线过期 | 用例/模型/Prompt hash 变化 | 重跑 `--write-baseline`；确认 hash 变化原因 |
| 记忆不可用 | `MEMORY_ENABLED` 未开/缺 `pg_jieba` | 开启环境变量；扩展缺失时用 `simple` 分词 |
| 知识库不可用 | `DIFY_*` 配置或真实 Dify | 检查 `DIFY_BASE_URL`、对应 `DIFY_KB_*_KEY` 与真实 Dify |

## 日志

- 访问日志：`event=http_request`，含请求 ID、方法、路径、状态、耗时。
- 轮次日志：`event=turn_completed`，含 turnId、workflowRunId、状态、模型/工具调用数。
- 工具日志：`event=tool_call`，含工具、code、attempts、耗时。
- 规划日志：`event=route_parse`，含 taskIntent、execution、plan、dropped。
- 停机：`event=shutdown`，含 phase、signal、duration、timedOut。
- 审阅写入失败不会影响业务，但会打印错误；持续失败由熔断与恢复任务处理。
- 不要把 `.env`、令牌或完整请求体贴进日志/工单。

## 备份与清理

- 每小时清理过期会话、请求幂等、长期记忆、审阅正文/链路。
- PostgreSQL 数据卷为 `assistant-db`；生产按实际策略备份。
- 审阅正文按预算截断，不保证保留完整原文。
- 标注、评测报告属于人工资产，不在自动清理范围；按团队策略备份。

## [重点] 踩坑复盘：一句话查询为什么发了 4–5 万 token

> 记录时间：2026-11-18；路径与现状按 2026-11-22 校正。
> 触发场景：用户问「查一下 SANC03 的设备状态和告警」。
> 结论先行：**不是模型贵，是每次模型调用都把「全量工具 + 全部领域规则 + 历史 + 工具结果」重新发了一遍。** 一轮里有几次模型调用，这份成本就乘几次。
> 阅读提示：本文记录 S040–S042 的排查过程；S069/S071 之后，工具选择已改为 route 输出 + 工具 metadata 驱动，中文业务正则被静态检查拦截。预算与压缩原则仍适用，具体候选规则以当前代码为准。

### 现象

一句很短的话：

> 查一下 SANC03 的设备状态和告警

观测到的单轮输入达到 **4–5 万 token**。拆开看，系统提示词里同时塞了：

- 意图判断分类（闲聊 / 单任务 / 多条件 / 缺参 / 不支持 / 业务流程）
- 本轮可用工具（全量业务工具 + 知识库工具 + 场景方法）
- 工具选择规则、写操作确认规则
- 三维场景动作说明
- 回答规则
- 历史对话、历史摘要、当前轮所有工具结果

而且**几乎每一步都有**：查设备状态一次调用、查告警再一次调用、最后总结再一次调用，每次请求都带着同一份完整提示词和同一份全量工具 schema。

数字口径：

| 口径 | 数值 | 来源 |
| --- | --- | --- |
| 旧实现单次模型输入 | 约 21k token | S040 spec / decisions 第 44 轮 |
| 旧实现一轮两次模型调用 | 约 42k token | 同上 |
| 用户侧观感 | 4–5 万 token | 多步查询 + 历史累积后的整轮累计 |
| 工具 schema 体积 | 约 28k 字符 | S040 spec |

单次 21k、两次 42k，再叠加多步、历史与工具结果，就是 4–5 万。**用户看到的「输入提示词」其实是整轮累计，不是一次请求。**

### 根因

不是某一处写错了，是五个默认习惯叠加：

| # | 现象 | 根因 | 处理 |
| --- | --- | --- | --- |
| 1 | 问设备状态也带着巡检、备件、批次、三维规则 | 系统提示词是一整块，不按意图裁剪 | Prompt 拆 base + 当前领域 skill，只追加候选工具对应的 skill |
| 2 | 工具 schema 每次请求完整下发 | `bindTools` 每轮绑定全部工具 | Host 先选候选工具，只绑定候选，系统提示只列候选 |
| 3 | 用户没提三维，场景方法照样占位 | 场景方法、工作流工具常驻 | 场景方法只在三维意图加载，且必须是宿主上报过的方法 |
| 4 | 步骤越多重复内容越多 | 历史对话、历史摘要、当前轮工具结果原样进入下一次调用 | 预算 + 压缩：保留最近完整轮次，较早工具结果压成确定性步骤摘要 |
| 5 | 单次「看着还行」，一轮下来翻几倍 | 只控制单次预算，没有整轮累计视角 | 增加整轮阈值：45k 经济模式、90k 只读模式 |

一句话：**把「系统存了什么」和「模型这一步需要看什么」混成了一件事。**

### 处理

核心原则：

> Host 决定模型这一步能看到什么；checkpoint 保留全部事实；模型只拿当前这一步的最小充分集。

落地为三层：**候选工具 → Prompt 分层 → 预算与压缩**。

#### 第一层：Host 选候选工具，不再全量绑定

代码：`apps/server/src/agent/context/tool-selector.ts`、`apps/server/src/agent/nodes/assistant.ts`

- 按当前用户消息、TaskCard、流程状态、上一步工具结果，确定命中的工具组；
- 只把候选工具绑定给模型，系统提示词也只列候选工具；
- 工具**保持独立定义，不合并**；
- `tools` 节点仍持有全量工具用于执行，权限、参数、审批仍由服务端校验——模型只是「看不见」，不是「不能用」。

| 工具组 | 触发词示例 | 候选上限 |
| --- | --- | --- |
| `alarm` | 告警 / 报警 / 确认 / 取消 / 趋势 / SOP / 误报 | 普通步骤共享 3 个 |
| `workorder` | 报修 / 维修 / 工单 / 故障 / 异响 / 停机 | 同上 |
| `batch` | 批次 / 批号 / 追溯 / 影响批次 | 同上 |
| `inspection` | 巡检 / 点检 | 同上 |
| `spare` | 备件 | 同上 |
| `knowledge` | 怎么 / 步骤 / 规程 / SOP / GMP / 工艺 / 手册 | 最多 2 个 |
| `production` | 停机 / 生产订单 / 产量 / 能耗 / 环境 | 普通步骤共享 3 个 |
| `core` | 设备 / 状态 / 健康 / 交接班 / 库存 / 设备号 | 同上 |
| `scene` | 飞到 / 聚焦 / 定位 / 高亮 / 标注 / 三维 | 仅三维意图 |
| `workflow` | 批次追溯 / 维修工单 / 报修 / 巡检 | 仅流程意图 |

关键规则：

- 知识库 7 个工具保持独立，**不合并成 `search_knowledge(app=...)`**；按问题词排序，最多取 2 个；
- 场景方法只在三维意图加载，且必须是宿主上报过的方法；
- `start_workflow` 只在流程意图加载，且必须单独调用；
- 已有 `activeWorkflow` 时，主图不绑定业务工具，交给流程子图；
- 条件任务（「如果有影响批次，再查 SOP」）在批次结果出现前**不加载**批次/SOP 工具，结果出现后再补载；
- 规则没命中任何候选、但文本含业务关键词时，只做**一次有范围补选**（core，含「告警」再加 alarm），不退回全量。

#### 第二层：Prompt 分层，base + 当前领域 skill

代码：`apps/server/prompts/assistant.yaml`、`act.yaml`、`skills.yaml`、`apps/server/src/prompts/index.ts`

- `assistant.yaml` 只保留 base：身份、工具纪律、安全边界、输出格式、通用选择规则；
- `skills.yaml` 按领域拆开：alarm、workorder、batch、inspection、spare、knowledge、production、scene；
- `renderAssistantPrompt` 只追加**当前候选工具对应的 skill**；
  - 不选知识库工具 → 不追加 knowledge skill；
  - 没有三维动作 → 不追加 scene skill；
- 工具描述和场景方法描述统一压成单行并限长，避免撑大提示词或夹带换行结构；
- 模板只允许已知占位符，未知占位符在加载时直接报错，避免模型看到空段落或未替换的占位符原文。

#### 第三层：预算、压缩与整轮阈值

代码：`apps/server/src/agent/context/context.ts`、`apps/server/src/agent/nodes/assistant.ts`、`apps/server/src/config/env.ts`

单次请求：

| 类型 | 压缩触发 | 硬上限 |
| --- | --- | --- |
| 普通步骤 | 9k | 10k（`CONTEXT_INPUT_TOKENS`） |
| 知识库 / SOP | 27k | 30k（`CONTEXT_KNOWLEDGE_INPUT_TOKENS`） |

- 预算把 system、工具定义、历史、摘要、输出预留、安全余量**全部计入**；
- 达到 90%（`CONTEXT_COMPACT_RATIO`）触发压缩；
- 超过硬上限抛 `ContextBudgetError`，**不静默截断**——宁可明确失败，也不让模型拿着缺事实的上下文硬答。

整轮：

| 累计输入 | 行为 |
| --- | --- |
| 45k | 经济模式：候选工具降到 1 个 |
| 90k | 只读模式：解绑工具，只生成最终答复 |
| 100k | 计划硬停止（尚未实现） |

当前轮压缩：

- 保留最近 2 个完整工具循环；
- 更早的循环压成一条确定性步骤摘要（调用了什么工具、参数、结果摘要），不调用模型；
- **只改模型可见内容，不改 checkpoint**，原始消息仍可用于审计与回溯。

#### 配套：StepLedger 与 token 观测

- `TaskCard.steps` 记录 `id / action / status / summary / resultRef / facts`，按 `toolCallId` 覆盖更新，最多 20 条；完整工具结果仍在 checkpoint；
- 系统提示词里的工作上下文只展示最近 5 条步骤，避免把整段历史搬回去；
- `TurnMetrics` 增加 `inputTokens` / `outputTokens`，用模型返回的 `usage_metadata` 累加；
- `ModelRequestContext` 冻结每次请求的 system / taskCard / summary / recent / memory 和 token 分解，审阅台可查。

### 结果

| 场景 | 旧实现 | 现在（单次模型输入） | 降幅 |
| --- | --- | --- | --- |
| 「查 SANC03 设备状态和告警」 | 约 21k / 次 | 2,155 与 2,377 | 约 89% |
| 知识库点检问答 | 约 21k / 次 | 2,277 与 2,681 | 约 88% |

- 设备查询只绑定 core + alarm 候选工具，Prompt 只含 base + alarm skill；
- 知识库查询只绑定 2 个独立知识工具，Prompt 只含 base + knowledge skill；
- 当时全量测试：203 项，178 通过、25 跳过、0 失败；当前数字见 [/03-项目实战/02-江中智能助手/10-数字速查与讲法](/03-项目实战/02-江中智能助手/10-数字速查与讲法)。
- 证据：`logs/cross/S040/`、`logs/cross/S041/`、`logs/cross/S042/`。

### 为什么这样解，而不是别的

| 备选方案 | 没选的原因 |
| --- | --- |
| 合并工具，减少 schema | 工具语义会变糊，选择准确率和审计粒度都下降；spec 明确禁止合并 |
| 把意图分类塞进工具绑定 Prompt | 后来按 S044 增加了独立 classify，但 classify 只判意图、不带工具目录；只有 `single/continue` 才 route。分层目标是减少每次调用的视野，不是再加一个全量 Router |
| 直接删历史消息 | 会破坏审计与回溯；正确做法是 checkpoint 不动，只缩模型视野 |
| 超预算静默截断 | 模型会拿着缺失事实编答案；明确报错更容易定位 |
| 只降单次预算 | 一轮多次调用仍然乘数放大；必须同时看整轮累计 |

### 仍未解决的坑

| 现象 | 根因 | 处理/现状 |
| --- | --- | --- |
| token 估算和真实值有偏差 | 仍是启发式估算，未接真实 tokenizer | 安全余量需按实际 `usage_metadata` 校准 |
| 候选可能漏选、知识库可能选错 | 还没有评测集统计 | 需要补候选漏选率、知识库选错率 |
| 「最终答复 4k / 6k」预算没生效 | 代码只区分「知识库 / 普通」 | 尚未单独识别最终答复 |
| 100k 整轮硬停止不存在 | 只实现到 45k 经济模式、90k 只读模式 | 计划硬停止待做 |
| 知识库 30k 上限是否必要 | 缺真实文档规模验证 | 用真实文档规模评估后再收窄 |
| 开启记忆后输入变大 | 记忆注入、历史摘要额外增加输入 | 持续看 `inputTokens` 分布 |
| 重复成本仍可再降 | 未使用 prompt caching | 候选绑定已降重复成本，缓存是下一步 |

### 下次先问这 8 个问题

1. 每次模型调用**实际**发了多少 token？用 `usage_metadata` 量，不要按字符数猜。
2. 其中工具 schema 占多少？
3. 这段话这一步真的需要吗？不需要的规则为什么在提示词里？
4. 历史对话和工具结果是不是在每一步原样重发？
5. 整轮累计是多少，而不只是单次？
6. 压缩有没有动 checkpoint？审计还能不能还原？
7. 候选漏选怎么兜底？兜底会不会又退回全量？
8. 超预算是报错还是静默截断？
