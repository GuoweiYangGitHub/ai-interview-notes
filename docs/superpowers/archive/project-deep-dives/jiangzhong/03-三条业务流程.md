# 江中智能助手 · 三条业务流程
> 批次追溯、维修工单、巡检三条固定流程，以及工单字段、运维角色业务地图和高价值场景。

## 固定流程的共同规则

三条**固定业务流程**都由「启动短语或工具」进入；进入后每一步先做确定性解析，解析不了才调用一次模型兜底。确认步不兜底，模型不能代替用户确认写操作。

普通只读查询（设备状态、工单、重复告警、健康、备件、趋势等）不走这三条固定流程，而是走只读计划执行器（见 [/03-项目实战/02-江中智能助手/02-请求链路与LangGraph](/03-项目实战/02-江中智能助手/02-请求链路与LangGraph)）。固定流程只负责需要多轮步骤、状态停留和逐站推进的业务。

## [重点] 批次追溯

启动：说「批次追溯」或「追溯批次」，或模型调用批次工具。

| 步骤 | 节点 | 做什么 |
| --- | --- | --- |
| 批次号 | `workflow_batch_trace_batch_no` | 提取并校验批号 |
| 方向 | `workflow_batch_trace_direction` | 正向（成品→原料）/ 反向（原料→成品） |
| 查询结果 | `workflow_batch_trace_trace` | 调中台，按方向分组输出 |
| 后续操作 | `workflow_batch_trace_followup` | 继续查质检、切换方向或退出 |

- 支持 `B20260001`、`B20260004` 等演示批号；缺少出库记录时显示「未知」，不编造客户去向。
- 查询失败保留当前步骤，提示重试或退出。
- 单轮结构化查询可走只读计划动作 `query_batch_trace`（S074），一次取用料、工序、质检与出库；固定流程用于逐轮引导。

## [重点] 维修工单（对话流程）

启动：说「维修工单」或「工单处理」，或模型调用工单工具。

| 步骤 | 节点 | 做什么 |
| --- | --- | --- |
| 选择工单 | `workflow_work_order_order` | 列待办，选择工单编号 |
| 操作类型 | `workflow_work_order_action` | 派工 / 维修 / 验收 / 退回 |
| 维修人 | `workflow_work_order_assignee` | 派工时选择维修人 |
| 处理说明 | `workflow_work_order_note` | 填写说明 |
| 确认执行 | `workflow_work_order_confirm` | 展示确认卡，等待人工确认 |
| 结果不确定 | `workflow_work_order_uncertain` | 不自动重试，要求核对 |
| 后续操作 | `workflow_work_order_followup` | 继续处理或退出 |

- 角色与状态不满足时立即提示（如非派工角色不能派工）。
- 版本冲突时刷新工单再操作；同一 `operationId` 可安全重试。
- 确认步的「取消」只回到上一步，不结束整个流程。
- 运维界面中的「报修」不走这条子图，而是主图的提议 + 审批；这条子图面向维修角色。

## [重点] 巡检

启动：说「巡检」或「巡检任务」。

| 步骤 | 节点 | 做什么 |
| --- | --- | --- |
| 创建任务 | `workflow_inspection_route` | 读取宿主上报的巡检路线，创建任务 |
| 站点结果 | `workflow_inspection_station` | 正常 / 异常 / 跳过 |
| 异常说明 | `workflow_inspection_note` | 异常或跳过时补说明 |
| 提交结果 | `workflow_inspection_advance` | 提交当前站，进入下一站 |

- 路线由宿主 `setInspectionRoute` 上报；站点含设备编号、名称、检查项。
- 「定位」会调用宿主 `fly_to_device`；定位成功与检查结果分别记录。
- 异常可转维修工单，仍需人工确认。
- 站点数据缺失时提示退出，不猜设备号。

## 命令词表

- 退出、取消、重试、确认、切换方向等命令集中在 `apps/server/src/workflows/commands.ts`。
- 提示词和宿主审批词表从同一份数据派生，避免「网关认为提交、宿主认为确认」这类不一致。
- 写流程用整句命令匹配 + 模型枚举兜底；「先不要提交维修」这类否定句不会触发写动作。

## 统一的失败处理

| 情况 | 行为 |
| --- | --- |
| 缺参数 / 格式错误 | 停留当前步，说明缺什么，等待更正 |
| 方向/动作不符 | 立即提示可选值，不推进 |
| 中台 5xx / 超时 | 停留当前步，提示重试或退出；不伪造结果 |
| 用户说退出/取消 | 结束流程（工单确认步的取消只回上一步） |
| 解析失败 | 单次模型兜底：选场景方法 → 校验后立即执行；选步骤回答 → 按本步规则推进；都不选 → 失败提示 |
| 写操作结果不明 | 标记「结果不确定」，要求人工核对，不自动重放 |
| 计划超出范围 | 整轮交回既有路径，不静默丢弃；非法计划最多修复一次 |
| 计划步骤失败 | 依赖步骤阻塞，独立步骤继续；只读叶步骤最多重试一次 |

## [重点] 工单字段与真实流程

> 真实维修工单通常怎么走、需要哪些字段，以及当前项目实现了哪一部分。

### 真实流程（常见 CMMS / 设备维保）

```text
报修申请
  → 审核 / 派工
  → 接单 / 到场
  → 维修处理（备件、工时、过程记录）
  → 完工
  → 验收 / 回访
  → 关闭
```

异常分支：驳回、转单、重派、暂停、交接、作废、超时升级。

### 各环节常见字段

| 环节 | 字段 |
| --- | --- |
| 报修 | 报修人、报修时间、设备编号、设备型号、故障描述、故障类型、紧急程度、是否停机、现场照片、报修地点 |
| 派工 | 派工人、派工时间、维修人/班组、计划时间、重派原因 |
| 接单 | 接单时间、预计到场、实际到场、接单状态 |
| 维修 | 检修人、维修过程、维修性质、备件消耗、工时、费用、现场资料 |
| 验收 | 验收人、验收时间、维修结果、费用、服务评价、反馈意见 |
| 关闭 | 回访/满意度、关单时间、是否闭环 |

### 当前实现到哪一步

当前只实现「报修 → 生成工单（待派工）」这一段，后续派工/维修/验收由对话式工单流程推进。

点击审批卡的「放大」按钮打开居中弹窗；设备 ID、当前告警只读，其余字段可编辑：

| 字段 | 当前 |
| --- | --- |
| 设备 ID | 只读 |
| 当前告警 | 只读 |
| 工单标题 | 可编辑 |
| 故障描述 | 可编辑 |
| 故障类型 | 可编辑（机械/电气/软件/工艺/安全/其他） |
| 紧急程度 | 可编辑（一般/紧急/特急） |
| 是否停机 | 可编辑 |
| 报修人 | 可编辑 |
| 联系电话 | 可编辑 |
| 期望完成时间 | 可编辑 |
| 处理参考 | 只读，折叠/限高，不写入工单 |

服务端把字段随审批提交给中台；mock 工单用 `metadata` 保存除标题/描述外的字段。

### 还没做

- 派工表单（维修人、计划时间、重派原因）
- 接单/到场时间
- 备件明细、工时、费用
- 维修过程记录与附件
- 验收评价、回访、关单
- 驳回、转单、暂停、作废等异常操作

这些不是当前报修弹窗的职责；如果要做完整 CMMS，需要单独的工作单管理页和状态机。

## 运维人员业务地图

> 当前 3D 场景 + 对话的用户是**车间运维/中控操作员**：负责实时盯设备、判断告警、报修、跟踪、交接班。
> 不是维修班组、不是派工员、不是验收人。

### 角色与每日闭环

```text
看场景/看告警
  → 判断是否误报
  → 能处理就按 SOP 处理
  → 处理不了就报修
  → 跟踪自己报修的进度
  → 交接班留下未闭环事项
```

核心诉求：**看得见、判断快、报得准、不重复、能追踪**。

### P0：当前界面应该做

| 业务 | 说明 | 当前状态 |
| --- | --- | --- |
| 实时设备状态 | 3D 标牌、颜色、当前告警 | 已有标牌/状态查询 |
| 告警查询与定位 | 查设备告警、飞到设备 | 已有 |
| 告警关闭 | 已处理/误报后，人工确认关闭 | 已有 |
| 告警确认/签收 | 标记已知悉 | 已有 |
| 误报/告警抑制 | 标记误报 | 未做 |

### 维修流程的边界

```text
运维（本界面）        调度/维修（其它界面）
报修  ───────────→  派工 → 接单 → 维修 → 完工
  ↑                                      │
  └──────── 只读进度 ←───────────────────┘
```

本界面只做「报修 + 进度查看」，不替别人接单、维修、验收。

### 重复报修规则

- **按设备去重**：同一设备已有未关闭工单（不是已关闭/已取消/作废）时，不再允许新建。
- 提示已有工单号、状态、标题；提供「查看进度」入口，而不是「再建一张」。
- 不同告警但同一设备，也拦截；避免一台设备多张并行维修单。
- 工单已关闭/取消/作废后，才允许重新报修。
- 旧会话历史里的工单号不作为依据，以中台当前查询为准。

## 业务系列与高价值场景

> 原则：动作可以多，系列不要多。告警确认、抑制、取消、升级都属于「告警处置」一个系列。

### 四个系列

| 系列 | 包含动作 | 入口 |
| --- | --- | --- |
| 告警处置 | 确认、误报/抑制、取消、升级、重复告警聚合 | 告警卡/对话 |
| 设备健康与报修 | 状态、历史、健康趋势、故障报修、本机报修、备件可用性 | 设备卡/对话 |
| 现场作业 | 巡检、3D 定位、空间邻域、交接班待办 | 场景/巡检卡 |
| 影响评估 | 批次影响、质量影响、生产/能耗影响 | 告警/设备/批次 |

知识库/SOP 不单独做系列，作为以上四个系列的辅助能力。

### 高价值场景

| 场景 | 价值 | 当前数据 | 建议 |
| --- | --- | --- | --- |
| 告警 → 批次影响 | 药厂最值钱：判断要不要隔离/召回 | 已实现只读 `batch.impact`（按设备） | P0（已做） |
| 重复告警聚合/告警风暴抑制 | 减少无效确认，发现劣化趋势 | 已实现只读 `alarm.repeats`；趋势/MTBF/MTTR 已实现 `alarm.trends`；抑制未做 | P0（部分） |
| 交接班待办闭环 | 不只是摘要，而是「哪些没闭环、谁跟进」 | 已有未确认计数、确认人、工单受派人 | P0（只读闭环已做） |
| 巡检异常 → 报修 → 批次影响 | 把现场异常和质量风险串起来 | 巡检、报修、`batch.impact` 已有；异常回复下已加「查影响批次/查备件」快捷动作，仍不自动执行 | P0（部分） |
| 设备健康档案/重复故障 | 「这台设备上周修过两次」 | 已实现只读 `device.health` | P1（已做） |
| 备件可用性联动报修 | 报修时就知道能不能修 | 已实现只读 `spare.availability`；领用申请 `spare.request` 已实现（人工确认，不扣库存） | P1（已做） |
| 停机/复产影响评估 | 停多久、影响哪些批次/订单 | 已实现只读 `downtime.impact`；复产清单未做 | P1（只读已做） |
| SOP 步骤化处置 | 告警不是「取消」而是按步骤处理留证据 | 已实现只读 `query_alarm_sop` 步骤引导；不自动执行，具体故障 SOP 依赖知识库覆盖 | P2（只读已做） |
| 告警超时升级 | 没人处理自动提醒班长 | 缺 SLA/通知 | P2 |
| 3D 空间邻域查询 | 「3 号设备附近有哪些设备/通道」 | 场景有坐标，缺空间查询接口 | P2 |

### 为什么这五个最值钱

1. **告警 → 批次影响**：把设备异常直接翻译成质量风险，是制药场景的核心价值。
2. **重复告警聚合**：运维每天被重复告警淹没；聚合比多一个「取消」按钮更有用。
3. **交接班待办闭环**：摘要只是看，闭环才是交接班真正要解决的问题。
4. **巡检异常 → 报修 → 批次影响**：把三条现有链路串成一条业务链。
5. **设备健康档案**：让「报修」从单次动作变成设备历史的一部分。

### 入口建议

不要为每个动作做入口。入口只保留：

```text
告警卡：确认 | 抑制 | 取消 | 升级 | 影响批次
设备卡：状态 | 历史 | 报修 | 本机报修 | 备件
巡检卡：站点结果 | 异常报修 | 影响批次
交接班：未闭环清单 | 生成摘要
```
