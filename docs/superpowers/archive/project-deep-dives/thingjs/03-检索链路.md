# THINGJS 文档 RAG · 检索链路
> 一句话定位：不是「问题转向量 → topK」，而是「先理解问题，再多路召回，再按 ThingJS 语义重排」。

## 总流程

入口：`server/src/retrieval/thingjsRetriever.ts` 的 `ThingJSRetriever.retrieve()`。

```text
问题
→ 意图识别（docs / offtopic）
→ 查询计划（归一化、错拼纠正、别名、实体/关系、否定、视点）
→ 向量召回 + BM25 多查询召回（并行）
→ 官方 EnsembleRetriever 加权 RRF
→ 补正文
→ 否定类排除
→ 采纳窗口 / 每类公平 / 文件内优先 / 精确符号置顶
→ 父块有界补全
→ 格式化 context
→ confidence / emptyReason / degradedReasons / phases
```

## 阶段 1：意图识别

实现：`server/src/retrieval/queryIntent.ts`

输出 `docs` 或 `offtopic`。规则是确定性的，不调用模型：

- **直接判定 offtopic**：
  - 空问题；
  - Kubernetes 请求（`k8s/pod/yaml/deployment` 且没有 ThingJS 意图）；
  - 其他框架请求（React/Unity/SQL 且没有 ThingJS 意图）。
- **直接判定 docs**：
  - 含 ThingJS 领域词（园区、孪生、相机、材质、飞到、挤出、热力……）；
  - 命中类目录（类名/全名出现在问题里，或编辑距离 ≤2）；
  - 命中别名；
  - 含强代码特征（`THING.X`、`app.`、PascalCase）。
- **offtopic 模式**：天气、笑话、菜谱、股票、星座、新闻、自我介绍等。
- **短寒暄**：你好、hi、谢谢、再见等。
- 最后兜底：有弱代码特征 → docs，否则 offtopic。

如果 offtopic，直接返回空结果，`emptyReason=offtopic`，生成层用固定话术回答，不调用模型。

补充两条 demo 相关规则：

- 领域词表额外覆盖 demo-index 的业务词（对象、事件、样式、图层、地球、瓦片、预制件、后期等），否则「动态修改对象的颜色」会被误判 offtopic。
- `unknown-class` 守卫会忽略 `ID / Name / Tags / CSS3 / SSAO / ECharts / URL / WMTS` 等业务缩写；但仍会拦截 `AbcMissingThing` 这种真正的未知 PascalCase 类名。

## 阶段 2：查询计划

实现：`server/src/retrieval/queryPlan.ts`、`queryRewrite.ts`、`queryEntities.ts`、`aliasStore.ts`

`buildQueryPlan()` 产出：

```ts
{
  original, normalized, vectorQuery,
  bm25Queries: string[],
  aliasExpand,
  rewrite, suggestions,
  exactSymbols, exactClasses, exactMembers,
  negatedClasses,
  resolution: { entities, pairs, candidates, classes, actions, negations, ambiguous, floor },
  viewpointAlternative
}
```

### 归一化与错拼纠正

- `normalizeQuestion()`：NFKC、去掉「怎么/如何/怎样/请问/一下」、去掉标点、压缩空白。
- `extractClassTokens()`：提取 PascalCase 和 `THING.xxx` 形式。
- `suggestClasses()`：按「问句包含类名 / 精确类名 / 类名前缀 / 邻近拼写」打分，最多 5 个建议。
- `uniqueNearClass()`：编辑距离 ≤2 且唯一命中才纠正；并列时不猜。
- 短词只接受显式 ThingJS 上下文中的相邻换位（`bxo → Box`），避免把普通英文单词纠正成类名。

### 别名展开

实现：`server/src/retrieval/aliasStore.ts`

- `data/aliases.yaml` 有 32 条别名（盒子→Box、挤出体→ExtrudeShape、摄像头→Camera……）。
- 长词优先、同一别名只取一次、区间不重叠，避免 `Box` 命中 `Box3` 的内部。
- 展开结果追加全名、类名、关键词，并生成 `hint`（「『盒子』→ THING.Box」）。
- 别名命中会绕过「未知类」判定。

### 实体/关系解析

`resolveQueryEntities()` 识别：

- 类（class）、成员（member）、动作（action）、值（value）、否定（negation）、上下文（context）。
- 角色：actor / target / receiver / context。
- 关系对：`QueryPair` 带 `status: confirmed | candidate | rejected` 和 `reason`。
- 特例：
  - 「相机看向/对准 X」→ 补 `Camera`，识别 `lookAt`；
  - 「飞到 X 旁边」且没有显式移动主体 → 视点移动特例 `viewpointAlternative`，主体按 Camera 处理，目标对象只是目的地；
  - 「不要销毁」→ 把 `destroy/destroyable` 加入否定成员，但「不能销毁」不算否定；
  - `style.color` 的小写前缀 `style` 即使与类名 `Style` 同名，也保留为精确成员。

### 否定与排除

- `extractNegatedMembers()`：抓「禁止/不要/不用/别用」后面的方法名，不当作检索目标。
- `extractForbiddenClassTokens()`：只抓「不要用 X / 不用 X」这类明确禁用类的说法；「不要 PixelLine」这种对比提及不排除。
- `negatedClasses` 只保留目录中真实存在的类；这些类从 `exactClasses` 和采纳结果中剔除，转入 `discarded`。
- 否定词剥离后可能留下裸命名空间（「不要用 THING.Marker」→「不要用 THING.」），`stripDanglingNamespace()` 清理。

### 多路 BM25 查询

`bm25Queries` 最多 6 条，优先级：

1. 归一化后的主查询；
2. 每个识别出的类单独一路（类多于剩余路数时打包合并）；
3. 「类名 + 构造函数 概述」——问句含 `new/创建/构造` 且类数 ≤3 时，为每个类补一路，避免多类创建问句只召回其中一类；
4. `lookAt`（视点问题）；
5. 前 2 个精确成员；
6. 别名展开、别名附加词、建议类名。

`vectorQuery` 是主查询 + 别名 + 建议 + `lookAt`，并剔除否定成员。

## 阶段 3：双路召回

### 向量召回

实现：`server/src/retrieval/vectorRetriever.ts`

```ts
store.asRetriever({ k: 28, filter: { sourceTypes: ['doc', 'module'] } })
// 类名/代码用法题 k 提高到 56；BM25 对应 80
```

- 走 LangChain 官方 `VectorStoreRetriever`，嵌入、topN、where 过滤由框架完成。
- 返回 `Document[]`，映射成 `ChunkHit`，按返回顺序记 `vectorRank`。
- `vectorScore = 1/(1+distance)`。
- 普通查询 topN=28；问题含明确类名或代码用法（事件/点击/绑定/示例等）时 topN=56，先把排在第 40 名后的 demo 代码纳入候选。
- 向量检索默认接受 `doc` 与 `module` 两类来源：`doc` 是 Markdown 文档，`module` 是代码示例/项目代码。精确符号召回仍以 `doc` 为主，代码通过 evidence 表补充用法证据。

### BM25 多查询召回

实现：`server/src/retrieval/bm25Retriever.ts`

- 每条查询各自 MiniSearch 打分，普通 topN=28；类名/代码用法题扩到 80。
- 多查询之间用官方 `EnsembleRetriever` 做 RRF（`c=60`，权重全 1），而不是把不同长度查询的原始 BM25 分直接相加。
- 回填的 `bm25Score` 取该 chunk 在各路中的最高原始分，供诊断。
- 最终按对应 topN 截断，记 `bm25Rank`。

### 为什么不是「三路并行」

- 实际并行的是 **向量 + BM25 两路**。
- 精确符号召回（`ExactSymbolRetriever`）是按元数据 `class_name / member_name / namespace` 查 LanceDB，不走向量；它在融合之后用于「精确置顶/补位」，不是第三路并行候选流。
- 不要把它讲成「三路召回并行」，否则面试官追问代码会对不上。

### 单路降级

```ts
Promise.allSettled([vector, bm25])
```

- 只有一路失败：另一路继续，`degradedReasons` 记录 `vector_unavailable` 或 `bm25_unavailable`，最终 `confidence` 从 `ok` 降为 `low`。
- 两路都失败：检索抛错，请求失败。
- 向量召回拆成 `embedding` 和 `vectorDb` 两段耗时，便于判断慢在模型服务还是数据库。

## 阶段 4：RRF 融合

实现：`server/src/retrieval/fusion.ts`

```ts
new EnsembleRetriever({
  retrievers: [FixedRetriever(vectorHits), FixedRetriever(bm25Hits)],
  weights: [1, 1],
  c: 60,
})
```

- `FixedRetriever` 是 `BaseRetriever` 的最小适配：只返回预计算文档，因为 `EnsembleRetriever` 需要 retriever 接口。
- 融合文档的 `pageContent` 必须是 `chunk_id`，`EnsembleRetriever` 用它去重和排序。
- 融合后按 `chunk_id` 回填两路的 `vectorRank / bm25Rank / text / images / source_type`。
- **官方 `EnsembleRetriever` 不暴露融合分**，所以 `fusionScore` 统一为 `null`；这不是 bug，是框架契约限制，已在复用决策里记录。
- 缺失正文的 chunk 用 `store.getByIds()` 批量补齐（hydrate）。

## 阶段 5：采纳与置顶

### 否定类先剔除

融合后的命中里，`class_name` 属于 `plan.negatedClasses` 的移出采纳流，写入 `discardedHits`，`evidence.missReason = 查询明确排除该类`。

> 当前实现的 `discarded` 主要承载「查询明确排除的类」；普通未采纳候选不会全部写入 discarded（`selectAdoptedAndDiscarded` 返回空 discarded）。面试时如果被问「discarded 是什么」，要按这个口径答。

### 采纳窗口

`adoptedLimitForPlan()`：

- 默认 `FINAL_TOP_K = 5`。
- 识别出 ≥2 个类，或 ≥2 个成员时：`n × PER_CLASS_ADOPTED`。
- 多类问题保证每个类都有机会进入窗口，而不是被一个类刷屏。

> 口径提醒：本页按 `project/04` 原文保留「每类 5 条」的表述；评测平台按响应里的 `effectiveTopK` 计分，当前实现口径是「普通题 5 条，多类/多成员 `n×3` 条」。被追问时以服务端实际采纳窗口和响应字段为准。

### 选择策略

`selectAdoptedAndDiscarded()`：

1. **命中了目录文件**（`matchedCatalogFiles`）时走 `stagedAdopt()`：
   - 只有 `source_type='doc'` 的块能算“目录文件命中”；demo 代码即使 `class_name` 相同也不参与，避免 `Box` 示例代码挤进 `THING.Box` 的证据窗口；
   - 文件内命中去重（同 class + member + file 只留一条）；
   - 每个已对上的文件先按槽位各取一条，单文件最多 3 条；
   - 全局还有其他类时，给其他类留名额；
   - 没有其他类时，再用同一文件把窗口补满。
2. **多个类**：`pickFairByGroup()` 按类轮转，每类最多 5 条。
3. **多个成员**：按成员轮转。
4. **普通情况**：`dedupeByClassMember()` 去重后截断。
5. **demo 代码预算**：普通类题保留 2 条代码证据；事件/点击/绑定/示例等代码用法题提高到 3 条。文档若先占满窗口，会替换尾部文档补回代码；精确文档置顶也预留代码名额。否则 `贴地多边形` 这类问句会被 5 条 demo 代码占满，把 `THING.EARTH.GeoGroundPolygon` 文档挤出窗口。

排序细节：

- 点名成员优先；
- 同档按「构造函数 → 概述 → 普通成员 → 实例属性/方法」排序；
- 构造函数/概述优先，避免回答缺构造签名。

### 精确符号置顶

`collectExactLead()`：

- 对 `resolution.pairs` / `candidates` / 已确认的复合类，按出现位置顺序：
  1. 先在融合结果里找同 class + member；
  2. 找不到再用 `ExactSymbolRetriever.find()` 按元数据查（limit 8）；
  3. 找到就放入 lead，标记 `matchMode=exact-symbol`，`adoptReason` 写清原因。
- 问「创建多个类」时，每个类至少取一条类片段；如果解析出动作，再取一条动作相关片段。
- 视点特例：问「不要用 flyTo，怎么飞到 X 旁边」时，lead 里优先放 `Camera.position`，再放 `Camera.lookAt`。
- `applyExactPlacement()` 把 lead 排在混合候选前面，不改融合分；没有 lead 时保持混合检索顺序。
- 找不到时把 `missReason` 写进 evidence（例如「THING.Box.width：索引无对应片段」），方便观测台和评测定位。

### 符号证据库

- 索引构建同时产出 `evidence.sqlite`：20,360 个符号、20,638 条提及、14,295 条签名。
- 每条提及带 `role`（definition / usage / reference）、`sourceKind`（official_doc / code_example / project_code）、owner、member、行号和来源文件。
- `augmentEvidenceHits()` 在融合和 hydrate 之后，用符号证据补充精确成员/签名的命中，不改变原始向量/BM25 排序；旧索引没有 `evidence.sqlite` 时为 null，行为退回纯元数据精确召回。
- 精确符号召回默认 `exactSourceTypes=['doc']`，避免 demo 代码抢占精确置顶；代码用法通过 `moduleQuota` 进入采纳窗口。
- 查询计划里的成员候选会用成员目录校验；目录存在时，像 `Box → Box3` 这种只在建议里出现、问题里没真正写出的类/成员不会进入精确目标。

### evidence 字段

每个最终 hit 带 `RetrievalEvidence`：

```ts
{
  matchMode: 'exact-symbol' | 'class-entity' | 'alias-compound' | 'hybrid',
  className, memberName,
  vectorRank, bm25Rank, fusionScore,
  finalPosition,
  adoptReason,
  missReason?
}
```

这是评测和观测台能解释「为什么这个块被采纳」的关键。

## 阶段 6：父块有界补全

实现：`server/src/retrieval/parentExpansion.ts`

- `parents.json` 加载到 LangChain `InMemoryStore<ParentContext>`。
- 按 `parent_id` 批量 `mget`。
- **不把整章父块粘进 context**：父块标题拼成 `【类名 · 章节 · 成员】` 标签；命中短片段时，在同一 `##` 章节内取不超过 1200 字的上下文窗口，窗口尽量从 h3 边界开始；`chunk_type='code'` 上限 1600 字符。
- demo 代码父块标题是 demo-index 的业务意图，用来补「这个示例解决什么问题」的语义。
- 这样 h3 保留成员级精确召回，h2 只提供有界邻接上下文，既避免碎片太短，也避免整章稀释 prompt。

## 阶段 7：上下文格式化

实现：`server/src/retrieval/context.ts`

每个片段：

```text
[#1] chunk_id=... | source_type=doc|module | corpus=api|example | class=Box | member=width |
     symbol=THING.Box | source=THING.Box.md | parent=实例属性
正文（截断 + 引用脱敏）

关联图片:
- ![alt](图片地址)
```

- `corpus` 由文件路径判断：`thingjs_api_v2.0 → api`、`thingjs_editor → editor`、`thingjs2.0demo → example`、`project_examples → example/project`、其他 → `doc`。
- 图片 URL 统一是 `/api/docs-assets/...`，生成层必须原样使用。
- 片段之间用 `---` 分隔。

## 输出与置信度

`RetrievalResult`：

```ts
{
  hits, discardedHits, context, sources,
  aliasExpand, phases,
  confidence: 'ok' | 'low' | 'empty',
  degradedReasons?,
  emptyReason?,
  suggestions, rewrite,
  effectiveTopK?,
  answerActorClasses?, answerTargetClasses?
}
```

规则：

- 有命中 → `ok`；无命中 → `empty`。
- 单路召回降级 → `low`，并带 `degradedReasons`。
- 未知类、offtopic 也会返回 `empty` + 对应 `emptyReason`。
- `phases` 记录 `queryIntent / queryPlan / vectorSearch / bm25Search / hybridWall / embedding / vectorDb / hydrateChunks / selectTopK / parentExpand / context / total`。
- `suggestions` 是错拼/未知类的「你可能想问」。
- `answerActorClasses / answerTargetClasses` 只在视点特例里出现，供生成层限制证据。

**当前未启用的契约字段**：

- `conflicts`：schema 和提示词都有冲突处理策略，但当前检索链没有生成 `conflicts`，实际返回空数组。
- `minFusionScore`：因为官方 `EnsembleRetriever` 不暴露融合分，当前不计算阈值。
- 面试时不要把这两个讲成已上线的能力。

## 三个典型问题怎么走

### 例 1：「THING.Box 怎么设置 width？」

1. 意图：命中类目录 → docs。
2. 查询计划：`exactClasses=[Box, THING.Box]`，`exactMembers=[width]`，`bm25Queries=[主查询, Box, width...]`。
3. 向量 + BM25 召回。
4. 融合后按 class+member 去重，构造函数/概述优先；`width` 成员片段被精确置顶。
5. 父块补上「实例属性」标签。
6. 生成层引用 `Box.width` 片段。

### 例 2：「不要用 flyTo，相机怎么飞到盒子旁边？」

1. 意图：领域词「相机/飞到/盒子」→ docs。
2. 否定：`flyTo` 进入否定成员，从向量/BM25 查询中剔除。
3. 实体：移动主体省略 → `viewpointAlternative`，Camera 作为 actor，Box 作为 target。
4. 精确 lead：`Camera.position` 置顶，`Camera.lookAt` 补位。
5. 证据筛选：只保留 camera 的 position/lookAt，其他类片段被排除。
6. 守卫：回答里只能操作 `camera`，不能 new 其他对象。

### 例 3：「同时创建 Box 和 Cylinder」

1. 识别 2 个类，`adoptedLimit` 按多类窗口扩大。
2. 每个类单独一路「类名 + 构造函数 概述」BM25 查询。
3. `pickFairByGroup` 每类轮转。
4. 构造函数片段优先。
5. 生成守卫：多对象示例里的配置字段/方法调用必须在证据里出现，否则触发纠错重试或回退。

### 例 4：「怎么动态修改对象的颜色和透明度？」

1. 问句没有显式类名，但命中业务词「颜色/透明度/样式」。
2. BM25 的 demo 代码块 `search_text` 包含 demo-index 业务意图「动态修改对象的颜色、透明度、轮廓高亮等视觉样式」，因此能召回 `thingjs2.0demo/对象效果/设置样式.js`。
3. 代码 chunk 的 `class_name` 是主类 `Box`，`chunk_type='code'`，父块标题是业务意图。
4. 上下文按代码上限 1600 字符保留完整示例；生成层引用该文件与 `Box` 文档。
5. `eval:demo` 用 File Hit@3 单独验证「业务意图 → 期望 demo 文件」，不和 API 类命中混在一起算。

## 性能与降级

- 向量全表扫描约 90ms（9,366 × 2560，项目文档实测）；BM25 内存索引。
- 两路并行，`hybridWall` 是墙钟时间，`vectorSearch`/`bm25Search` 是各自耗时。
- 检索队列 8 并发，超出排队；队列满 429，超时 504。
- 向量或 BM25 单路失败降级为 low；两路失败才报错。
- 父块、上下文格式化都是内存操作，耗时很小。

## 面试讲法

> 「检索侧我没有直接上向量 topK，而是先做查询计划：识别类、成员、否定和视点，做别名和错拼纠正，再生成多路 BM25 查询。召回是向量 + BM25 并行，用 LangChain 官方 EnsembleRetriever 做 RRF。融合后不是简单截断，而是按类/成员公平窗口、文件内优先、精确符号置顶，并给代码证据预留名额。切块上 H3 保留成员身份，同一 H2 内合并短成员成 900/1200 的检索块，精确成员用 `member_names` / `symbol_spans` 定位，查询时再扩有界上下文，不粘整章。每一步都有 phase 耗时和 evidence，评测平台能逐题看到命中/丢弃/原因。」
