# THINGJS 文档 RAG · 生成与会话记忆
> 一句话定位：把生成做成有契约的流水线——改写、记忆组装、JSON 输出、证据筛选、规则守卫、确定性清洗、引用对齐，而不是一次黑盒模型调用。

## 总流程

入口：`server/src/app/runtime.ts` 的 `runChat()` → `server/src/generation/generate.ts` 的 `generateAnswer()`。

```text
问题 + 会话/客户端 history
→ 判断独立切题 / 追问；追问才改写为可独立检索的问句（失败回退原问句）
→ 组装会话记忆：会话要求 + 摘要 + 最近问答组 + 相关历史（五阶段预算）
→ 识别代码/报错意图；检索（见「03-检索链路」）
→ 回答形态分类（与检索并行，失败回退 simple）
→ 选回答证据（禁用词 / 视点约束）
→ Prompt 渲染（answer / scene-code / code-debug；answer-format / answer-domain 注入）
→ LCEL: format → model.bind(response_format) → JSON 解析 → Zod
→ 领域守卫检查
→ 违规时一次纠错重试
→ 确定性清洗 sanitizeAnswerText
→ 引用选择/校验
→ 输出后置校验（finish_reason / completionTokens）
→ 汇总 usage / confidence / memory trace / degraded / timing
→ JSON 或 SSE done
```

## 多轮改写

实现：`server/src/generation/history.ts`

- 只在 `history.length > 0` 时调用。
- Prompt：`server/prompts/rewrite.yaml`，temperature 0.2，输入历史 + 当前问题，输出一条独立问句。
- 结果清洗：取第一行、去引号、截断 500 字符。
- 失败回退原问句，并把 `rewriteFallbackReason` 写进最终答案。
- 改写消耗的 token 会加到最终 usage。
- 历史里如果带上一轮回答的禁用名，先脱敏再改写。
- 中止（客户端断开/服务关闭）不是改写失败，直接抛出不回退，避免白跑。

**为什么不用 `RunnableWithMessageHistory`**：HTTP 契约是无状态的，历史由调用方显式传入；会话窗口由前端/服务端历史负责。复用决策 §6.11 记录了这一点。

## [重点] 会话记忆与 Token 预算

> 本节是 2026-11-19 首切片实装后的口径。旧的「摘要 500 / 最近 1200 / 相关 600」只用于复现旧基线。

### 会话、轮次与重试

- `chat_turns` 记录一轮状态（`running / ok / error / interrupted / cancelled`），`chat_steps` 记录 summary / rewrite / answer-shape / answer / scene-code / code-debug 的模型调用。
- 用户消息在模型调用前先入账；同一会话同时只允许一个 running turn；重复 `clientTurnId` 幂等；服务启动时把遗留 running 标记 `interrupted`。
- 重试：`/api/chat` 接受 `retryOfUserClientId` / `retryOfAssistantClientId`，只引用既有消息；服务端按会话归属、角色、配对校验，非法统一 400 `invalid_retry_reference`。前端保留原始字符串 ID，重试请求省略新增 `userClientId`。
- 普通轮次排除提前入账的本轮用户问题；重试额外排除原用户和被确证关联的旧助手尝试；筛选发生在最近窗口和相关历史候选之前。

### 记忆选取

- **独立切题 vs 追问**：`memoryIntent.ts` 用指代/承接信号和类目录判断；明确点名类/成员且无指代时跳过改写和摘要，追问才带历史。
- **最近历史**：以完整问答组为裁剪单位，窗口边界回填配对用户消息；旧助手消息只有在来源关联或可确证配对时才进入记忆，否则只保留可独立使用的用户消息。
- **相关历史**：对更早消息用 MiniSearch + jieba 检索，扩成原始问答组后去重、按时间排序；预算不足时按组舍弃或裁剪内容。
- **会话要求**：`chat_sessions.requirements_json` 保存语言/格式要求及来源用户消息；程序规则识别，来源 ID + 顺序保证幂等；明确撤销后不再采用；回答使用独立区块，随模板进入 `promptVersion`。
- **摘要边界**：从过滤本轮消息之前的原始有序快照确定上界，取「当前用户消息、最近窗口第一组起始消息、较早未完成轮次起始消息」中最早的一条；批次只处理边界之前的完整历史组，游标只跨过实际归档的消息。
- **摘要迁移**：旧格式摘要保留供降级排查，模型先使用原始历史；首次压缩从最早仍保留的消息重建，摘要 + 游标 + 格式版本同一事务保存，取消/条件写入不覆盖已提交状态。

### 预算与输出校验

实现：`server/src/generation/memoryBudget.ts`、`server/src/generation/memoryLimits.ts`

| 阶段 | 输入上限 | 记忆上限 | 输出上限 | 安全系数 |
| --- | ---: | ---: | ---: | ---: |
| rewrite | 2,048 | 512 | 1,024 | 0.2 |
| summary | 3,072 | 2,300 | 512 | 0.2 |
| answerShape | 2,048 | 0 | 128 | 0.1 |
| answer | 8,192 | 2,300 | 1,536 | 0.2 |
| code | 12,288 | 2,300 | 3,072 | 0.2 |

```text
requestBudget = modelContextLimit - outputReserve - envelopeReserve
memoryBudget  = max(0, min(2300, requestBudget - fixedParts))
```

- 回答阶段记忆总上限 2,300 估算 token；改写、摘要、形态、回答、代码分别计算，`fixedParts` 包含该阶段提示词和固定输入。
- 中文按 1.5 字/token、ASCII 4 字/token 估算；首轮校准 303 样本：中位比 0.96、平均绝对误差 5.5%、P95 14.7%、最坏低估 51.4%，因此字符估算不能直接当 generation 硬上限。
- 网关探针显示 `max_tokens` / `max_completion_tokens` / `max_output_tokens` 都被忽略（32 上限实际 output 161–636，`finish_reason` 仍为 `stop`）；服务端改为后置校验：`finish_reason=length` 或实际 `completionTokens > 阶段上限` 时，改写回退、摘要不写入、回答走证据降级。
- **观测**：`memorySelection` 记录模式、选中/排除 ID、要求、摘要跳过和非法要求标记；`budgets` 记录各阶段计划；调用详情仍保存实际 system/history/user 提示词。
- **效果**：20 轮输入 118,097 → 83,162（-29.6%），调用 77 → 55，摘要 17 → 5，改写 20 → 10，当前问题重复 20 → 0；预算核对 80/80 条，memory/request/output 超限均为 0。单次实装，不是 3 次重复，回答质量仍需人工评分。
- **暂不做**：跨会话向量记忆、用户级长期画像；当前只做会话级记忆。

## Prompt 与版本

实现：`server/src/generation/prompts.ts`

- 文件：`server/prompts/answer.yaml`、`answer-shape.yaml`、`answer-format.yaml`、`answer-domain.yaml`、`rewrite.yaml`、`session-summary.yaml`、`scene-code.yaml`、`hints.yaml`、`code-debug.yaml`。
- `answer-shape.yaml`：文档问答分类器，只输出 `primary/secondary/flags/writeCode/confidence`；`runChat` 中与检索并行调用，失败/低置信度回退 `simple`。
- `answer.yaml` 只保留通用契约、质量要求、输出 JSON；`generate.ts` 的 `answerRuleVars` 读分类结果，从 `answer-format.yaml` 选格式，从 `answer-domain.yaml` 注入共享/创建/操作/销毁/视点/否定/冲突/图片规则。
- 格式：YAML + mustache 占位符，由 LangChain `ChatPromptTemplate` 渲染。
- `answer.yaml`：
  - 声明 `temperature: 0`
  - `response_format: json_object`
  - system 里是完整的 ThingJS 回答规范（最小充分、只使用上下文、禁止内部路径、禁止元说明、参数表签名、Box 构造、多对象、destroy、视点、来源优先级、图片等）。
  - 分类器 `writeCode=true` 且用户要求写场景代码时，切换到 `scene-code.yaml`，直接生成使用场景对象 ID 的代码，不再只给文档解释。
  - 回答组织按问题类型选择：怎么用/参数 → 直接答案/最小示例/注意事项；A 与 B 对比 → 结论/对比表/适用场景；不生效/报错 → 结论/原因/修复/依据/验证边界；简单事实问题 1–3 句，不强行分节。先给直接答案，不写「根据文档」开场。
  - 依据默认由 `citations` 提供；正文只在需要时列 1–3 条关键片段，不复制整段文档。
  - user 是 context + question。
- 提示词版本：所有 YAML 文件名排序后拼接 `name\0content\0` 的 sha256 前 12 位。
  - 出现在 `/api/health`、`/api/chat` 响应、调用记录、生成评测报告。
  - 进程内缓存，**改 YAML 后需重启**。
- `hints.yaml` 集中放空结果、别名、冲突、图片等话术，避免散落在代码里。
- `code-debug.yaml`：显式 `code`/`errorText`，或单框问题里出现代码围栏、`new THING.`、`const/let/var`、报错/堆栈等特征时启用；输出「结论 / 原因 / 修复 / 依据 / 验证边界」；只依据检索证据，不执行代码，不声称验证过修复。代码阶段的预算为 12,288 / 2,300 / 3,072；检索查询里的代码/报错截断到 2,000 字符，生成层保留完整内容。

> **温度绑定**：`answer.yaml` / `code-debug.yaml` 声明 `temperature: 0`，`rewrite.yaml` 声明 0.2。`createChatModel(env, apiKey?, temperature)` 接收温度；`runChat` 按提示词声明的温度取模型，`llmPrompt.temperature` 记录的就是实际使用的值。共享模型按温度缓存，请求级令牌每次新建实例。

## 回答形态分类

实现：`server/src/generation/answerShape.ts`、`server/prompts/answer-shape.yaml`

- 用同一个聊天模型做轻量分类，输出：
  - `primary`：`create` / `operation` / `compare` / `troubleshoot` / `simple`；
  - `secondary`：`operation` / `create`；
  - `flags`：`destroy` / `viewpoint` / `forbidden` / `path` / `conflict` / `images`；
  - `writeCode`、`confidence`。
- 解析失败、超时或 `confidence < 0.5` 回退 `simple`，不阻断回答。
- 分类只影响 Prompt 的格式段和领域规则注入（`answer-format.yaml` / `answer-domain.yaml`），不改变检索结果和回答证据。
- `writeCode=true` 且用户要求写场景代码时切到 `scene-code.yaml`，直接生成使用场景对象 ID 的代码。

## 回答证据筛选

实现：`server/src/generation/evidence.ts`

`selectAnswerEvidence(question, retrieval)`：

- 先提取 `forbiddenTerms`：只处理「不要用 / 禁止 / 避免 / 不得 / 不准 / 勿」后面紧跟的标识符，取末端成员名，长度 ≥3。
- 如果没有禁用词、也没有「actor + target」视点约束，直接返回全部检索命中。
- 有约束时逐条筛：
  - 成员名在禁用列表 → `forbidden-member`；
  - 片段正文含禁用词 → `forbidden-text`；
  - 视点问题里不是 actor 类 → `non-actor`；
  - 视点问题里成员不是 `position/lookAt` → `unrelated-member`；
  - 视点问题里没有 `position` → 所有命中标记 `missing-position`，清空证据。
- 被排除的片段写入 `excludedAnswerEvidence`，最终答案里可以解释「为什么没引用它」。
- 如果筛选后的 context 仍含禁用词，直接清空证据，返回「资料不足」。

**注意**：禁用词只影响「回答证据」，不修改原始召回列表；`retrieved` 仍然展示召回结果，`answerEvidenceIds` 才是实际喂给模型的证据。

## LCEL 链

实现：`server/src/generation/answerChain.ts`

```ts
format (RunnableLambda: prompt.formatMessages)
  .pipe(run (createModelRunnable + response_format))
  .pipe(parse (parseAnswerResponse))
```

### 模型封装

实现：`server/src/generation/chat.ts`

- `ChatOpenAI`：回答 `temperature = 0`（按 `answer.yaml` 声明）、改写 `0.2`（按 `rewrite.yaml` 声明）、timeout 60s、`maxRetries: 0`（重试交给 LangChain Runnable）、`enable_thinking: false`（避免 reasoning 内容污染 JSON）。
- `createModelRunnable()`：`RunnableLambda.from(invoke).withRetry({ stopAfterAttempt: 2 })`。
- 不手写退避/计数。

### JSON 解析

`parseLlmJson()` 三级兜底：

1. 如果模型返回对象，直接 `LlmJsonSchema.parse`；
2. 原文 `JSON.parse` → Zod；
3. LangChain `JsonOutputParser.parse`（能处理 markdown 围栏/前后缀）；
4. `jsonrepair` 修复缺引号、尾逗号等常见模型输出问题，再 `JSON.parse`。

`LlmJsonSchema`：

```ts
{
  reasoning_summary?: string,
  final_answer?: string,
  citations?: string[]
}
```

如果全部失败，把原文当 `final_answer`，引用用本次证据的前几个 chunk 兜底，`fallback: true`。这样 `llmPrompt / usage` 契约不会丢。

## [重点] 回答守卫

实现：`server/src/generation/guards.ts`、`server/src/generation/checks.ts`

### 检查项

`inspectAnswer()` 返回：

| 检查 | 规则 |
| --- | --- |
| `forbidden` | 回答里出现用户明确禁用的 API 名 |
| `boxConstructor` | `new THING.Box({ width/height/depth ... })` 这种无证据的对象字面量构造；宽高深必须按参数表位置传入 |
| `animation` | 回答出现 `requestAnimationFrame / 逐帧 / 插值 / tween / lerp` 等，但证据里没有 |
| `multiObject` | 多对象代码里的配置字段/方法调用在证据里找不到 |
| `viewpoint` | 已确认是相机视点移动时，回答操作了 `camera.position/lookAt` 以外的对象或成员 |

`violatesGuards()` 任一为真即违规。

### 一次纠错重试

```text
首轮违规
→ onReset（SSE 清空预览）
→ 生成 correctionMessage（只描述哪里越界，不引入证据外 API）
→ 把 correction 作为新的 HumanMessage 追加
→ 再调用一次模型
→ 重新解析
→ 仍违规：safeFallback=true，返回「资料不足以给出可验证实现」
```

- `answerGuard.modelCallCount` 记录调用次数（1 或 2）。
- `answerGuard.status`：
  - `not_applicable`：没有禁用词，且首轮没有触发纠错（当前实现按 `forbiddenTerms.length` 初始化，所以视点守卫首轮未触发时也可能是这个值）；
  - `first_pass`：有禁用词，首轮通过；
  - `retry_pass`：纠错后通过；
  - `fallback_violation`：纠错后仍违规；
  - `fallback_error`：纠错调用异常；
  - `no_answer_evidence`：证据被用户约束全部排除。
- `triggerReasons` 记录多对象等具体原因。

### 为什么用规则而不是再调一个模型

- 这些是 ThingJS 领域规则（Box 构造、视点、多对象），通用模型裁判不稳定且慢。
- 规则是确定性的、可单测的、可在评测里复现的。
- 裁判模型放在评测平台做离线质量评估，不放在在线生成链路的强约束里。

## [重点] 确定性清洗

`sanitizeAnswerText()`：

即使守卫通过，模型仍可能带元说明或泄漏路径。清洗做这些事：

1. **资源路径**：`xxx.gltf / xxx.glb / xxx.bin` → `你的模型资源路径`；`你的3D模型路径` → `你的模型资源路径`。
2. **代码块先摘出**，避免按句过滤把整块代码删掉。
3. **按句删除**：
   - 元说明/免责话术：「根据最佳实践」「以实际运行结果为准」「取决于引擎实现」「通常独立生效」「释放资源」「从场景移除」等；
   - 证据里不存在的 `THING.<类名>`；
   - 证据里不存在的构造 `new THING.X`；
   - 证据里没有的默认值断言（`默认值为 true/false/数字`）；
   - 含内部路径（`assets/`、`src/`、`examples/`、`models/`）的句子。
4. **代码块内**：
   - 含不支持的类/构造/默认值的行注释掉；
   - `destroy()` 之后继续读取同一对象的行注释掉；
   - 多行对象/调用按括号深度整块注释，避免留下半截代码。
5. **内部 Markdown 路径**：`THING.X.md`、`docs/...md` 不出现在回答里。

这一步不增加模型调用，直接把常见幻觉和路径泄漏消掉。

## 引用选择

实现：`server/src/generation/citations.ts`、`server/src/generation/generate.ts`

### 从回答正文反推引用

`citationsFromAnswer(answer, selected)`：

- 对每条证据打分：
  - 回答里同时提到类名和成员名 → 5；
  - 回答里有 `new THING.X(...)` 且是类概述片段 → 4；
  - 只提到类名 → 2；
  - 没提到类名 → 0，不引用。
- 多类问题先按类各取一条最佳片段，保证每个类都有引用。
- 再用正文实际用到的成员片段/构造概述补足，最多 3 条。
- 同类无关成员不凑数，避免引用和正文不对齐。

### 回退模型声明的引用

如果正文没有可用引用，`validateCitations(parsed.citations, evidence.hits)`：

- 只保留本次回答证据里真实存在的 `chunk_id`；
- 去重；
- 至少 1 条，最多 `FINAL_TOP_K`；
- 如果模型一条都没给，用证据第一条兜底。

### 引用与 discarded 互斥

评测会检查 `citations` 不能指向 `discarded`；生成层引用的来源是 `evidence.hits`，而 discarded 已经被排除，所以天然互斥。

## [重点] 流式问答（SSE）

实现：`server/src/generation/stream.ts`、`server/src/app/http/sse.ts`

### 事件

`POST /api/chat` 传 `stream: true` 返回 `text/event-stream`：

| event | data | 说明 |
| --- | --- | --- |
| `phase` | `{ phase, ms, startMs? }` | 改写/检索/生成阶段完成 |
| `delta` | `{ text }` | `final_answer` 的增量预览 |
| `reset` | `{ reason? }` | guard 重试或模型重试，前端清空预览 |
| `done` | `{ ok: true, traceId, ...ChatResponse }` | 与普通 JSON 同构的最终结果 |
| `error` | `{ ok: false, traceId, code, error }` | 流开始后的失败 |

### 增量提取

模型仍然输出结构化 JSON，不能直接把原始 token 当答案。`createAnswerDeltaExtractor()`：

- 先判断模式：`{` → JSON；```→ 等出现`{` 再按 JSON；其他 → plain。
- JSON 模式下找到 `"final_answer": "` 的起始位置。
- 用 `decodeJsonString()` 只解码 JSON 字符串，不尝试完整解析对象；能处理 `\" \\ \n \t \uXXXX`，末尾半个转义序列留到下一块。
- 只把已解码的增量发给前端。
- 最终结果仍走 `parseAnswerResponse()`，前端预览不是权威结果。

### 重试与重置

- `streamModelAnswer()` 用 `RunnableLambda` 包 async generator，再 `.withRetry({ stopAfterAttempt: 2 })`。
- 每次尝试前 `extractor.reset()`；`attempt > 1` 时发 `onReset('模型重试')`。
- guard 触发重试时也发 `onReset('回答校验重试')`。
- 客户端断开 → abort → 服务端停止模型调用，记录 `client_aborted`。

### 非流式

`stream` 缺省或 false 时走普通 `chain.invoke()`，行为不变；客户端断开同样 abort。

## 降级

`runChat()` 的捕获逻辑：

| 错误类型 | 是否降级 | 说明 |
| --- | --- | --- |
| abort / 客户端断开 / 服务关闭 | 否 | 直接抛出，记录 `client_aborted` / `server_shutdown` |
| `HttpStatusError`（队列满/超时） | 否 | 服务端结论，不能伪装成降级答案 |
| 网关致命错误（401/403/429/504 等） | 否 | 鉴权/配额/模型权限问题，不能降级 |
| 其他模型/熔断错误 | 是 | `degradedFromRetrieval()` 返回检索片段 + `degraded=true` |

降级答案：

```text
模型暂不可用（原因）。以下是已检索到的文档片段，请自行阅读：
<context>
```

- `degradedReasons` 包含 `generation_unavailable` 和检索侧降级原因。
- 如果检索片段含禁用词，返回「当前无法给出满足要求的可验证答案」。
- `confidence` 沿用检索置信度。
- 降级次数计入 `thingjs_events_total{event="degraded"}`。

## 时间与用量

- `runChat` 记录阶段：`rewrite / retrieval / generation / total`，以及检索子阶段。
- `RagAnswer.timing`：

  ```ts
  {
    totalMs,
    phasesMs: { 'retrieval.vectorSearch': ..., ... },
    phases: [{ phase, ms, startMs }]
  }
  ```

- usage：
  - 改写调用 + 生成调用（+ 纠错重试）逐项相加；
  - `promptTokens / completionTokens / totalTokens` 允许 null（网关没上报时）。
- `indexVersion / indexBuiltAt / promptVersion` 写进响应，便于观测台定位「这条回答跑在哪个索引/提示词上」。

## 对外答案契约

实现：`server/src/schemas/answer.ts`

关键字段：

```ts
{
  answer, reasoningSummary,
  citations, retrieved, discarded,
  answerEvidenceIds, excludedAnswerEvidence,
  answerGuard: { status, modelCallCount, retrievalConfidence, triggerReasons? },
  llmPrompt: { promptName, promptVersion, model, temperature, responseFormat, messages },
  usage,
  confidence, emptyReason, degraded, degradedReasons,
  suggestions, rewrite, rewriteFallbackReason,
  indexVersion, indexBuiltAt, promptVersion,
  timing
}
```

- `retrieved` 是全部召回；`answerEvidenceIds` 是实际喂模型的证据；`citations` 是最终引用。
- `llmPrompt.messages` 写的是实际格式化后的 system/user（含 context），观测台可以复盘。
- `answerGuard` 让评测和观测能区分「一次过 / 纠错过 / 回退」。

## 面试讲法

> 「生成侧我把它当成一个有契约的流水线，而不是一次模型调用。Prompt 是 YAML 版本化的，要求结构化 JSON；温度也由 YAML 声明并真正绑定到模型：回答 0、改写 0.2。解析有三层兜底，解析失败也保留原文和 usage。回答前先做回答形态分类，决定用哪套格式和领域规则，再用用户禁用词和视点约束筛证据；回答后用规则检查 Box 构造、动画、多对象和视点越界，违规只纠错一次，仍不行就回退成可验证的最小回答。最后再做一层确定性清洗，去掉元说明、内部路径、证据外 API 和 destroy 后读取。引用不是模型说了算，而是按正文实际提到的类/成员反推，保证引用和答案对齐。多轮场景不是把历史全塞进去，而是按会话要求、摘要、最近问答组和相关历史组装，并用五阶段预算和 trace 控制；代码/报错题走独立链路，不执行用户代码。」
