# THINGJS 文档 RAG · 评测平台与质量门禁
> 一句话定位：评测不是跑几个例子看感觉，而是黄金集 + 确定性指标 + 独立裁判 + 基线 + 三套门禁 + 配置版本 + 发布检查。

## 为什么单独做一个进程

评测平台 `review/`（端口 9968）不是服务端的一个路由，而是独立 TypeScript 服务：

- 只通过 HTTP 调服务端，不 import 服务端实现；
- 黄金集、评分、门禁、报告、问题队列、发布检查都在这里；
- 模型/网关配置从 `server/.env` 读取，不复制密钥；
- 评测调用带 `x-thingjs-eval-run` / `x-thingjs-eval-kind`，与生产统计隔离。

这样服务端保持单一职责，评测可以独立运行、独立扩展，也不会因为评测代码把服务端依赖搞乱。

## 六个视图

| 路由 | 视图 | 作用 |
| --- | --- | --- |
| `/calls` | 调用观测台 | 调用列表、详情、阶段耗时、提示词、重放 |
| `/trends` | 趋势 | 调用/错误/点踩率/空结果率、P95 阈值线、索引版本表 |
| `/issues` | 问题队列 | 状态流转、分类、回归用例、验证记录 |
| `/evals` | 评测历史 | 检索/生成/回归运行、趋势、失败用例、批量建单 |
| `/verify` | 回归验证 | 单题/回归/发布三种验证模式、队列、运行记录、封版窗口 |
| `/release` | 发布检查 | 三套门禁、未关闭 P0/P1、质量阈值、自动门禁、KB 健康 |

### 检索题字段

```ts
{
  id, question,
  expectClass,
  acceptableClasses?,   // 同义可接受类
  expectClasses?,       // 多类题，每类都要命中
  forbiddenClasses?,    // 禁止出现的类
  expectMember?,
  answerable?,          // false 表示负例，应返回 empty
  tag?: 'class'|'member'|'colloquial'|'typo'|'mixed'|'negative'

```

### 难度分层

`tag` 用来防止「只优化简单题」：

- `class`：类级问题；
- `member`：成员级问题；
- `colloquial`：口语化（盒子、摄像头、飞到……）；
- `typo`：错拼（bxo、THING.bxo……）；
- `mixed`：多类/多成员；
- `negative`：负例（应拒答/空结果）；
- `code`：代码/报错题；
- `real`：真实问法。

### 覆盖审计与分层

- core：100 检索 + 30 生成 + 12 裁判校准，负责每次改动的回归与门禁。
- coverage：161 条，按 API 类/成员分层抽样，回答「知识库覆盖得怎么样」。
- real：30 条，使用更接近用户的问法，回答「题目是否像真实用户」。
- code：20 条，带代码/报错，回答「贴代码能不能排错」。

## [重点] 检索评分

实现：`review/src/eval/scoreSearch.ts`

### 指标

| 指标 | 定义 |
| --- | --- |
| Class Hit@1 | 每一组期望类，在 top1 至少命中一个 |
| Class Hit@3 | 每一组期望类，在 top3 至少命中一个 |
| Class Hit@K | 每一组期望类，在 topK 至少命中一个；K = `effectiveTopK` |
| Member Hit@1/3 | 同一 chunk 同时含期望类和成员，在 top1/top3 |
| Member MRR | 第一个同时含类和成员的 chunk 的 `1/rank` |
| false-empty | 可回答题返回 empty，且 Class Hit@K 未命中 |
| forbiddenViolation | 禁止类出现在评分窗口 |
| strictClassHitAtK | 按元数据 `className` 精确相等，而不是正文包含 |
| strictMemberHitAt3 | 按元数据 `memberName` 精确相等 |
| unscorable | 元数据缺失，无法严格评分 |

`effectiveTopK` 来自响应；响应缺失时评测按「多类题 `max(8, 类数×3)`」兜底。服务端实际采纳窗口是：普通问题 5 条，多类/多成员 `n×3` 条。

### 单题通过条件

```text
可回答题：
  positivePass（有 forbidden 时看 exactClassHit，否则看 Class Hit@K）
  && 有 expectMember 时 Member Hit@3
  && 无 forbiddenViolation
  && 非 forbiddenUnscorable

负例题：
  confidence === 'empty' 或 chunks.length === 0
```

`passed` 是宽松口径（正文包含即可）；`strictCaseStatus` 是严格口径（元数据相等）。门禁用哪个口径取决于指标。

### 门禁阈值

`searchGateFromEnv()`：

| 阈值 | 默认 | 含义 |
| --- | --- | --- |
| `GATE_CLASS_HIT8` | 0.9 | Class Hit@K ≥ 90% |
| `GATE_MEMBER_HIT3` | 0.75 | Member Hit@3 ≥ 75% |
| `GATE_FALSE_EMPTY` | 0.02 | false-empty ≤ 2% |
| `GATE_COLLOQUIAL_HIT8` | 0.7 | 口语题 Class Hit@K ≥ 70%（至少 5 题） |
| `GATE_LAYERED_MEMBER_HIT3` | 0.7 | member 分层 Member Hit@3 ≥ 70%（至少 5 题） |
| `GATE_TYPO_HIT8` | 0.5 | 错拼题 Class Hit@K ≥ 50%（至少 3 题） |

另外：

- 禁止类命中必须为 0；
- 门禁必须跑完整黄金集；`--ids` 只能排查，不能当门禁；
- 单题评测异常（`evalError`）算该题失败，整批不中断。

### 基线对比

实现：`review/src/eval/baseline.ts`

基线固定在 `server/plans/baseline/search-gate.json`，比对：

- Class Hit@K 不低于基线；
- Member Hit@3 不低于基线；
- false-empty 不高于基线；
- forbiddenViolations 不高于基线。

基线缺失按阻塞处理；确需跳过要显式 `--no-baseline`。

## [重点] 生成评分

实现：`review/src/eval/scoreGeneration.ts`

### 确定性检查

| 检查 | 规则 |
| --- | --- |
| schema | 响应能被契约解析（能拿到 body 即视为 true） |
| confidence | 与期望一致；可回答题默认 `ok`，负例默认 `empty` |
| citationValid | 引用都在 `retrieved`（或 `answerEvidenceIds` 范围内），数量 ≥ `minCitations` |
| citationDiscardedDisjoint | 引用不指向 `discarded` |
| classMention | 回答或 retrieved 中出现期望类 |
| memberMention | 回答中出现期望成员 |
| mustMention | 必须提及的词都出现 |
| mustNotMention | 禁止提及的词不出现（否定句里的提及不算违规） |
| mustNotAppear | 显式禁用名称完全不出现 |
| codeOk | 要求代码块时有代码块 |
| pathSanitized | 不出现场景路径、`.gltf/.glb/.bin` 文件名、绝对路径 |
| noInternalPath | 不出现 `THING.X.md`、`docs/...md` |
| templateSkip | 低/空置信时不应调用 LLM；高置信应调用 |
| guardPassed | 不是 `fallback_violation/fallback_error/no_answer_evidence` |
| negativeCorrect | 负例应 `empty` 且不调用 LLM |
| unexpectedDegraded | `confidence=ok` 但 `degraded=true`，算异常 |
| thresholdInjury | 期望类只出现在 `discarded` |

### LLM 裁判

实现：`review/src/eval/judge.ts`

裁判输入：

- 问题、评分重点、参考提示、参考事实、禁止事实、继承事实；
- 回答、引用（带正文）、retrieved 证据（不用 discarded）。

裁判输出：

```ts
{
  grounded_in_context: 1-5,
  answers_question: 1-5,
  citation_alignment: 1-5,
  hallucination: boolean,
  api_usage?: 1-5,
  citation_supports?: boolean,
  failed_facts: string[],
  unsupported_claims: string[]
}
```

通过条件：

```text
grounded_in_context >= 4
&& answers_question >= 4
&& citation_alignment >= 4
&& !hallucination
```

答案正确：

```text
api_usage >= 4
&& answers_question >= 4
&& !hallucination
&& failed_facts 为空
```

设计要点：

- 裁判是一个**独立模型**（`JUDGE_MODEL`，当前 `deepseek-v4-pro`，与基线一致），支持 `response_format: json_object`，不支持时自动退回普通 JSON。
- 温度 0，超时 180s（长样本需要更宽窗口）。
- 系统提示里给了评分锚点和 ThingJS 领域核对规则（Box 构造、多对象、否定语义、相机移动、辅助调用）。
- 12 条人工标注样本用于校准；提示或模型变化后跑 `pnpm eval:judge:calibrate`，避免门禁失真。
- 裁判只用于评测，不进入在线生成链路的强制约束。

`generationGateFromEnv()`：

| 阈值 | 默认 |
| --- | --- |
| `GATE_GEN_SCHEMA` | 1.0 |
| `GATE_GEN_CONFIDENCE` | 1.0 |
| `GATE_GEN_CITATION_VALID` | 1.0 |
| `GATE_GEN_CLASS_MENTION` | 0.95 |
| `GATE_GEN_MEMBER_MENTION` | 0.85 |
| `GATE_GEN_PATH_SANITIZE` | 1.0 |
| `GATE_GEN_NEGATIVE` | 1.0 |
| `GATE_GEN_INJURY` | 0（阈值误伤率上限） |
| `GATE_GEN_JUDGE_PASS` | 0.8 |
| `GATE_GEN_HALLUCINATION` | 0 |

额外要求：

- 生成黄金集至少 30 条；
- 门禁必须全量；
- 所有 eligible 案例都必须有裁判结果，裁判失败算门禁失败；
- `--no-judge` 不能用于生成门禁。

### 生成基线

`server/plans/baseline/generation-gate.json`，比对 10 项指标：

`schema / confidence / citationValid / classMention / memberMention / pathSanitize / noInternalPath / negative / injury / judgePass`。

唯一容忍：`judgePassRate` 允许 1 个样本的波动（`1/可回答数`），因为裁判和回答都是模型采样；绝对下限仍由 `minJudgePass` 守门。

## 回归评测

实现：`review/src/quality/regression.ts`

- 回归用例来自问题队列，写入 `review/fixtures/regression-search.json` / `regression-generation.json`。
- 用例只增不删，可 `disabled`。
- 单题排查：

  ```bash

  ```

- 回归门禁：

  ```bash
  pnpm eval:regression:gate
  ```

  - 回归集必须 100% 通过；
  - 必须全量；
  - 生成回归需要裁判，不能 `--no-judge`；

- 回归集复用黄金集的评分/裁判/报告，只替换题集与基线（回归不对比基线，逐题通过即可）。

## [重点] 发布门禁（自动）

实现：`review/scripts/publish-gate.ts`

服务端 `DOCS_WATCH_GATE_CMD` 可以指向：

```bash
pnpm -w eval:publish-gate
```

流程：

```text
比对 /api/health 的索引版本与提示词版本
→ 不一致直接退出 2（说明门禁跑在旧版本上）
→ 检索门禁
→ 检索回归门禁（空集跳过）
→ PUBLISH_GATE_GENERATION=1 时：生成回归 + 生成门禁
→ PUBLISH_GATE_KB=shadow|1 时：KB 门禁
→ 全部通过退出 0，任一失败退出 1
```

- 内置 240s watchdog（`PUBLISH_GATE_TIMEOUT_MS`），早于服务端 300s 回滚超时。
- 服务端门禁失败会回滚 `active.json` 并热加载旧版。
- `PUBLISH_GATE_KB=shadow` 只记录结果，不阻断；`=1` 时阻断。
- KB 门禁只判定四条：`KB-C05`（解析成员全部入索引）、`KB-Q07`（父块缺失）、`KB-V01`（索引结构）、`KB-F01`（docs 指纹一致）。报告缺失、版本不一致或 fast 报告按失败处理。
- 默认关闭阻断，建议至少积累 3 个索引版本的报告后再启用。

## 回归验证（Verify Runs）

实现：`review/src/quality/verifyRuns.ts`

三种模式：

| 模式 | 用途 |
| --- | --- |
| `single` | 单题排查；可指定 search/generation、golden/regression、ids |
| `regression` | 跑整套回归集 |
| `release` | 发布前跑三套门禁 |

- 任务状态：`running / passed / failed / error`。
- 步骤状态：`pending / running / passed / failed / skipped`。
- 队列来自问题队列的待验证问题。
- 运行结果写入 `/ops/api/issues/:id/verification`，记录 `verify_run_id / verify_passed`。
- 通过且在修复中 → 自动进入 `verifying`。
- 封版窗口（release window）决定哪些问题属于本次发布；封版后新增 P0 仍阻塞。

## 配置版本、逐题证据与人工确认

### 配置版本

实现：`review/src/quality/configVersion.ts`

```text
configVersion = sha256({
  promptVersion,
  indexVersion,
  chatModel,
  judgeModel,
  retrievalConfigHash
}) 前 16 位
```

- 评测平台同时知道 `JUDGE_MODEL`，所以最终版本在 review 侧计算。
- 报告、回归确认、发布检查统一使用这个版本；索引/提示词/模型/检索配置任一变化，旧结果自动过期。
- 回归确认按 `(kind, caseId, configVersion)` 存一条最新记录；版本变化后旧确认标记 `stale`。

### 逐题证据

- `GET /api/eval/runs/:id/cases?status=all&limit=50` 打开逐题结果：问题、期望、实际、通过状态、原因。
- 生成用例额外展示保存的回答和答案裁判结果。
- 完整报告仍走 `/reports/:id/report.html`，包含超过预览上限的题目和证据细节。
- 步骤成功但报告缺失/被清理时，页面显示失败或可重试，不会把“没报告”当成通过。

### 人工确认

实现：`review/src/quality/caseConfirmations.ts`

- `POST /api/regression/confirmations` 保存人工复核结果：`kind`（search / generation）、`caseId`、`configVersion`、`machinePassed`、`passed`、`note`、`actor`。
- 发布检查的回归模块只认**当前配置版本下人工确认过**的用例；机器判定只作参考。
- 问题验证记录同时保存 `verifyConfigVersion`、`verifyMachinePassed`、`verifyConfirmedBy`，避免用旧版本的通过结果关闭问题。

### 问题修复字段

- `fixTarget`：`docs` / `prompt` / `retrieval` / `model` / `code` / `other`，用于按修复面聚合。
- `verifyMode`：`rag` / `ask`，决定用检索还是问答链路验证。
- 回答/引用/提示词问题处于修复中或待验证且关联检索用例时，可「改建生成用例」，填写逐行 `referenceFacts` 后由生成裁判读取。

## 发布检查

实现：`review/src/quality/releaseCheck.ts`

聚合：

- 当前索引版本/构建时间/模型/是否 ready；
- 三套门禁最近结果（search/generation/regression）；
- 未关闭 P0/P1（封版范围内）；
- 封版后新增 P0（阻塞，需热修或顺延）；
- 近 24h 点踩率、空结果率、错误率、P50/P95；
- 重启中断、用户取消、旧索引调用计数；
- 服务端自动门禁 `publish.gate`；
- KB 健康卡片。

门禁过期判定：

- 检索门禁：索引版本或黄金集 fixture hash 变化 → 过期；
- 生成/回归门禁：索引版本、黄金集/回归集 hash、提示词版本任一变化 → 过期；
- 过期门禁按未通过处理，必须重跑。

质量阈值：

| 阈值 | 默认 |
| --- | --- |
| `RELEASE_MAX_DOWN_RATE` | 15% |
| `RELEASE_MAX_EMPTY_RATE` | 5% |
| `RELEASE_MAX_P95_MS` | 8000ms |
| `RELEASE_MAX_SHUTDOWN_CALLS` | 未配置时只展示不判定 |

阻塞原因：

- 任一门禁未通过或过期；
- 封版范围内有未关闭 P0/P1；
- 封版后新增 P0；
- 点踩率/空结果率/P95 超阈值。

结论：`release` 或 `blocked`。

## Session / Memory 评测

实现：`review/src/eval/sessionEval.ts`、`review/src/eval/memoryEval.ts`

检索与生成评测看「答得对不对」，Session 评测看「一轮对话是否可靠」。两套都只走 HTTP，不 import `server/src`，不读服务端 SQLite。

### Session 生命周期

| 用例 | 断言 |
| --- | --- |
| S01 正常两轮 | 2 个 turn 都是 `ok`，消息账本 4 条 |
| S02 重复 clientTurnId | 不新增 turn，不重复写消息 |
| S03 并发 | 第二路 409 + `session_busy` |
| S04 停止生成 | 模型调用前 user message 已入账；turn 变 `interrupted`；继续提问仍成功 |

### 记忆契约

长会话按「会话要求 + 摘要 + 最近问答组 + 相关历史」组装，服务端按阶段预算裁剪：

| 阶段 | 输入上限 | 记忆上限 | 输出上限 |
| --- | ---: | ---: | ---: |
| rewrite | 2,048 | 512 | 1,024 |
| summary | 3,072 | 2,300 | 512 |
| answerShape | 2,048 | 0 | 128 |
| answer | 8,192 | 2,300 | 1,536 |
| code | 12,288 | 2,300 | 3,072 |

`memoryEval` 从调用详情的**实际模型请求消息**和 `budgets` / `memorySelection` trace 里取证，而不是复制服务端裁剪代码：

| 指标 | 含义 |
| --- | --- |
| relevantHistoryRecall | 指代/追问时，相关历史确实被召回 |
| irrelevantHistoryRate | 无关旧话题混进相关历史 |
| constraintRetentionRate | 早期格式/版本约束仍在摘要或相关历史中 |
| requirementSelected | 会话要求实际进入回答请求 |
| budgetViolations | 各阶段 `estimatedMemoryTokens > memoryBudget`、`estimatedRequestTokens > requestBudget` 或输出超上限 |
| currentQuestionDuplication | 当前问题重复出现在记忆里 |
| retryLeak | 重试排除的旧回答/旧摘要重新进入请求 |

语义指标先报告，门禁只阻断确定性预算违规；避免模型摘要措辞变化造成假失败。旧命令里的固定 500 / 1200 / 600 只用于复现旧基线。

### 观测台

调用详情新增「会话轨迹」页签：

- 通过 `GET /api/sessions/:id/turns` 由评测平台代理服务端 HTTP（上游 `GET /ops/api/sessions/:id/turns`，不依赖网页账号归属）；
- 展示每轮 status、问题、耗时、`turn_id`；轮次默认折叠，点开才展开步骤与请求详情；
- 展示每步 `prompt_name`、模型、状态、context/usage 快照；
- 展开某一轮后拉取该轮调用详情，按模型请求逐条展示：请求序号、阶段、模型、状态、耗时、token 用量、实际 prompt（system/历史/user）和模型输出；生成步骤未单独落输出时回退到该轮 final answer；
- 与「耗时」页签的模型请求列表、记忆预算数字互相印证。

## 面试讲法

> 「评测不是跑几个例子看感觉，而是三层：第一层是确定性指标，检索看 Class Hit@K、Member Hit@3、false-empty、禁止类命中；生成看 schema、置信度、引用合法性、类/成员提及、路径脱敏、负例、阈值误伤。第二层是独立 LLM 裁判，只看问题、回答、引用和 retrieved，温度 0，12 条人工样本校准。第三层是门禁和基线：绝对阈值 + 与上一版逐项对比，门禁必须全量、不能只跑子集，生成门禁还要求裁判全覆盖。再往后是配置版本和人工确认：提示词、索引、回答模型、裁判模型、检索配置任一变化都会生成新的 configVersion，回归用例必须在当前版本下人工确认；发布检查只认当前版本的确认，避免拿旧结果放行。最后发布检查会把门禁是否过期、未关闭 P0/P1、点踩率、空结果率、P95 一起聚合，给出可发布/阻塞的结论。最近一次生成门禁 23/24 被拦截，正好说明门禁不是摆设。」
