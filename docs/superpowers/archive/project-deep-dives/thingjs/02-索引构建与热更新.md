# THINGJS 文档 RAG · 索引构建与热更新
> 一句话定位：按 ThingJS 的类/章节/成员结构切块，向量 + BM25 + 父块 + 符号证据写进版本目录，文档变更走指纹、子进程构建、原子切换和失败回滚。

## 总流程

```text
docs/**/*.md（260 篇知识文档） + docs/**/*.{js,jsx,ts,tsx}（117 个代码文件）
→ Markdown：DirectoryLoader + TextLoader / Demo：fast-glob + TypeScript AST
→ remark/mdast 解析 Markdown 结构 / ts.createSourceFile 取顶层语句
→ 提取类名、命名空间、H2 章节、H3 成员 / Demo 提取业务意图、主类、符号
→ MD 切块（同 H2 合并短 H3；target 900 / max 1200 / overlap 150）/ 代码切块（target 1200，max 1600）
→ 父块（MD：intro + 每个 H2 一条；Demo：每个文件一条）
→ 图片引用扫描（assets）
→ Embedding（Qwen3-Embedding-4B，2560 维）
→ LanceDB 写入
→ parents.json / bm25.json / fileHashes.json / evidence.sqlite / manifest.json
→ validateIndexDir
→ BUILD_OK
→ active.json 指针
```

对应代码：`server/src/documents/index.ts` 的 `buildDocumentCorpus()`，`server/src/documents/code.ts` 的 `buildCodeChunks()`，`server/src/indexing/build.ts` 的 `buildIndex()`。

## 输入发现

配置：`server/config/doc-sources.json`

默认来源：

```text
root: docs
include:
  **/*.md
  **/*.{js,jsx,ts,tsx}
exclude:
  **/node_modules/**
  **/dist/**
  **/build/**
  **/coverage/**
  **/*.min.js
  **/*.map
```

规则：

- 已登记 root 下新增目录、`.ts/.tsx` 自动发现；
- 新增独立知识库才新增 source；
- `demo-index.md` 是可选路由表，不是代码入库前置条件；
- 没有路由表时，intent fallback：

```text
JSDoc / @description
→ 文件头普通注释
→ 父目录 + 文件名
→ 文件名
```

- 已知文件读取失败、root 不可达时构建中止，不把文件当删除；
- `file_id = source_id + ":" + 规范化相对路径`。

### 类目录只收官网 API 类

切片入库 ≠ 类目录。类检测只看官网 API 文档格式：

```text
sourceKind = official_doc
classNameSource = explicit
  → # 类: Box
  → **命名空间:** THING
```

只有同时满足这两个条件的文档才进入 `ClassEntry`，用于：

- 查询计划的类名建议；
- `exactClasses` / `exactMembers`；
- 精确符号置顶。

不进入类目录：

| 文档 | 原因 |
| --- | --- |
| `docs/README.md` | 普通 H1（`# thingjs-docs`），不是官网类声明 |
| `ThingJS_XXV_SDK开发文档.md` | 没有 `# 类: X`，只能 fallback 文件名 |
| 编辑器/项目说明 | 不是官方 API 类文档 |

它们仍然可以作为普通文档被向量/BM25 检索，但不能成为 Box/Sphere 问题的目标类。`exactMembers` 也会用官方成员目录校验；`ThingJS` 这种泛词不会因为出现在问句里就变成成员。

## 文档加载

实现：`server/src/documents/loader.ts`

- 用 LangChain `DirectoryLoader` + `TextLoader` 遍历 `docs/**/*.md`，递归、忽略未知扩展名。
- 过滤隐藏目录与 `assets/` 目录。
- 路径归一化为 `docs/<相对路径>`，例如 `docs/thingjs_api_v2.0/THING.Box.md`。
- 每个文件算 sha256 前 16 位作为 `fileHash`。
- 排序用 UTF-16 码元，不用 `localeCompare`，避免中文按拼音重排导致基线不一致。
- 文档集指纹 `docsHash` = 排序后的 `filePath + fileHash` 的 sha256，同时覆盖 Markdown 与 demo 代码文件。

## Markdown 解析

实现：`server/src/documents/parser.ts`

只解析文档结构，不做通用 Markdown 渲染：

- H1：`# 类: THING.Box` 或 `# Box` → `className`。
- `**命名空间:** THING` → `namespace`；没有时用目录名提示（如 `thingjs_editor`）。
- H2：章节（`## 构造函数`、`## 实例属性`、`## 实例方法`……）→ `ParsedSection`。
- H3：成员（`### setSize`、`### 静态 clamp`）→ `ParsedMember`。
- 成员类型：
  - 标题含「静态」或正文有 `**类型:** function` → `static`；
  - 正文有 `**类型:** function` 或 `#### 参数` → `method`；
  - 其他 → `member`。
- 行号：用 `LineIndex` 把 remark 的 offset 映射成「只按 `\n` 分行」的 1-based 行号；CRLF 文件不会错位。
- 成员名：`### 静态 clamp` → `clamp`（`memberDisplayName`）。

**为什么不用通用 Markdown 分割器直接切**：ThingJS 文档的语义单位是「类 → 章节 → 成员」，H3 是成员边界；先解析结构再切块，才能把 `class_name / member_name / section / start_line / end_line` 写进索引，检索时才能做类/成员精确召回与评测。

## 切片

实现：`server/src/documents/chunker.ts`、`server/src/documents/splitter.ts`

### 切块单位

| 来源 | member_name | 说明 |
| --- | --- | --- |
| intro | `intro` | 类概述，按目标长度装箱 |
| H2 章节且成员数 ≥ 8 | `<section>__summary` | 生成成员清单摘要，最多 1200 字 |
| H2 章节无 H3 成员 | `<section>__body` | 章节正文 |
| H3 成员 | 合并组 primary member | 同一 H2 下相邻短 H3 合并；`member_names_json` 记录全部成员 |

### 切块参数

```text
CHUNK_TARGET_CHARS = 900
CHUNK_MAX_CHARS    = 1200
CHUNK_MIN_CHARS    = 400（软下限，当前合并逻辑未使用）
CHUNK_OVERLAP      = 150（只在强制拆开同一 unit 时）
CHUNKING_VERSION   = md-h2-merge-h3-900-1200-v4-symbol-spans
```

- 合并块记录 `member_names_json` 与 `symbol_spans_json`；`member_name` 保留 primary 兼容旧消费者。
- 同一 H2 下：短 H3 依次加入当前组；当前组达到 900 后，遇到下一个成员就断开；加入下一个成员会超过 1200 时必须断开；不跨 H2；单个 H3 超过 1200 时单独拆。
- 结构边界之间 0 overlap；同一正文拆分时按预算尝试重叠，实际长度取决于剩余空间和内容边界。
- 旧 H3 口径 `md-h3-max800-ov200-v3-image-refs` 只作为历史基线，不再用于当前构建。

### 代码围栏保护

`ThingJSMarkdownSplitter` 是 LangChain `TextSplitter` 的薄适配：

1. `splitMarkdownAtoms()` 先把正文拆成「文本原子」和「代码围栏原子」，代码块不切断。
2. `packAtomsToChunks()` 按原子装箱，不超过 1200；需要续接时从上一片尾部取 150 字符 overlap。
3. 超大代码块按行切，每片补回围栏和 `###` 标题；单行仍超长时按字符预算硬切。
4. 未闭合围栏自动补上闭合，保证后续切片围栏成对。

**为什么保留自定义实现**：LangChain `RecursiveCharacterTextSplitter` 没有「先保护代码围栏再装箱」的组件；直接按分隔符切会把代码块切断。这个缺口在 `server/plans/reuse-decisions.md` §6.2 和 `server/docs/framework-gaps.md` 有验证记录。

### chunk_id 稳定性

```text
sourceId = doc:<file_path>
raw = sourceId:memberName:p<partIndex>:L<startLine>:<sha256(text) 前 16 位>
chunk_id = doc_<sha256(raw) 前 16 位>
```

- 文档内容、成员、分片序号、起始行任一变化都会产生新 id；未变化部分 id 稳定。
- 增量构建和旧基线逐题对比都依赖这个稳定性。

### search_text 增强

每个 chunk 的 `search_text` = 完整类名 + 类名 + 命名空间 + 成员名 + 章节 + 层级 + 正文。图片的 `alt` 或 `url` 也会追加到 `search_text`，让「gridnight.png」这类图片提示可被检索到。

### H3 与 H2 的均衡

H3 是语义/符号边界，但不再强制作为检索块边界：

- **同一 H2 下短 H3 合并**：目标 900、最大 1200，不跨 H2；
- **长 H3 单独拆**：超过 1200 时沿段落、列表、代码围栏拆；
- **成员定位保留在 span**：`member_names_json` 记录块内全部成员，`symbol_spans_json` 记录起止偏移与行号；
- **精确召回走 evidence 表**：`symbol_mentions` 找到块，`symbol_spans` 定位成员，不要求成员单独成块；
- **大章节用摘要块**：成员数 ≥ 8 的 H2 额外生成 `<section>__summary`，解决“章节很大但成员名找不到入口”的问题。

### 示例：THING.Sphere

以 `docs/thingjs_api_v2.0/THING.Sphere.md` 为例：

```text
THING.Sphere.md
→ intro：类概述和构造参数表 → 概述块 384 字符
→ H2 实例属性
   → 相邻 H3：radius、helper、lerp、level、collider、name
   → 合并块 924 字符，原文第 20–107 行
      → radius span：第 20–31 行
```

`radius` 成员只有 89 字符。装箱时，它和后面的 5 个属性一起进入 924 字符的检索块；此时达到 900 的目标，下一成员进入下一组。构造参数表位于前面的 `intro`，保留为独立块。

```text
member_name       = radius（primary）
member_names_json = ["radius", "helper", "lerp", "level", "collider", "name"]
symbol_spans_json = [
  { memberName: "radius", start: 0,  end: 89,  startLine: 20, endLine: 31 },
  { memberName: "helper", start: 91, end: 252, startLine: 32, endLine: 45 },
  ...
]
```

两个问法对应不同的证据。「`Sphere.radius` 是什么？」用 `symbol_mentions` 找到合并块，再用 `symbol_spans` 定位第 20–31 行；「Sphere 怎么创建？」需要上方独立的概述块，那里有构造参数表。

## 代码切片

实现：`server/src/documents/code.ts`

### 适用范围与发现

代码源按 `server/config/doc-sources.json` 统一发现，不再只扫描 `thingjs2.0demo`：

- 已登记 `docs` 根目录下所有 `.js/.jsx/.ts/.tsx` 自动发现；
- 排除 `node_modules/dist/build/coverage/*.min.js/*.map`；
- 新目录不需要 `demo-index.md`；没有路由时 intent fallback 到 JSDoc → 文件头注释 → 文件名；
- 当前 117 个代码文件（demo 101 + project_examples 16）。

### AST 切块规则

```text
ts.createSourceFile
→ import 抽为 header
→ 顶层声明作为 unit
→ 小 unit 合并
→ 长 unit 拆分
```

1. `ts.createSourceFile` 解析 AST，顶层语句（函数/类/变量/表达式）作为 unit；`import` 抽出来作为 header。
2. 小 unit 合并到目标 1200 字符；单 unit 超过 1600 字符或解析失败时，才用 LangChain `RecursiveCharacterTextSplitter.fromLanguage('js')` 兜底。
3. 每个 chunk 带 header：业务意图、文件路径、`THING.X`/`app.*` 符号；`search_text` 同时包含业务意图与代码正文。
4. 元数据：`source_type='module'`、`chunk_type='code'`、`language`、`class_name=<该 chunk 的主操作类>`、`symbol_name='demo:<文件名>'` 或 `code:<文件名>`、`parent_id` 对应文件。同一文件含多个业务类时按类断开，`对象事件.js` 会拆成 `Sphere` 与 `Box` 两个代码块；App/Math/LoopType 等工具类不抢主类。
5. 每个代码文件一条父块，`title` 是业务意图或 fallback intent，`className=''`，避免污染 API 类目录。
6. `demo-index.md` 是可选路由表，**不**按 Markdown 文档重复入库；它的内容会参与 `docsHash`，业务意图变化仍能触发索引更新。
7. `.tsx` 使用 `ScriptKind.TSX`，`.jsx` 使用 `ScriptKind.JSX`；`const sphere = new THING.Sphere()` 建立变量映射，`sphere.on(...)` 归属 Sphere；跳过 `App / Math / MathUtils / LoopType / Space3D / Color / Vector3 / Quaternion`；只有同一 unit 被拆开时才 overlap。

**为什么用 TypeScript compiler API**：项目已依赖 `typescript@5.7`，`ts.createSourceFile` 能零新增依赖拿到顶层语句边界；`tree-sitter` 需要额外 grammar/WASM。LangChain 没有「按顶层语句分组并保留业务意图」的代码切块组件，分组与元数据属于 ThingJS 示例契约，记录在 `server/plans/reuse-decisions.md`「demo 代码入索引」。

### 示例：对象事件.js

`docs/thingjs2.0demo/事件/对象事件.js` 的原文同时操作球体和盒子：

```text
对象事件.js
→ 按 AST 顶层语句取代码单元
→ 识别 sphere 创建及后续 click 处理
→ 识别 box 创建及后续更新和鼠标处理
→ Sphere 块 443 字符，第 6–18 行
→ Box 块 626 字符，第 20–41 行
```

`const sphere = new THING.Sphere(...)` 建立 `sphere` 到 `Sphere` 的映射，后面的 `sphere.on("click", ...)` 就能跟创建语句留在同一块；遇到 `box` 的业务代码时换组。这样代码块短于 1200 字符也可以保留，因为该业务对象的相关语句已经成组。

## 父块

实现：`server/src/documents/parents.ts`

- 每个文档固定一条 `intro` 父块：`类`、`命名空间`、`introText`。
- 每个 H2 章节一条父块：`类`、`章节`、章节正文。
- `parent_id = doc:<file_path>#<section>`。
- 代码：每个文件一条父块。
- 存入 `parents.json`，服务端加载到 LangChain `InMemoryStore<ParentContext>`。

**注意**：检索时不会把整章父块塞进 context；命中短片段时会在同一 `##` 章节内扩一个不超过 1200 字的窗口（代码上限 1600），既补足上下文，又避免整章稀释。父块标题拼成 `【类名 · 章节 · 成员】`，窗口尽量从 H3 边界开始，不跨 H2。

## Embedding

实现：`server/src/models/embeddings.ts`、`server/src/models/gateway.ts`

- 模型：`Qwen3-Embedding-4B`，2560 维。
- 文档侧：直接用 `search_text` 或 `text`。
- 查询侧：加指令前缀：

  ```text
  Instruct: Given a web search query, retrieve relevant passages that answer the query
  Query:<query>
  ```

  文档侧不加前缀；前缀实现为 `InstructedEmbeddings.embedQuery()`。
- 批量大小 10；超时 180s（网关冷启动/长代码块实测可超过 60s）；最多重试 1 次。
- Embedding 的 Key / Base URL 留空时复用 `OPENAI_API_KEY` / `OPENAI_BASE_URL`，同一网关不需要重复配置。
- 网关协议适配：LangChain/OpenAI SDK 发 `input`，本机网关要 `texts`；响应 `{embeddings:[[...]]}` 转成 OpenAI 的 `{data:[{embedding}]}`，数字数组编码为 float32 little-endian base64。
- 本地 Qwen3-Embedding-4B 不支持 Matryoshka，默认不发送 `dimensions`；需要时用 `EMBEDDING_REQUEST_DIMENSIONS=true` 打开。

## 存储

### LanceDB

实现：`server/src/indexing/vectorStore.ts`

- 表名 `chunks`，列包括 `chunk_id`、`source_id`、`parent_id`、`source_type`、`chunk_type`、`language`、`class_name`、`member_name`、`namespace`、`symbol_name`、`file_path`、`start_line`、`end_line`、`text`、`search_text`、`images_json`、`vector`。
- 继承 LangChain 官方 `LanceDB` 集成，复用写入、schema 推断、元数据映射。
- 官方 `similaritySearch` 会忽略 filter，所以补了 `searchVectorWithFilter()` 和 `findByFilter()`，过滤条件下推成 LanceDB `where`。
- **不建 ANN 索引**：`table.query().nearestTo(query).bypassVectorIndex()` 全表扫描。原因：
  - 旧基线索引的 IVF-PQ 训练带随机性，重建后近似排序不可复现；
  - 2 万行级数据全表扫描约 90ms（项目文档实测），比 ANN 更确定、查询也更快。
- 距离转分数：`score = 1 / (1 + distance)`。

### BM25

实现：`server/src/indexing/bm25Store.ts`

- 用 MiniSearch 建倒排索引，jieba HMM 分词，标点/空白由 `processTerm` 丢弃。
- 索引字段是 `search_text`，存储字段包括 `chunk_id / text / source_type / namespace / class_name / member_name / parent_id / file_path`。
- 持久化为 `bm25.json`，记录 `format: minisearch`、`formatVersion`、`tokenizer: jieba-hmm+identifier-v1`、`count`、序列化索引。
- 加载时校验 tokenizer，不匹配直接报错。
- **不手写 BM25 打分**：分词、倒排、BM25 评分都由 MiniSearch 提供；项目只做多查询合并编排。
- 实测：9,366 条构建约 5s、持久化 22MB、加载 0.4s、查询 7–16ms（项目文档实测）。

### 证据表

索引版本目录包含：

```text
evidence.sqlite
  symbols
  symbol_mentions
  normalized_signatures
```

作用：

- 合并块里的每个成员都有 mention；
- 精确符号查询通过 `symbol_mentions` 找回 chunk；
- `symbol_spans` 定位具体成员；
- 参数表尝试写入 `normalized_signatures`；
- 运行时一次性读入内存并关闭 SQLite 文件，避免 Windows 锁。

当前规模：20,360 symbols / 20,638 mentions / 14,295 signatures；旧索引可缺失。

## 版本、激活与增量

### 版本目录

```text
data/indexes-new/
└─ Qwen3-Embedding-4B/
   ├─ active.json
   ├─ publish.lock
   ├─ 20261117.12.13.14/   （旧版）
   └─ 20261118.16.00.00/   （当前激活）
      ├─ lancedb/
      ├─ bm25.json
      ├─ parents.json
      ├─ fileHashes.json
      ├─ evidence.sqlite
      ├─ manifest.json
      └─ BUILD_OK
```

- 版本名默认本地时间 `YYYYMMDD.HH.mm.ss`；重名自动加 `-2`、`-3`。
- `active.json` 按 embedding 模型分 profile：

  ```json
  {
    "version": 1,
    "profiles": {
      "Qwen3-Embedding-4B": {
        "embeddingModel": "Qwen3-Embedding-4B",
        "embeddingDimensions": 2560,
        "version": "20261118.16.00.00",
        "path": "...",
        "activatedAt": "..."
      }
    }
  }
  ```

- `activate:index` 先校验目录，再原子写 `active.json`（临时文件 + rename）。
- `prune:indexes` 默认保留最近 5 个 `BUILD_OK` 版本，`--keep <n>` 可调；默认 60 分钟保护窗口，窗口内的版本即使超出保留数也不删；未完成构建的目录永远不自动删。

### 增量构建

实现：`server/src/indexing/build.ts`

```text
当前文件 hash
→ 找最近的兼容版本（同模型、同维度、同切块指纹、有 BUILD_OK）
→ 文件 hash 未变的文件，其 chunk 向量按 chunk_id 复用
→ 只对新增/变更文件重新 embedding
→ 写新版本目录
```

- 兼容条件：`embeddingDimensions` 一致 + `chunkingFingerprint` 一致。
- 当前切块指纹 = `md-h2-merge-h3-900-1200-v4-symbol-spans` + 代码切块参数（target/max/overlap/import 上限）；任一变化必须全量重建。
- 支持 `vectorSourceDir`：按 `chunk_id` 从外部只读索引复用向量（例如旧基线索引）。
- 历史 manifest 记录（2026-11-17 加入 demo 代码）：切块指纹变化触发全量构建，但用 `--vector-source` 复用旧索引 20,922 条 Markdown 向量；新嵌入 498 条（新增 Markdown 152 条 + demo 代码 346 条）；共 21,420 chunks / 879 parents。这是过渡版本，不是当前激活口径。

### 合成向量加速

合并切块改变了 chunk_id，直接全量 embedding 约 9k 个长文本，实测约 2 秒/条，需要 5–6 小时。

```bash
pnpm --dir server exec tsx scripts/build-index.ts \
  --synthesize-from data/indexes-new/Qwen3-Embedding-4B/<旧版本>
```

做法：

- 读取旧索引的 H3 成员向量；
- 新合并块按 `member_names_json` 找到对应成员向量；
- 做归一化平均，得到合并块向量；
- 找不到成员的块才实际 embedding；
- 结果写入 manifest 的 `syntheticVectorSource`。

2026-11-18 实测：

```text
新切块 9,366
合成向量 9,290
实际 embedding 76
构建耗时 4.4 分钟
```

这比直接 embedding 的预计 5–6 小时快两个数量级。代价是合并块的向量是成员向量近似，检索门禁需要重新验证；本次检索门禁已通过。生成门禁曾出现未通过（confidence 96.7%、judgePass 87%、幻觉 2），说明成员向量平均对生成质量有损；当前保留该版本仅供手动测试，正式发布应改用真实合并块 embedding，或继续调整合成策略后重新跑生成门禁。最新一次生成报告的逐题口径见 [07-评测平台与质量门禁](/03-项目实战/01-THINGJS文档RAG/07-评测平台与质量门禁)。

## 热更新

实现：`server/src/indexing/docsWatch.ts`

### 触发条件

- `DOCS_WATCH=true`。
- 监听 `docs/` 下 `.md`、`.markdown`，`thingjs2.0demo/` 下 `.js`、`.ts`，以及 `assets/` 下图片（png/jpg/jpeg/gif/svg/webp）。
- 同时监听 `data/aliases.yaml`。
- 忽略隐藏目录、`node_modules`、编辑器临时文件（`~`、`.swp`、`.tmp`）。

### 去抖与指纹

```text
文件事件
→ debounce 5000ms（默认）
→ computeDocsFingerprint：
   docs = 每个 md / demo js-ts / asset 的 relPath + mtimeNs + size 排序后的 sha256
   aliases = aliases.yaml 内容 sha256（不存在为 "missing"）
→ 与上次指纹相同则跳过
→ 只变 aliases：只重读别名并重建 retriever，不重建索引
→ 变 docs：进入发布流程
```

- 构建中再来事件只标记「尾部待跑」，由 `finally` 合并成下一轮。
- 一轮结束后进入 cooldown（默认 2500ms），避免连续保存导致抖动。
- 指纹只 stat 文件和读 aliases，不读文档全文。

### 发布流程

```text
加发布锁（proper-lockfile，重试 12 次 × 5s）
→ spawn 子进程 scripts/publish-index.ts --no-lock
   （构建 + 校验 + activateIndex）
→ 父进程 reloadIndex()
→ 如果配置了 DOCS_WATCH_GATE_CMD：
   执行外部门禁（环境变量带 THINGJS_INDEX_VERSION / THINGJS_INDEX_DIR / THINGJS_PROMPT_VERSION）
   非零退出或超过 DOCS_WATCH_GATE_TIMEOUT_MS（默认 300s）视为失败
→ 门禁通过：promoteKbHealthLatest()，状态 ready
→ 门禁失败：回滚 active.json 到发布前指针，reloadIndex 旧版，状态 failed，
   指纹不更新，下一轮变更会重试
```

- 构建放在子进程，避免 BM25/LanceDB 的主线程计算阻塞 HTTP。
- 门禁命令的 stdout/stderr 只进日志；状态里只留退出码/超时摘要，防止敏感信息进报告。
- `publish.gate` 状态透传到 `/api/health` 和 `/ops/api/summary`。
- 门禁失败回滚只在「当前指针仍指向失败版本」时执行，避免覆盖同时发生的更新发布。

### 多实例

- 只让一个实例开 `DOCS_WATCH` 负责构建。
- 其余实例设 `INDEX_POLL_MS > 0`，按 `active.json` mtime 轮询，发现变化后热加载。
- 切模型/维度需要重建索引并重启；热加载会拒绝模型/维度不一致的索引。

### 提示词为什么不热更新

- `server/prompts/*.yaml` 在进程内缓存，`promptVersion` 是文件内容的 sha256 前 12 位。
- 修改 YAML 后需要重启服务才生效。
- 重启后再跑生成/回归门禁；发布检查会按索引与提示词新鲜度判断旧门禁是否过期。
- 这是有意的取舍：提示词变更属于代码变更，应该走重启和门禁，而不是线上静默换行为。

## 知识库健康度（KB Health）

实现：`server/src/indexing/health.ts`

检查覆盖六类，共 40+ 个 finding code：

| 前缀 | 类别 | 例子 |
| --- | --- | --- |
| `KB-V` | 索引结构 | manifest、chunk 数、维度、文件完整性 |
| `KB-C` | 覆盖度 | 类/成员覆盖率、解析成员是否入索引 |
| `KB-M` | 元数据 | class_name、member_name、namespace、file_path、行号 |
| `KB-Q` | 切块质量 | 空块、过短块、超长块、重复块、父块缺失 |
| `KB-S` | 一致性 | chunk/parent/bm25 数量、docsHash、索引版本 |
| `KB-F` | 新鲜度 | 索引年龄、docs 指纹一致、提示词版本 |
| `KB-Z` | 其他 | 汇总 |

- 报告写入 `data/reports/kb-health/`，完整报告与 `--fast` 各保留 20 版。
- 发布构建会写版本报告；门禁通过后才推进 `latest.json`。
- `chunk_type='code'` 参与切块质量、重复块与父块检查，但不计入 API 类/成员覆盖率，避免 demo 主类污染目录统计。
- `pnpm kb:health -- --strict` 有 error 级 finding 时退出 1。
- 当前口径：0 error / 3 warn（具体处置见 `server/plans/kb-health.md` §10）。

## 当前实测与口径

新切块 dry-run：

```text
9,366 chunks / 878 parents
Markdown 8,891 / code 475
合并块 5,883
p50 = 968
p90 = 1,151
p95 = 1,185
max = 1,598
```

旧 H3 口径对比：

```text
p50 ≈ 350
p90 ≈ 633
p95 ≈ 696
```

为什么不是纯 H3 或纯 H2：

| 方案 | 问题 |
| --- | --- |
| 纯 H3 | `radius` 约 90 字，碎片化，缺少参数/示例上下文 |
| 纯 H2 | 章节过大，无关成员和示例混在一起，token 浪费 |
| H3 边界 + 同 H2 合并 + span | 块可理解，成员仍可精确回指 |

一句话：

> **H3 负责符号身份，H2 内合并负责可理解上下文，span 负责精确定位。**

## 失败模式与处理

| 失败 | 表现 | 处理 |
| --- | --- | --- |
| 没有激活索引 | `indexReady=false` | 检索/问答 503 `index_not_ready` |
| 模型/维度与索引不一致 | 启动时警告 | 服务照常启动，检索/问答 503 `index_embedding_mismatch` |
| 索引加载失败 | 热加载抛错 | 旧 runtime 继续服务，`active.json` 回滚 |
| 构建失败 | 子进程非零退出 | 状态 failed，不切换 active |
| 门禁失败 | 发布后检查不通过 | 回滚 active + 热加载旧版，指纹不更新 |
| 别名文件损坏 | YAML 解析失败 | 发布失败，旧版继续服务 |
| 单路召回失败 | 向量或 BM25 报错 | 另一路继续，confidence 降为 `low`，`degradedReasons` 记录 |
| 两路都失败 | 检索抛错 | 请求失败，记录 error |

## 面试讲法

> 「索引层我做了三件事：第一，按 ThingJS 的类/章节/成员结构切块，而不是按字符硬切，代码围栏有保护；第二，117 个代码文件也进索引，用 TypeScript AST 按顶层语句切，有 demo-index 时带业务意图，没有时用 JSDoc/文件名 fallback，这样用户问“怎么设置样式”能直接命中对应示例；第三，向量和 BM25 都落到版本目录里，带 manifest、文件哈希和 BUILD_OK，支持按文件哈希增量复用；文档变更走 chokidar 去抖 + 指纹比对 + 子进程构建 + active.json 原子切换，发布后可以跑外部门禁，失败自动回滚。这样文档更新不需要停服务，也不会把坏索引留在线上。」
