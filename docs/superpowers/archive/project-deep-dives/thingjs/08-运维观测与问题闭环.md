# THINGJS 文档 RAG · 运维观测与问题闭环
> 一句话定位：线上每次回答都有 trace、阶段耗时、证据和 prompt 版本；出问题能定位、能重放、能闭环、能恢复。

## 目标

回答三个问题：

1. **线上现在怎么样？** 调用量、错误、空结果、点踩率、P95、索引版本、队列、会话。
2. **这次回答为什么这样？** trace、阶段耗时、prompt、召回/丢弃、usage、guard 状态。
3. **出了问题怎么闭环？** 点踩/评测失败/异常扫描 → 问题 → 回归用例 → 单题验证 → 关闭 → 发布检查。

## 状态库

SQLite（better-sqlite3，WAL），默认 `data/rag.sqlite`，可用 `RAG_DB_PATH` 覆盖。

### 表

| 表 | 作用 |
| --- | --- |
| `turns` | 每次检索/问答/重放/拒绝的审计记录 |
| `feedback` | 点踩/评论 |
| `mcp_sessions` | MCP 会话生命周期 |
| `request_rejections` | 限流/校验等入口拒绝 |
| `issues` | 问题队列 |
| `issue_events` | 问题状态/分类/指派/验证事件流 |
| `chat_sessions` | 用户会话（软删除）；含 `requirements_json` / `summary_format_version` |
| `chat_messages` | 会话消息（按 clientId 幂等；含 `question` / `code` / `error_text` / `source_user_client_id`） |
| `chat_turns` / `chat_steps` | 一轮状态与阶段调用账本（summary / rewrite / answer-shape / answer / code） |
| `issue_verifications` | 人工验证记录：runId、configVersion、machinePassed、confirmedBy |

### turns 关键列

```text
id, trace_id, route, question, answer,
confidence, empty_reason, chunk_ids, dropped_ids,
usage, latency_ms, error_code,
user_id, dept, team, client_ip, session_id,
quota_used, source, phases, detail,
index_version, embedding_model, prompt_version,
created_at
```

- `route`：`http.search / http.chat / mcp.search / mcp.ask / replay` 等。
- `source`：`web / mcp / replay / eval / ...`，评测调用单独隔离。
- `detail`：完整请求/响应/阶段/提示词/usage/LangChain trace，JSON。
- `index_version` / `prompt_version`：请求开始时捕获，热切换后仍能追溯。
- `dropped_ids`：当前主要记录否定类丢弃。

### 保留策略

- `turns`、`feedback`、`mcp_sessions`、`request_rejections`：默认 30 天（`AUDIT_RETENTION_DAYS`）。
- `chat_sessions` / `chat_messages`：默认 30 天（`CHAT_HISTORY_RETENTION_DAYS`）；软删除会话多留一个保留期。
- 单用户最多 200 个会话（`CHAT_SESSION_MAX_PER_USER`）。
- 长驻进程每天清一次；启动时也清一次。
- 手动清理：`POST /ops/api/prune`（只允许本机）。

## Trace

### traceId

实现：`server/src/ops/trace.ts`

- 中间件 `attachTraceId`：优先 `x-trace-id`，否则 `newTraceId()`。
- `newTraceId()` = 时间戳 base36 + uuid 前 8 位。
- `AsyncLocalStorage<TraceContext>` 传播 traceId/route/clientIp。
- 响应头 `X-Trace-Id`。

### Live trace

- `runSpan()` 记录一次检索/问答：
  - traceId、route、question、startedAt/endedAt、totalMs、status；
  - `phases[]`（phase/ms/startMs）；
  - `modelCalls[]`（rewrite / answerShape / generation 的模型、耗时、usage、fallback/error）；
  - identity（userId/dept/team/clientIp/sessionId）。
- 内存保留最近 500 条，`traceBus` 支持订阅。
- 结束时观察请求耗时指标 + 写 pino 日志。

### LangChain 回调

实现：`server/src/generation/callbacks.ts`

`GenerationTraceHandler` 实现 LangChain `BaseCallbackHandler`：

- 收集 chain / llm / retriever 事件：
  - runId、parentRunId、name、startedAt/endedAt、durationMs、status；
  - messageCount（不记录完整 prompt）；
  - usage；
  - error。
- 通过 `onEvent` 把 trace 附到同一个 traceId 的 live trace 上。
- 不记录完整提示词/密钥；prompt 正文只在调用详情里按需落库。

### Session 生命周期

- `chat_turns`：一轮用户输入，状态 `running/ok/error/interrupted/cancelled`；
- `chat_steps`：一轮里的模型调用（summary / rewrite / answer-shape / answer / scene-code / code-debug）；
- 用户消息在模型调用前先入账；成功、停止、失败分别更新 turn；
- 同一 session 同时只允许一个 running turn，重复 `clientTurnId` 幂等；
- 服务启动时把遗留 running 标记 interrupted；
- `GET /api/chat/sessions/:id/turns` 可查轮次状态（网页账号归属）；
- `GET /ops/api/sessions/:id/turns` 供评测台只读展开会话轨迹，不依赖网页账号归属；调用详情同时写 `identity.sessionId`。

### 调用详情

`buildCallDetail()` 组装：

```ts
{
  request: { question, history, ... },
  response / error,
  phases,
  modelCalls: [{ phase, promptName, model, durationMs, usage, fallback?, error? }],
  generation: LangChain events,
  usage,
  identity: { userId, dept, team },
  index: { version, builtAt, embeddingModel },
  model,
  client: { source, userAgent? },
  replayOf?
}
```

观测台详情能看到：

- 阶段瀑布（用 `startMs` 和 `ms`）；
- 模型请求列表：会话摘要、问题改写、题型分类、生成各算一次，显示 prompt 名称、模型、耗时、tokens、fallback；展开可看本次实际 system/history/user 提示词。
- 实际 prompt（system/user）；
- retrieved/citations/discarded；
- answerGuard；
- usage；
- 原调用与重放对比。

## [重点] 重放

实现：`server/src/ops/replay.ts`

- 只支持 `http.chat` / `http.search`。
- 读取原调用 detail 的问题与历史；没有 detail 返回 409 `no_detail`，不猜。
- 新 traceId、新检索、新生成，不复制旧回答/旧阶段耗时。
- `source=replay`，`detail.replayOf` 指向原 trace。
- 并发限制：同一 trace 同时 1 个，全局最多 2 个；超出 429 `replay_busy`。
- 重放使用当前索引与当前提示词；详情同时展示原记录与重放结果的版本/指纹。
- 详情并排对比回答、置信度、延迟、证据和阶段耗时，标注新增/消失的 chunk。

### 与旧项目对比

旧项目 `thingjs-docs-agent-js` 的「回放」主要停留在两个层面：

- `/ops/api/turns/:traceId` 是**只读审计**：按 traceId 取回当次 turn，用于查证据、耗时和错误；
- `review/tests/generationReplay.test.ts` 是**评测侧固定回放**：把历史答案和 retrieved 摘录写进测试，离线跑评分，用来防止 G19/G21 这类问题回归。

它没有 `POST .../replay` 这样的运行时重放入口，也不会用当前链路重新执行一次原问题。旧项目规格 S029 还明确写了「不要求旧 turn 重放或推断过去的 Embedding/Chat 状态」。

当前项目补的是运行时重放：

| 维度 | 旧项目 | 当前项目 |
| --- | --- | --- |
| 入口 | `/ops/api/turns/:traceId` 只读审计 | `POST /ops/api/calls/:traceId/replay` + 观测台按钮 |
| 执行方式 | 评测侧固定答案/证据，离线评分 | 按原问题、历史、代码/报错重跑当前检索与生成 |
| 结果归属 | 固定夹具 | 新 trace，`source=replay`，`detail.replayOf` 指原记录 |
| 对比能力 | 看历史记录 | 并排对比回答、置信度、延迟、证据、阶段耗时、新增/消失 chunk |
| 配置漂移 | 不能回答「用现在这版会不会好」 | 使用当前索引/提示词/模型，同时展示双方版本与指纹 |
| 并发与失败 | 无运行时并发控制 | 同一 trace 1 个、全局 2 个；无 detail 409，忙 429 |

一句话区分：

> 旧项目的固定回放适合**防回归**，当前项目的运行时重放适合回答**「现在修好了没有」**。前者证明历史问题不会复发，后者验证当前链路在同一个问题上的真实表现。

注意不要说成「复现历史运行状态」：当前重放用的是现在的索引、提示词和模型，不是把旧进程冻结后重跑。它的价值是拿同一条输入做 A/B，而不是伪造历史环境。

## [重点] 问题队列

实现：`server/src/ops/issues.ts`

### 来源

`feedback`、`eval`、`latency`、`empty`、`error`、`manual`。

### 分类

`retrieval_miss`、`ranking`、`citation`、`answer_wrong`、`prompt`、`latency`、`empty`、`error`、`other`。

### 严重级

`P0`、`P1`、`P2`、`P3`。默认：

- feedback / eval / error → P1；
- 其他 → P2。

### 状态机

```text
new → triaged / fixing / wontfix
triaged → new / fixing / wontfix
fixing → triaged / verifying / wontfix
verifying → fixing / closed / wontfix
closed → new
wontfix → new
```

约束：

- `wontfix` 必须填写备注；
- 进入 `verifying` 前必须有关联回归用例；
- `closed` 前必须有关联回归用例 + 最近一次验证通过；
- 退回 `new/triaged/fixing` 会清空旧验证，防止用过期结果关闭。

### 去重

- `fingerprint = sha256(normalize(question) + '\n' + category)`。
- `normalize`：小写、去空白/标点、截断 500。
- 同一指纹再次出现只累加 `occurrence_count`、更新 `last_seen_at`，并写 `recurred` 事件；同一 trace 不重复累加。
- 严重级只会从 P1 升级到 P0，不会自动降级。

### 修复面与验证方式

- `fixTarget`：`docs` / `prompt` / `retrieval` / `model` / `code` / `other`，用于按修复面聚合和筛选。
- `verifyMode`：`rag` / `ask`，决定用检索还是问答链路验证。
- 回答/引用/提示词问题处于 `fixing` 或 `verifying` 且关联检索用例时，可改建生成用例；生成用例支持逐行 `referenceFacts`，由现有生成裁判读取。
- 历史回归编号跨检索/生成两类夹具重复时，优先按夹具 `issueId` 匹配，再按唯一同题文本匹配；仍有歧义则要求明确关联，不任选一类。

### 事件流

`issue_events` 记录：

- `created`、`recurred`、`status_changed`、`assigned`、`category_changed`、`severity_changed`、`note`、`verification`。

详情页展示完整时间线。

## 三条建单路径

### 点踩 → 问题

```text
POST /api/feedback { traceId, rating:'down', comment }
→ 校验 traceId 是否存在
→ 同一 traceId + rating 幂等；重复只更新评论
→ 写 feedback
→ createIssueForFeedback：
   - 从 turns 取 question/confidence/empty_reason/error_code
   - 推断 category
   - source=feedback，severity=P1
   - 同指纹累加/建单
→ 建单失败不影响反馈本身
```

历史点踩（自动建单上线前）可以：

- 问题队列空态点「回填历史点踩」；
- 或 `POST /ops/api/issues/backfill-feedback`；
- 已有关联 trace 的问题跳过。

### 评测失败 → 问题

- 评测历史详情勾选失败用例 → 批量建单；
- 或「全部转为问题」；
- 回填 `eval_run_id` / `eval_case_id`；
- 运行详情可按 `evalRunId` 反查产生的问题。

### 异常扫描 → 问题

实现：`server/src/ops/anomalies.ts`

```bash
pnpm scan:issues              # 默认只预览
pnpm scan:issues -- --apply   # 建单
```

候选：

- `slow`：慢调用；
- `empty`：空结果；
- `error`：错误。

慢调用阈值：

```text
max(OPS_SLOW_MS, 同路由同来源 24h P95 × 2)
```

- 默认 `OPS_SLOW_MS=30000`。
- 排除评测调用（`source=eval`）。
- 重复扫描按问题指纹去重。

## [重点] 修复 → 验证 → 关闭

1. 问题详情生成独立回归用例：
   - 写入 `review/fixtures/regression-*.json`；
   - 只增不删，可 `disabled`；
   - 原调用证据自动预填 `expectClass / expectMember`；
   - 回答类问题可改建生成用例，填写逐行 `referenceFacts`；
   - 保存后问题转 `fixing`。
2. 单题回归：
   - 评测平台 `/verify` 或问题详情触发；
   - 可通过 `GET /api/eval/runs/:id/cases?status=all&limit=50` 打开逐题结果，展示问题、期望、实际、通过状态和原因；生成题还展示回答与裁判结果；
   - 机器结论只作参考；人工确认走 `POST /api/regression/confirmations`，按 `(kind, caseId, configVersion)` 保存；
   - 结果写 `/ops/api/issues/:id/verification`，记录 `verify_run_id / verify_passed / verify_config_version / verify_machine_passed / verify_confirmed_by`；
   - 通过且问题在 `fixing` → 自动 `verifying`。
3. 关闭：
   - 必须有关联回归用例；
   - 最近一次人工确认必须通过，且确认的 `configVersion` 与当前一致；版本变化后旧确认 stale；
   - 否则 400。

**黄金集何时重测**：

- 单题修复用回归用例即可；
- 合并/发布前跑三套门禁；
- 改文档或检索逻辑 → 黄金检索门禁必跑；
- 改提示词/生成 → 黄金生成门禁必跑；
- 门禁跑在旧索引/旧提示词/旧夹具上会被发布检查判为过期。

## 发布检查

完整聚合逻辑见 [07-评测平台与质量门禁](/03-项目实战/01-THINGJS文档RAG/07-评测平台与质量门禁) 的「发布检查」。运维侧只强调：

- `/release` 聚合三套门禁、未关闭 P0/P1、封版后 P0、点踩率/空结果率/P95、自动门禁、KB 健康；
- `blocked` 时列出全部原因，不截断；
- 发布后可观察新增问题、旧索引调用、重启中断。

## 备份与恢复

实现：`server/src/ops/backup.ts`

```bash
pnpm backup:state -- --out data/backups/<timestamp>
pnpm verify:backup -- --from data/backups/<timestamp>
pnpm restore:state -- --from data/backups/<timestamp> [--force]
```

备份内容：

- `rag.sqlite`：用 `VACUUM INTO` 生成一致性快照；
- `aliases.yaml`；
- `indexes-new/active.json`；
- `manifest.json`：文件大小 + SHA-256 + 说明。

不备份：

- 索引目录（靠版本目录重建/重新激活）；
- `server/.env`（不落备份）。

校验：

- manifest 存在且可解析；
- 文件 SHA-256 匹配；
- SQLite `integrity_check`；
- 缺文件/大小不符/哈希不符报错。

恢复：

- 默认拒绝覆盖，需 `--force`；
- 覆盖前生成带时间戳的 `.bak-*`；
- 同时处理 SQLite `-wal/-shm` 侧车文件，避免回放错页；
- 恢复后需重建/激活索引。

## 优雅关闭

实现：`server/src/app/server.ts`

```text
SIGINT / SIGTERM
→ shuttingDown=true，incCounter('serverShutdown')
→ shutdownController.abort()：在途检索/问答/MCP 调用中止
→ closeAllSse()：结束长连接，避免 server.close 等心跳
→ docsWatch.close() / indexPoller.close()
→ 关闭 MCP 会话
→ closeHttpServer(server, 5000)：先停新连接，再断空闲，超时强制断
→ inflight.waitForIdle(SHUTDOWN_DRAIN_MS=3000)：给最后一条 turn 落库
→ closeOpenSessions('process')
→ checkpoint + db.close()
→ process.exit(0)
```

- 15s 强制退出兜底。
- 中止的请求记录 `server_shutdown`（503），不是 `client_aborted`。
- 关闭期间 `/api/ready` 返回 503 + `shuttingDown`，`/metrics` 有 `thingjs_shutting_down=1`。

## 日志

- pino，默认 stdout；`LOG_FILE` 设置后 pino-roll 按大小轮转（默认 10m，保留 5 份），同时保留 stdout。
- 脱敏路径：Authorization、token、apiKey、OPENAI_API_KEY、EMBEDDING_API_KEY、AUTH_JWT_SECRET、LDAP_BIND_PASSWORD。
- prompt 正文不写日志；进 SQLite detail。
- 门禁命令 stdout/stderr 只进日志，状态里只留退出码/超时摘要。


## 面试讲法

> 「可观测性我做了三层：第一层是 trace，traceId 用 AsyncLocalStorage 传播，检索和生成的阶段耗时、LangChain 回调、prompt、usage 都落到 turns.detail；第二层是指标，Prometheus 暴露事件计数、请求耗时、队列、索引版本、重载耗时；第三层是问题闭环，点踩/评测失败/异常扫描都能进问题队列，问题状态有严格流转，关闭前必须有回归用例和当前配置版本下的人工确认。回归验证能打开逐题证据，确认记录绑定 configVersion，提示词/索引/模型/检索配置一变，旧确认就 stale。发布检查会把门禁是否过期、P0/P1、点踩率、空结果率、P95 一起看，不满足就 blocked。」
