## 1. 模型与调用层

### 1.1 采样参数 ★★★★

**问法**：temperature、top_p、top_k 分别是什么？怎么调？

**答点**

- `temperature`：对 logits 做缩放后再采样。越低越确定，越高越发散。抽取、分类、结构化输出用 0–0.2；创意、头脑风暴用 0.7–1.0。
- `top_p`（nucleus）：只在累计概率达到 p 的候选集里采样。与 temperature 二选一调，别同时大改。
- `top_k`：只保留概率最高的 k 个候选。对长尾噪声抑制更直接，但不同词表规模下不可比。
- 生产默认：结构化任务 `temperature=0`、`top_p=1`；对话可给 0.3–0.7。

**陷阱**

- 「temperature=0 就完全确定吗？」不是。浮点累加、batch 调度、MoE 路由、并行 kernel 都可能带来微小差异；要完全复现需固定 seed + batch + 硬件/后端。
- 「top_p=0 会怎样？」通常等价于取 argmax；不同厂商实现有差异，不要依赖。

### 1.2 上下文与 token ★★★★★

**问法**：context window 是什么？token 怎么算？prefill 和 decode 有什么区别？

**答点**

- token 是模型的输入单位，不等长于字符；中文常见 1 字 ≈ 1–2 token，代码/符号更碎。估算用 tokenizer，不要用字符数硬算。
- **prefill**：并行处理整段输入，是矩阵乘法，算力密集 → 决定**首 token 延迟（TTFT）**。
- **decode**：逐 token 自回归生成，每步要读全部权重和 KV cache，是**显存带宽密集** → 决定**出字速度（TPS）**。
- **KV cache**：把已算过的 K/V 缓存下来，避免每步重算。多轮对话复用能显著降延迟；但改 system prompt 会让前缀失效。
- **prompt caching**：对稳定前缀做缓存，命中条件是「前缀逐 token 完全一致」。工程上把稳定的 system/工具定义/长文档放前面，把变量放后面。
- 长上下文 ≠ 免费：成本线性涨、延迟涨、还有 lost in the middle。

**追问**

- 「长上下文能取代 RAG 吗？」不能。RAG 解决的是**知识更新、权限隔离、引用溯源、成本**，不只是塞不塞得下。详见 §3.12。
- 「怎么估成本？」输入 token × 输入单价 + 输出 token × 输出单价；注意缓存命中价、图片按 token 折算、reasoning token 单独计费。

### 1.3 流式输出 ★★★★

**问法**：流式怎么做？SSE 和 WebSocket 怎么选？

**答点**

- **SSE**（`text/event-stream`）：单向 server→client，走普通 HTTP，自动重连，适合「请求一次、持续推送」。LLM 输出天然是单向流。
- **WebSocket**：双向、长连接，适合需要客户端频繁上行（协同编辑、语音）或自定义二进制协议。
- **fetch ReadableStream**：前端也可以直接读 chunk，适合不想用 EventSource 的场景（能带自定义 header、能 POST）。
- 首 token 优化：缩短 prompt 前缀、启用 prompt cache、检索与生成并行、先推检索阶段状态、用更小的模型做改写。
- 结构化输出 + 流式：不要边流边 `JSON.parse` 整个对象。要么只解出某个字符串字段做预览（增量解码 + 处理转义/半个 unicode），要么用「事件流 + 最终完整对象」两段式。
- 取消：`AbortController` 从 HTTP 层一路传到模型调用和检索；服务端要能感知客户端断开并停止计费。

**陷阱**

- 「SSE 能 POST 吗？」原生 EventSource 不能，但可以用 fetch + ReadableStream 自己解析 `data:` 行。
- 「流式下怎么保证最终一致？」delta 只做预览，`done` 事件给权威完整结果，前端再做一次 schema 校验。

### 1.4 结构化输出 ★★★★★

**问法**：怎么让模型稳定返回 JSON？失败怎么办？

**答点**

- 三种实现，可靠性递增：
  1. **Prompt 要求 JSON**：最弱，容易带 markdown 围栏、注释、前后废话。
  2. **JSON mode**：服务端保证语法合法，但不保证符合你的 schema。
  3. **Function calling / JSON Schema 约束**：把 schema 交给模型侧约束，最稳；部分厂商支持 constrained decoding（按语法生成）。
- 工程上必须做**最后一道校验**：Zod / Pydantic。校验失败的处理顺序：
  1. 轻量修复（去围栏、`jsonrepair`）；
  2. 把**校验错误原文**回灌给模型重试一次（repair loop）；
  3. 仍失败则降级：返回原始文本 / 走规则兜底 / 报可识别的错误码。
- schema 设计：字段少而稳定、枚举代替自由文本、必填项别太多、给每个字段写描述（描述也是 prompt）。

**追问**

- 「为什么不用正则抠 JSON？」能跑 demo，生产会死在嵌套和转义上。
- 「流式 + JSON 怎么办？」见 §1.3。

### 1.5 幻觉 ★★★★★

**问法**：幻觉怎么产生的？怎么治理？

**答点**

- 分层归因（比一句「模型会编」强得多）：
  1. **知识缺失**：训练里没有，模型仍按语言先验补全；
  2. **检索失败**：没召回 / 召回错 / 上下文被截断；
  3. **上下文冲突**：多个来源互相矛盾，模型随机选一个；
  4. **指令压力**：prompt 要求「必须回答」，模型不敢说不知道；
  5. **解码随机性**：采样温度高。
- 治理要按层下手：
  - 检索侧：提高召回、加引用、控制上下文质量；
  - 生成侧：强制「只依据上下文」、允许拒答、结构化输出；
  - 后处理：证据校验（引用必须能在原文定位）、断言级检查、禁用词/领域规则；
  - 评测侧：黄金集里专门放负例和 `mustNotMention`；
  - 产品侧：展示引用、低置信度降级、用户反馈闭环。
- **关键认知**：prompt 里写「不要编造」是最弱的一层；真正有效的是**可验证的引用 + 不确定就拒答 + 自动化评测**。

**陷阱**

- 「你们幻觉率多少？」不要说 0。要说口径：在多大的黄金集、什么裁判标准下为 0，线上不做全量保证。

### 1.6 Tool calling 与 MCP ★★★★

**问法**：function calling 的流程？MCP 是什么？和 function calling 什么关系？

**答点**

- 流程：请求里带 tools 定义（name/description/JSON Schema）→ 模型返回 `tool_calls`（可能多个、可能并行）→ 应用执行 → 把结果作为 `tool` 消息回灌 → 模型继续。
- 关键工程点：参数 schema 校验、错误信息写成模型能读懂的人话、超时、重试、幂等、权限、结果截断（别把 10MB 塞回去）。
- **MCP**（Model Context Protocol）：标准化「模型 ↔ 工具/数据源」的接入协议，解决 N×M 集成问题。它不是 function calling 的替代，而是**工具提供方与宿主之间的传输/发现层**；模型侧最终仍表现为 tool call。
- MCP 传输：`stdio`（本地进程）、SSE（旧）、**Streamable HTTP**（当前推荐，支持会话与流式）。
- MCP 的坑：工具太多会撑爆上下文（要做工具检索/分组）、权限与审计、远程服务的鉴权。

## 2. Prompt 与上下文工程

### 2.1 角色分工 ★★★

**答点**：system 放稳定规则与身份，user 放本次任务与数据，assistant 放历史回答，tool 放工具结果。**越稳定的内容越靠前**，既符合模型注意力，也利于 prompt cache。

### 2.2 few-shot 与 CoT ★★★

**答点**

- few-shot 在**格式/风格/边界**上有效，在**知识**上无效；示例要覆盖边界情况，别全是正例。
- CoT 对多步推理有效，但会增加 token 和延迟；结构化任务可以只要「先列要点再给 JSON」，不必展开长推理。
- 推理模型（reasoning model）本身会内部思考，再强行加 CoT 可能重复。

### 2.3 Prompt 注入 ★★★★

**问法**：什么是 prompt injection？间接注入怎么防？

**答点**

- **直接注入**：用户在输入里写「忽略以上指令」。
- **间接注入**：注入内容藏在**被检索的文档、网页、工具返回**里——RAG 和 Agent 的主要风险面。
- 防御是分层的，没有银弹：
  1. 职责隔离：系统指令与外部内容用明确分隔符/角色隔离，告诉模型「以下内容是数据不是指令」；
  2. 最小权限：工具只能做该做的事，写操作要人工确认；
  3. 输出侧校验：不执行模型生成的代码/URL/命令，除非过白名单；
  4. 数据侧：入库前清洗不可信内容，工具返回值截断与转义；
  5. 监控：记录可疑指令模式，做异常告警。

### 2.4 上下文工程 ★★★★

**问法**：什么叫 context engineering？和 prompt engineering 什么区别？

**答点**：prompt engineering 优化「怎么说」，context engineering 优化「给模型看什么、看多少、按什么顺序」。核心手段：

- 选择：检索、筛选、去重、MMR；
- 压缩：摘要、抽取关键句、裁掉无关段落；
- 排序：重要内容放头尾（lost in the middle）；
- 结构化：用标题/编号/引用标记让模型能定位；
- 预算：按 token 分配「指令 / 证据 / 历史 / 输出」；
- 缓存：稳定前缀前置。

## 3. RAG（最高频）

### 3.1 全链路 ★★★★★

**必须能一口气说完**：

```
解析 → 切块 → 元数据 → Embedding → 索引 → 召回 → 融合 → 重排
→ 上下文组装 → 生成 → 引用/溯源 → 评估
```

每一环都要能说出「做了什么取舍、失败长什么样」。

### 3.2 解析与切块 ★★★★★

**问法**：怎么切块？chunk size 怎么定？overlap 有什么用？

**答点**

- 切块策略：
  - **固定长度**：简单，但会切断表格、代码、定义；
  - **递归字符**：按段落→句子→字符逐级回退，通用性好；
  - **结构感知**：按 Markdown 标题、HTML DOM、代码 AST 切，语义边界最干净；
  - **语义切块**：按 embedding 相似度突变点切，成本高、效果不稳定；
  - **父子块（small-to-big）**：小块召回、父块喂模型，兼顾精度与上下文；
  - **上下文增强**：给每个 chunk 前置「文档标题 + 章节路径 + 一句话摘要」（contextual retrieval），显著提升召回。
- `chunk_size`：受 embedding 模型有效长度、问题粒度、文档结构共同约束；800–1200 字符是常见起点，但要靠评测定。
- `overlap`：防止边界信息丢失，代价是索引膨胀和重复召回；10%–25% 常见。
- 元数据决定后续能不能过滤、能不能引用：`doc_id / path / title / section / symbol / line_range / hash`。
- **chunk_id 要稳定**：由内容哈希 + 位置决定，增量索引和基线对比都依赖它。

**陷阱**

- 「overlap 越大越好？」不是，会重复召回、稀释上下文、涨成本。
- 「语义切块一定更好？」不一定，慢且不稳，结构化文档优先结构切。

### 3.3 Embedding ★★★★

**答点**

- 选型维度：语言（中文要选多语言/中文优化）、维度、最大输入长度、是否支持 query/passage 前缀、是否可本地部署、成本。
- 常见：bge-m3、bge-large-zh、Qwen3-Embedding、`text-embedding-3-small/large`。
- **query 与 doc 可能要用不同前缀**（如 `query: ` / `passage: `），用错会明显掉点。
- 相似度：cosine / dot / L2。向量归一化后 cosine 与 dot 等价。
- **换 embedding 模型 = 必须重建索引**，且新旧向量不可混用；工程上做版本化索引目录。
- 维度不是越高越好：召回略升，但存储和扫描成本线性涨。

**追问**

- 「怎么评估 embedding 模型？」固定切块和查询集，只换模型，比 recall@k / MRR；同时看延迟和成本。
- 「能不能用 LLM 做 embedding？」可以但不划算，且语义空间不稳定。

### 3.4 向量库与 ANN ★★★★

**答点**

- 选型看：部署形态（嵌入式/服务端/云）、过滤能力、规模、多租户、是否支持混合检索、运维成本。
  - 嵌入式：LanceDB、FAISS、Chroma；
  - 服务端：Milvus、Qdrant、Weaviate；
  - 已有 PG：pgvector。
- **HNSW**：多层可导航小世界图。
  - `M`：每个节点最多连多少边，越大召回越高、内存越大；
  - `efConstruction`：建图时候选集大小，越大图质量越好、建得越慢；
  - `efSearch`：查询时候选集大小，越大召回越高、延迟越大。
- **IVF**：先聚类分桶，查询只扫 `nprobe` 个桶；`nlist` 越大桶越细。
- **PQ**：把向量分段量化压缩，省内存但损失精度。
- **过滤 + 向量**：pre-filter 先按元数据缩小集合再搜，过滤条件写错会直接漏；post-filter 先搜再过滤，可能过滤后不足 k 条，要用更大的 topN 补偿。生产要确认数据库的实际语义。
- 小数据量（几万条）全表扫描可能比 ANN 更快、更可复现——不要为了「架构感」上 ANN。

### 3.5 混合检索与融合 ★★★★★

**问法**：为什么要混合检索？RRF 是什么？为什么不直接加权？

**答点**

- 稠密向量擅长**语义/口语**，稀疏检索（BM25）擅长**精确符号**：类名、型号、错误码、API 名、人名。单路必漏。
- **RRF**：`score(d) = Σ 1 / (k + rank_i(d))`，`k` 常取 60。只用名次，不用原始分，所以天然解决「向量分和 BM25 分不可比」的问题。
- 加权求和需要分数归一化，且不同查询下分布会漂；RRF 更稳、更少调参。
- 工程细节：多路召回要**并行**、设置每路 topN、融合后做去重（按 chunk_id）、再做公平窗口（多类问题每类保底）。
- 精确匹配可以不做成第三路并行，而是作为**融合后的置顶/补位**——避免长尾符号淹没主查询。

### 3.6 重排 ★★★★

**答点**

- 召回是「快而粗」，重排是「慢而准」。cross-encoder 把 query 和 doc 一起编码，精度高但只能对小候选集做。
- 典型链路：召回 top 50 → 重排 top 5。
- 方案：bge-reranker、Cohere Rerank、LLM rerank（贵、慢、但能理解复杂约束）。
- 收益与代价：通常明显提升 context precision，代价是 50–300ms 延迟和成本；要按 P95 预算决定。

### 3.7 Query 改写 ★★★★

**答点**

- 多轮场景必做**指代消解**：「它怎么设置宽度」→「THING.Box 怎么设置 width」。
- 其他手段：multi-query（生成多个改写再融合）、HyDE（先生成假想答案再检索）、step-back（先问更抽象的问题）、decomposition（拆子问题）。
- 改写的代价：多一次模型调用、可能引入噪声、可能把精确符号改坏。**失败要能回退原问句**。
- 判断要不要改写：有历史 + 指代词/省略 → 改写；单轮精确符号查询 → 不改。

### 3.8 上下文组装 ★★★★

**答点**

- 去重（同一文档多 chunk 合并）、MMR（多样性）、按 token 预算裁剪。
- 排序：重要内容放头尾；给每个片段编号/路径，方便模型引用。
- **lost in the middle**：长上下文中间的信息容易被忽略。
- 引用对齐：上下文编号必须和最终 citations 一一对应，不能模型自己编编号。

### 3.9 增量索引 ★★★★

**问法**：文档更新了怎么办？怎么不停服？

**答点**

- 指纹：文件 hash / mtime + size；内容没变就跳过。
- 增量复用：按稳定 `chunk_id` 复用旧向量，只重算变化的 chunk。
- 版本化：新索引写新目录，构建 + 校验通过后原子切换 `active` 指针。
- 失败回滚：构建失败或门禁失败，指针指回旧版本。
- 删除：墓碑标记 + 重建时清理，避免「删了还能搜到」。
- 双写/切换窗口：切换瞬间要保证读到的是一致版本（加载成功再替换内存对象）。
- 多实例：只让一个实例构建，其他实例轮询指针或接收通知。

### 3.10 RAG 评估 ★★★★★

**问法**：怎么证明 RAG 变好了？指标有哪些？

**答点**

- 检索侧：`recall@k`、`precision@k`、`MRR`、`nDCG`、`hit rate`、false-empty（可回答却返回空）、禁止命中（不该返回的类却返回）。
- 生成侧：`faithfulness`（答案是否被上下文支撑）、`answer relevancy`、`context precision`、`context recall`、`answer correctness`（RAGAS 体系）。
- 黄金集怎么建：真实 query 采样 + 人工标注「正确 chunk / 正确要点 / 禁止点」；按 tag 分层（类名、口语、错拼、多类、负例）。
- **基线 + 门禁**：固定黄金集和 fixture hash，每次改动跑全量，和基线逐题对比，指标下降就阻断发布。
- 子集只能用来排查，不能当门禁——否则会挑简单题。

**LLM-as-judge 的坑（★★★★）**

- 位置偏差：偏好第一个/最后一个 → 随机交换顺序；
- 长度/啰嗦偏好 → 评分 rubric 明确写「长度不构成加分」；
- 自我偏好 → 用不同厂商/不同模型做裁判；
- 评分漂移 → 温度 0、固定 prompt、人工校准集、多次采样取多数。

### 3.11 失败定位 ★★★★★

**问法**：用户说答不出来，你怎么查？

**标准链路**

1. 拿原 query 重跑检索：正确 chunk 在不在 top-k？
2. 不在 → 切块 / embedding / query 改写 / 混合检索 / 过滤条件的问题；
3. 在但答错 → 上下文太杂、被截断、prompt 约束不够、模型能力不足；
4. 都正常 → 问题超出知识库范围，应该拒答而不是硬答；
5. 最后看 trace：每阶段耗时、召回列表、丢弃原因、最终 prompt、模型输出。

### 3.12 进阶话题 ★★★

- **长上下文 vs RAG**：长上下文贵、慢、有 lost-in-middle，且不能做权限隔离和引用溯源；RAG 是「按需取用 + 可审计」。
- **GraphRAG**：适合多跳、实体关系密集的问题；成本高，需要评测证明必要性。
- **多模态 RAG**：图片走 OCR/图注/多模态 embedding；表格要专门处理（结构保留）。
- **Agentic RAG**：让模型决定检索几次、检索什么；灵活但延迟和成本不可控，要用步数上限兜底。
- **微调 vs RAG**：RAG 解决「知识新、要引用、可更新」；微调解决「风格、格式、领域表达、小模型提效」。二者不互斥。

## 4. Agent / LangGraph

### 4.1 什么时候该用 Agent ★★★★★（反向题）

**答点**

- Agent 的本质：LLM + 工具 + 循环 + 状态。代价是不确定性、延迟、成本、难测试。
- **能确定性编排就不要 Agent**：分类、抽取、固定流程用 LCEL/workflow。
- 适合 Agent 的场景：步数不确定、需要根据中间结果决定下一步、工具组合开放（如「查一下再改一下再验证」）。
- 面试官问「为什么不用 Agent」，是在考判断力，不是考你会不会用。

### 4.2 ReAct 循环 ★★★★

**答点**：Reason → Act（tool call）→ Observe（工具结果）→ 再 Reason，直到给出最终答案或达到步数上限。
工程上必须加：最大步数、循环检测（相同工具+参数重复）、超时、成本上限、失败降级。

### 4.3 LangGraph 核心概念 ★★★★★

**答点**

- `StateGraph`：节点改状态，边决定走向；状态是显式 schema。
- **reducer**：决定同名字段怎么合并。`add_messages` 是 append 而不是覆盖——这是消息列表能累积的原因；自定义 reducer 可做求和、取最新等。
- 节点 / 普通边 / **条件边**（按状态路由）/ `Command`（同时更新状态并跳转）。
- 子图：可复用、可嵌套；状态可以共享 key 或显式映射。
- 并行分支：fan-out 后 fan-in，注意 reducer 要能合并并发写。

### 4.4 状态与持久化 ★★★★★

**答点**

- **checkpointer**：每个 super-step 存快照；`thread_id` 标识一条会话/任务。
- 持久化后端：Memory（开发）/ Postgres / Redis / SQLite。
- 能力：断点续跑、时间旅行（`get_state_history`、`update_state`）、人工介入、崩溃恢复。
- **durable execution**：长任务可以在进程重启后从最后一个 checkpoint 继续；前提是节点逻辑幂等。
- 生产注意：checkpoint 表会膨胀，要做清理；有状态服务不能随便水平扩展，状态必须外置。

### 4.5 Human-in-the-loop ★★★★

**答点**

- `interrupt()` 在节点内暂停，把待确认内容抛给前端；恢复时用 `Command(resume=...)` 把用户输入送回。
- **必须配 checkpointer**，否则没有状态可恢复。
- 适用：写操作、发消息、付款、删除等高危动作。
- 设计要点：展示「将要做什么」而不是原始参数；超时策略；拒绝后的回退路径。

### 4.6 多 Agent ★★★

**答点**

- 拓扑：supervisor（主管分派）、handoff（移交）、planner-executor、reflection/critic（生成-批评-修订）。
- **必须主动说代价**：token 成本是单 agent 的数倍、错误级联、调试困难、延迟高。
- 适用：子任务边界清晰、可并行、需要不同工具/提示词/模型。
- 不适用：一个 agent 加几个工具就能解决的事。

### 4.7 工具设计 ★★★★

**答点**

- 描述是给模型看的：什么时候用、什么时候别用、参数含义、返回什么。
- 参数用 schema 严格校验；枚举优于自由文本。
- 错误信息要可行动：「参数 id 不存在，请先调用 search 获取 id」，而不是 stack trace。
- 幂等、超时、重试、结果截断、权限最小化、危险操作二次确认。
- 工具数量要控制：太多会撑爆上下文、降低选择准确率；可做工具分组或工具检索。

### 4.8 记忆 ★★★

**答点**

- 短期：消息窗口、滑窗 + 摘要、token 预算裁剪。
- 长期：向量记忆（检索相关历史）、事实抽取（用户偏好/画像）、结构化状态。
- 风险：记忆污染（错误信息被长期记住）、隐私、过期；要能查看/编辑/删除。

### 4.9 可靠性 ★★★★

**答点**：最大步数、`recursion_limit`、循环检测、超时、成本上限、失败降级（降级到纯 RAG / 纯规则）、可重放、幂等、可观测（每步的输入输出与 token）。

### 4.10 LangChain 0.3 vs 1.x ★★★★

**答点**

- 0.3：`AgentExecutor` + 各类 agent 封装；LCEL 是编排核心。
- 1.x：agent 抽象迁到 **LangGraph** 之上，`AgentExecutor` 退役，包结构拆分，入口变成 `createAgent`（JS）/ `create_agent`（Python）；LCEL 仍可用。
- 迁移判断：看是否依赖旧 agent 封装、是否有自定义 callback/parser、是否有大量 chain 组合；先锁版本，再单独评估。
- 面试时不要说「0.3 就是老版本所以不好」，要说清**锁版本的理由**（生态兼容、迁移成本、行为可复现）。

## 5. 工程化

### 5.1 并发与限流 ★★★★

**答点**

- 并发控制：信号量 / 队列 / `p-limit`；区分「检索并发」和「生成并发」（生成更贵）。
- 队列满：返回 429/503，别无限排队。
- 限流算法：固定窗口、滑动窗口、令牌桶（允许突发）、漏桶（平滑）。
- 供应商限流：读 `Retry-After`、指数退避 + 抖动、区分可重试（429/5xx/网络）与不可重试（400/401/403）。
- 熔断：连续失败后快速失败一段时间，避免雪崩；半开探测恢复。

### 5.2 取消与超时 ★★★★

**答点**：`AbortController` 贯穿 HTTP → 检索 → 模型 → 流式输出；每一层都要监听 signal。超时要分层设置（总预算 > 单步超时）。客户端断开后服务端必须停止后续工作，否则白烧 token。

### 5.3 类型与契约 ★★★★（TS 岗重点）

**答点**

- 用 Zod 做**单一事实源**：请求/响应 schema、模型输出 schema、前端类型推导。
- 前后端不共享实现，但共享契约；服务端定义，前端/评测各自校验响应形状。
- 好处：契约变更尽早暴露、错误码可枚举、IDE 有补全。
- 模型输出也走同一套 schema，校验失败走 repair loop。

### 5.4 长任务与异步 ★★★

**答点**：HTTP 请求不适合跑分钟级任务。做法：提交任务 → 返回 task_id → 轮询/SSE/WebSocket 推送 → 任务状态落库。注意幂等（重复提交）、超时、重试、取消、结果过期清理。

### 5.5 缓存 ★★★

**答点**

- prompt cache：稳定前缀前置；
- 语义缓存：query embedding 相似度命中历史答案，要注意「相似但不同」的误命中；
- embedding 缓存：按内容 hash；
- 检索结果缓存：注意索引版本变化要失效。

### 5.6 成本 ★★★★

**答点**：按租户/功能统计 token、模型单价、检索调用数；做预算告警和配额；优化手段：小模型路由、减少上下文、缓存、批处理、限制输出长度、流式早停。

### 5.7 部署 ★★★

**答点**

- Node：注意事件循环不要被 CPU 密集任务阻塞（大文件解析、分词、embedding 预处理）→ worker_threads / 子进程。
- 有状态服务：session / checkpoint / 限流状态必须外置，否则不能水平扩展。
- 冷启动：模型客户端连接池、索引懒加载 vs 预加载。
- 优雅关闭：停止接新请求 → 中止在途 → 落库 → 退出。

### 5.8 安全 ★★★★

**答点**：密钥不进代码/日志/报告；日志脱敏（Authorization、token、API key）；prompt 正文是否入日志要明确；多租户数据隔离；工具权限最小化；输出过滤（XSS、危险 URL、代码执行）；审计。

## 6. 评测与可观测

### 6.1 离线评测 ★★★★★

**答点**

- 数据集：黄金集（输入 + 期望）、回归集（历史 bad case）、负例集（应该拒答/空结果）。
- 指标要**确定性优先**：schema 是否合法、引用是否合法、路径是否泄漏、必须提及/禁止提及——这些不依赖 LLM 裁判。
- LLM 裁判只做语义判断，必须校准（人工样本 + 一致性）。
- 门禁：绝对阈值 + 基线对比，必须全量，失败非零退出。
- 数据集版本化：fixture hash 变化要标记门禁过期。

### 6.2 线上可观测 ★★★★

**答点**

- trace：traceId 贯穿每阶段（检索、重排、生成、解析、守卫），记录耗时、token、召回列表、最终 prompt、错误。
- 指标：QPS、P50/P95/P99、TTFT、错误率、空结果率、点踩率、成本。
- 日志：结构化、可检索、脱敏、轮转。
- 闭环：点踩 → 问题单 → 回归用例 → 修复验证 → 关闭。

### 6.3 线上评估 ★★★

**答点**：A/B 或灰度、用户反馈、抽样人工评审、影子流量（新链路只记录不展示）。离线指标涨不代表线上体验涨，要看任务完成率和满意度。

## 7. 选型与生态

### 7.1 LangChain / LlamaIndex / 自研 ★★★★

**答点**

- LangChain：通用编排、生态广、集成多；抽象层多，出问题要读源码。
- LlamaIndex：偏数据/RAG 管线，索引和检索抽象更细。
- 自研：可控但重复造轮子。
- **正确姿势**：通用能力用成熟组件，领域规则和框架缺口才自研；每个自研都要有失败用例和记录（这是第 10 篇的核心观点）。

### 7.2 TypeScript vs Python ★★★★★（你的差异化）

**答点**

- Python：训练、微调、评测、数据生态最强；
- TS/Node：Web 服务、流式、类型契约、前后端同栈、部署运维统一；
- 结论：**按团队和服务栈选**，需要训练/微调的部分单独用 Python 跑离线任务。
- 要说得出跨语言差异：两边 LangChain 版本线和 API 不完全对齐，不能照抄示例。

### 7.3 模型选型 ★★★★

**答点**：能力（评测集实测）、上下文长度、延迟、成本、是否支持 tool/JSON、多语言、私有化部署、稳定性。做法：小模型打底 + 难例路由到大模型；用同一套评测集横向比。

## 8. 手撕 / 设计题

准备这 7 道就够：

1. **流式 RAG 接口**：检索 → 拼 prompt → SSE 推 token → done 推引用与耗时。
2. **多轮改写 + 混合检索 + 引用溯源**的问答系统。
3. **召回率下降的定位流程**（见 §3.11）。
4. **文档增量索引 + 无停服切换 + 失败回滚**。
5. **一个 tool-calling agent 循环**：最大步数、错误回灌、取消、成本上限。
6. **多租户限流 + 成本控制**。
7. **LLM 输出的结构化校验与修复**：schema → 校验 → repair → 降级。

## 9. 答题模板

- **讲取舍**：`场景 → 候选方案 → 我选了什么 → 为什么 → 代价是什么 → 怎么验证`。没有「代价」的答案会被认为没落地。
- **讲数字**：说清口径（数据集多大、什么指标、什么时候测的），不要只给一个漂亮数。
- **讲失败**：主动说一个真实坑 + 怎么定位 + 怎么验证修好了，比背概念可信得多。
- **不会时**：`这块我没有在生产里做过，我的理解是……，如果要落地我会先验证……`。比硬编强得多。
- **不要过度声称**：没做过的不说做过；用了依赖不等于用了能力。
