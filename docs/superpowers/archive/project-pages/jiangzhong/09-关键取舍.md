# 江中智能助手 · 关键取舍
> 16 条设计取舍，每条都回答「为什么不用另一种」。

## 1. [重点] 为什么用 LangGraph，而不是一条 LCEL 链？

一条链适合「一次输入 → 一次输出」；这个项目需要：

- 多轮状态与 checkpoint；
- 模型 → 工具 → 再回模型；
- 三条固定流程在不同步骤停留、恢复；
- 只读计划按依赖分批执行、部分失败、重试；
- 审批/场景动作需要「暂停后继续」。

所以用 `StateGraph` 做主图，固定流程各自编译子图。代价是状态与路由更复杂，收益是流程可控、可恢复、可观测。换成一条 LCEL 链，就无法在步骤之间暂停、恢复和按依赖调度。

## 2. [重点] 为什么先 classify → route → act，而不是一个大 Prompt？

- classify 只判断意图类别，不携带工具目录，减少第一次调用的体积与误导；
- route 看全量工具和选择规则，产出结构化 goals + plan，而不是让模型边想边调；
- act 只执行当前计划或候选工具，上下文更小、行为更可复现；
- 每个阶段都能单独评测、单独看 trace。

代价是多一次或两次模型调用；收益是查询链路可校验、可回放、可归因。一个大 Prompt 把所有规则和工具一次性塞给模型，既贵，也无法定位错在理解、规划还是执行。

## 3. [重点] 为什么需要计划编译器，而不是直接执行模型计划？

模型输出的计划可能包含未知工具、缺参数、循环依赖、跨设备串用、把写步骤混进只读计划。编译器的职责是：

- 工具必须在目录内且属于允许的只读动作；
- 参数必须命中合同；
- 设备必须已接地；
- 绑定、条件、依赖必须存在且无环；
- 最多 8 步、3 层依赖、3 个知识库步骤；
- 范围外整轮交回既有路径，非法计划最多修复一次。

没有编译器，模型的一个错误计划会直接变成一串错误工具调用。直接执行模型计划，等于把工具白名单、参数合同和依赖顺序都交给模型自觉。

## 4. [重点] 为什么固定流程还是独立子图？

因为批次追溯、维修工单、巡检需要：

- 跨多轮收集/确认字段；
- 中途停下来等用户或审批；
- 分支、循环、回退；
- 逐步审计「走到哪一步」。

普通只读查询不需要这些，走计划执行器即可。判断标准不是「是不是业务」，而是「是否需要多轮状态与暂停恢复」。把所有业务都塞进一张大图，会让只读查询也背上流程状态；把所有流程都压成工具调用，又会丢掉中途暂停和逐站推进。

## 5. [重点] 为什么确认步不做模型兜底？

写操作（取消告警、创建工单、巡检报修、备件申请、批次记录）不可逆。确认必须由用户明确表达；模型兜底只用于「识别用户这句话是场景指令还是步骤回答」，不用于代替确认。让模型兜底确认，等于把不可逆操作交给一次概率判断。

## 6. 为什么场景方法由宿主上报，服务端不内置？

- 不同宿主的三维能力不同，服务端不应该硬编码方法名；
- 宿主注册时同时给用途与参数 Schema，模型据此选择与生成参数；
- 执行函数只留在宿主，服务端看不到实现，减少耦合。

代价是每次请求多带一份目录；收益是宿主可替换、方法可扩展。服务端内置方法名，会让换宿主时必须改服务端，也无法保证方法真的存在。

## 7. 为什么要有场景回执，而不是模型说执行就执行？

模型只生成动作与参数；真正执行在宿主。回执让服务端知道：

- 成功/失败/模拟；
- 是否可以继续本轮；
- 断线后是否状态不明。

没有回执就无法区分「执行了」和「模型说执行了」。直接相信模型的「已完成」，会把三维动作变成一句不可验证的话。

## 8. [重点] 为什么状态不明时不自动重放？

重复取消告警、重复建单、重复写批次都有副作用。系统宁可要求人工核对，也不自动重试。幂等键解决的是「同一次请求重放」，不是「执行结果未知」。把未知当失败重试，可能造成第二次副作用；把未知当成功继续，又会漏掉真实失败。

## 9. [重点] 为什么同一会话要用 PostgreSQL 锁？

多副本部署时，进程内锁无效。会话轮次必须跨实例串行，否则同一会话的两条消息会同时改图状态。用数据库咨询锁 + 超时，简单且可验证。轮次另有 active turn、心跳和租约，用来区分「正在跑」「中断」「可放弃」。用进程内锁，单机看似够用，扩容后立刻失效。

## 10. [重点] 为什么流式用 SSE，不用 WebSocket？

- 对话是单向服务端推送，SSE 足够；
- 走普通 HTTP，鉴权、代理、日志复用现有设施；
- 浏览器 `fetch` 能消费，宿主模块用 `ReadableStream` 解析。

代价是不能客户端双向推送；本项目不需要。上 WebSocket 会引入额外连接管理、心跳和代理兼容成本，却换不来本场景需要的能力。

## 11. 为什么审阅台独立进程、独立鉴权？

- 审阅是只读、低频、可能跨团队使用；
- 与对话主链路隔离，采集失败不影响业务；
- 独立令牌/IP 白名单，避免把执行链路暴露给普通用户；
- 评测、标注、校准写的是审阅数据库，不是业务库。

把审阅塞进业务进程，会让采集故障影响对话，也会让普通用户可能触达执行链路。

## 12. 为什么撤销独立 SDK，改成宿主内模块？

- 原 SDK 只服务一个宿主、`private`、未发布；
- 审批输入解释、工单字段组装仍在宿主，单换客户端不足以移植；
- 不同宿主的 UI、身份、三维场景差异大，整目录复制更现实；
- 网关仍是唯一事实源，HTTP/SSE 合同不变。

现在的分层是：`assistant/core/`（HTTP/SSE/回执/恢复）、`assistant/ui/`（通用窗口）、宿主 `integrations/`（业务适配）。继续维护独立 SDK，会把业务适配留在宿主，却额外背一层版本和发布成本。

## 13. 为什么宿主模块仍要支持注入 `fetch`？

ThingJS 会覆盖全局 `fetch`，返回对象的 `body` 不是 `ReadableStream`。模块不注入就只能依赖全局实现，宿主无法自救。注入让宿主保留自己的 polyfill，同时让助手拿到原生流。要求宿主改 ThingJS 或改全局环境，成本和风险都更高。

## 14. [重点] 为什么评测要加裁判和人工标注？

执行断言只能证明「按合同跑了」，不能证明「用户拿到了什么」。交付判定把「工具查到」与「回答交付」分开；裁判补语义覆盖与依据；人工标注提供最早偏离、责任节点和具体问题；校准再回答「裁判和人工是否一致」。这样质量结论不是单一模型的自我评价。只看执行断言，会把「工具成功但回答漏项」判成通过。

## 15. 为什么有后台运行？

用户关闭页面后，耗时只读任务不应被 abort。`assistant_runs` + 单进程 worker 把执行从 HTTP 请求生命周期里解耦，支持轮询与取消；但重启不自动重跑，避免状态不明时重复副作用。把长任务绑在请求上，用户一关页面就前功尽弃；让 worker 自动重跑，又可能重复副作用。

## 16. 已知不做的取舍

- 没有 CI 门禁（E4 本期取消）；
- 没有多租户配额/计费；
- 三维只验证了 3 个真实动作；
- 只读计划只覆盖 12 类有合同的动作；
- 长期记忆默认关闭，用户域与向量检索未做；
- 裁判模型开通与校准尚未完成，交付指标不进入 gate；
- 第二层 live 在扩展到 57 题后尚未重建完整基线。

这些是有意留边界，不是漏做：先把可验证的主链路跑稳，再逐步扩范围和进门禁。面试时主动说边界，比假装全能更可信。
