# THINGJS 文档 RAG · 八股项目答法
> 一句话定位：先判断「这题能不能用 ThingJS 项目接、能接到多深、哪里必须刹车」，再按「结论 → 分层 → 数字 → 代价」逐题作答。

完整的 60 秒 / 3 分钟 / 10 分钟讲法和唯一一份数字表见 [10-面试讲法](/03-项目实战/01-THINGJS文档RAG/10-面试讲法)，本页不复述。

## 一句话定位

> 这个项目在八股文里的定位是：**RAG 全链路 + 检索工程 + 评测门禁 + 索引运维的深度样本**；不是 Agent / LangGraph / 微调的样本。面试时把话题往前者引，后者用其他项目或概念回答。

## 强项：主动往这四块引

### 检索不是「向量 topK」

能讲出的层次比大多数候选人多 3 层：

1. 意图识别（docs / offtopic，闲聊不调模型）；
2. 查询计划（归一化、错拼纠正、别名展开、实体/成员配对、否定约束、视点特例）；
3. 向量 + BM25 双路并行召回；
4. 官方 `EnsembleRetriever` 做 RRF；
5. 精确符号置顶 / 补位；
6. 多类问题每类公平窗口；
7. 有界父块补全。

**这是最值得展开的一块**，因为它同时覆盖「RAG 检索」「混合检索」「RRF」「领域适配」四个高频题。

### 评测不是「跑几个例子看感觉」

- 100 题检索集（94 可回答）+ 30 题生成集（24 可回答）+ 12 题裁判校准；
- 确定性指标 + 独立 LLM 裁判；
- 绝对阈值 + 基线逐题对比；
- 三套门禁 + 发布检查；
- 门禁过期判断（索引版本 / fixture hash / 提示词指纹）。

**这块是区分度最高的**：绝大多数候选人只能说出「我们人工看了下」。

### 索引是「可运维的」

- 版本目录 + `manifest` + `BUILD_OK` + `active.json`；
- 文件 hash 增量复用向量；
- 子进程构建，父进程加载成功才替换 runtime；
- 门禁失败回滚指针并热加载旧版；
- 保留最近 5 个版本。

对应八股题：增量索引、热更新、失败回滚、索引版本一致性。

### 生成是「有契约的流水线」

```text
改写 → Prompt(YAML) → LCEL → JSON 解析 → 证据筛选
→ 领域守卫(一次纠错) → 确定性清洗 → 引用重排 → SSE
```

对应八股题：结构化输出、幻觉治理、引用溯源、流式、降级。

## 中性项：能讲，但要主动交代边界

| 话题 | 能讲什么 | 必须交代 |
| --- | --- | --- |
| 工程化 | 队列、熔断、abort、优雅关闭、trace | 单机进程内，不是分布式 |
| 部署 | 单机内网、SQLite、文件会话 | 水平扩展需要外置 |
| MCP | 两个工具，Streamable HTTP，会话登记 | 是服务端接入，不是 Agent 编排 |
| 前端 | SSE、Zod 校验、DOMPurify、E2E | 不是重点，别讲太久 |
| 鉴权 | 网关会话 + Bearer + 配额预检 | 多用户共用全局 secret |
| LangChain | LCEL、组件复用、回调、Retry | 锁定 0.3，未上 1.x |

## 弱项与空白：诚实 + 转场

### LangGraph（最重要的边界）

**事实**：项目**没有引入 LangGraph**（依赖已移除）；主链路是显式 `runChat` + LCEL，不是状态图。

**怎么答**：

> 「这个项目没用 LangGraph——文档问答是固定的检索-生成链路，不需要状态机，引入它反而是过度设计。LangGraph 我在另一个多轮业务助手的项目里用的：状态图、Postgres checkpointer、interrupt 人工确认、跨重启恢复。」

**不要做**：把 LCEL 链路包装成「LangGraph 思想」硬讲，一追问 checkpoint/state 就穿帮。

### Agent 与多 Agent

- 本项目能讲：为什么**不该**用 Agent（固定链路、确定性优先）；
- 能讲 MCP 服务端实现（工具定义、传输、会话）；
- 多 Agent 用概念 + 其他项目回答，不要说本项目的 Agent 经验。

### 微调 / 训练 / 多模态 / GraphRAG

- 只答概念和取舍；
- 明确说「没有生产实践」，然后给「如果要落地我会怎么验证」。

## 答题三段式

```text
① 一句话结论（反常识优先）
② 3–5 个层次（每层一个动作 + 一个理由）
③ 数字 / 证据 / 代价（证明不是纸上设计）
```

示例：

> 「我们的检索不是『问题转向量取 topK』（①）。中间有查询计划、双路召回、RRF、精确置顶、父块五层（②）。最近一次 100 题检索门禁 94/94、false-empty 0（③）。代价是链路长、单次检索比纯向量多几十毫秒，我们用并发和缓存控制。」

## 1. 模型与调用层

### Q1.1 你们 temperature 怎么设的？

**一句话**：按提示词声明走：回答 0、改写 0.2，模型实例按温度解析。

**展开**

- `answer.yaml` / `code-debug.yaml` 声明 `temperature: 0`，`rewrite.yaml` 声明 0.2；
- `createChatModel(env, apiKey?, temperature)` 接收温度，不再写死全局常量；
- `runChat` 按提示词温度取模型：共享模型按温度缓存，请求级令牌每次新建；
- `generateAnswer` 通过 `resolveModel(promptSpec.temperature)` 取实例，`llmPrompt.temperature` 记录的就是实际使用的值。

**防守**：这条链路曾经断过（YAML 声明 0、工厂写死 0.2），修完后补了单测和 YAML 严格校验；主动讲「配置必须真正绑定到运行时」比背参数更加分。

### Q1.2 怎么保证输出稳定？

**一句话**：不靠 temperature，靠「契约 + 校验 + 兜底」。

**展开**

1. JSON 输出契约：`final_answer` / `reasoning_summary` / `citations`；
2. `JsonOutputParser` + `jsonrepair` + Zod 校验；
3. 解析失败保留原文和 usage，不假装成功；
4. 确定性清洗把模型爱加的元说明、路径、无证据默认值删掉；
5. 评测里 schema/引用/路径/负例都是 100% 阈值。

**数字**：生成门禁历史通过 24/24、judgePass 95.8%、幻觉 0；最近一次 23/24、confidence 96.7% 被拦截并进入闭环。schema/confidence/citation/path/negative 要求 100%。

### Q1.3 流式怎么做的？

**一句话**：SSE，`delta` 只做预览，`done` 是权威结果。

**展开**

- 事件：`delta / reset / phase / done / error`；
- 增量解码只解 `final_answer` 的 JSON 字符串，处理转义和半个 unicode；
- 前端拿 `done` 里的完整对象再做一次 Zod 校验；
- 中断：客户端断开 / 服务关闭都会 abort 在途检索和生成。

**追问「为什么不用 WebSocket」**：输出是单向的，SSE 走普通 HTTP、自动重连、部署简单；不需要双向通道。

**追问「流式 JSON 怎么不炸」**：不整体 parse，按字段做增量解码，最终仍走完整解析。

### Q1.4 结构化输出失败怎么办？

**展开**

- 优先 `JsonOutputParser`；坏了用 `jsonrepair`；再不行保留原始文本；
- 生成侧还有一次**规则纠错**（守卫违规时重试一次）；
- 模型调用本身 `RunnableRetry` 重试 2 次；
- 最终失败才降级；鉴权/配额/队列错误**不伪装成降级**。

**关键句**：「降级要区分错误类型，把 401 当成『模型不可用』会把问题藏起来。」

### Q1.5 怎么防幻觉？

**一句话**：四层，不靠一句「不要编造」。

**展开**

1. **Prompt 约束**：只用上下文，没有就写「文档未说明」，禁止内部路径和元说明；
2. **证据筛选**：用户禁用词、视点 actor/target 约束，先把不该用的证据剔掉；
3. **规则守卫**：Box 构造、动画、多对象、视点越界；违规纠错一次，仍不行回退最小回答；
4. **确定性清洗**：删元说明、证据外 `THING.X`、无证据默认值、内部 `.md` 路径；destroy 后读取会注释掉。

**再补一刀**：评测有 `mustMention / mustNotMention / mustNotAppear`、负例、裁判幻觉计数。

**防守**：不要说「幻觉 0」，说「30 题生成集里 24 题可回答，裁判幻觉 0」。

### Q1.6 引用是怎么产生的？模型给的还是你们算的？

**一句话**：优先按正文反推，模型声明只作兜底。

**展开**

- 回答正文里实际提到的类/成员 → 反查对应 chunk → 生成引用；
- 不足时才回退模型声明的 `citations`，并校验 `chunk_id` 合法；
- 引用上限 3 条；引用和 `discarded` 互斥（引用不能指向被丢弃的块）。

**为什么**：模型经常「引用了没说的」或「说了没引用」，按正文对齐更可信。

## 2. Prompt 与上下文工程

### Q2.1 你们的 prompt 怎么管理？

**一句话**：YAML 版本化 + 指纹 + 不热更新。

**展开**

- `server/prompts/*.yaml`，mustache 占位 + `ChatPromptTemplate`；
- 模板里要求 JSON；提示词指纹进入发布检查；
- **改 YAML 要重启**，进程内缓存；换来的是「提示词变更不能静默上线」。

**取舍**：灵活性换可追溯性。要做热更新就得配版本化 + 门禁重跑。

### Q2.2 上下文怎么组装？

**展开**

- 检索默认 top5；多类/多成员按公平窗口分配证据；
- 父子块只回填**父块标题**做标签；命中短片段在同一 H2 内扩不超过 1200 字的窗口，不粘整章；
- 构造函数/概述优先；
- 输出 `confidence / emptyReason / evidence`，让下游知道「为什么空」。

**追问「为什么父块不粘整章」**：会上下文膨胀、稀释相关性；跨段语义让模型从多个 chunk 组合。

### Q2.3 怎么防 prompt 注入？

**一句话**：这个项目是文档问答，风险面主要是「文档内容里藏指令」，我们靠边界和输出侧约束。

**展开**

- 系统指令与检索内容分角色/分隔；
- 明确「上下文是资料不是指令」；
- 输出侧有领域守卫和确定性清洗，模型即使被带偏也过不了规则；
- 工具面（MCP）只读检索，没有写操作。

**防守**：不要说「我们完全防住了」，说「分层降低风险，没有银弹」。

## 3. RAG（主战场）

### Q3.1 讲一下你们的 RAG 全链路

**一句话**：不是「切块 → 向量 → topK → 拼 prompt」，每一环都有领域适配。

**展开**

```text
Markdown 结构解析 → 类/章节/成员切块 → 向量 + BM25 + 父块
→ 意图识别 → 查询计划 → 双路召回 → RRF → 精确置顶
→ 每类公平窗口 → 有界父块 → Prompt → JSON → 守卫 → 清洗
→ 引用 → SSE
```

**数字**：260 篇 / 9,366 chunks / 878 parents / 2,560 维。完整时间盒讲法见 [10-面试讲法](/03-项目实战/01-THINGJS文档RAG/10-面试讲法)。

### Q3.2 为什么不用固定长度切块？

**一句话**：ThingJS 文档是结构化 API 文档，按字符切会切坏代码和成员边界。

**展开**

- 用 `remark/mdast` 解析 H1 类名、H2 章节、H3 成员、行号；
- `ThingJSMarkdownSplitter` 保护代码围栏：同一 H2 内短 H3 合并，target 900 / max 1200 / overlap 150，不跨 H2；
- 超长代码按行切并补围栏，避免半截代码块；
- chunk_id 由 `sourceId + member + part + startLine + textHash` 决定，稳定可对比。

**追问「为什么 900/1200」**：H3 独立块太碎、H2 整章太大；同 H2 合并短成员到目标 900、上限 1200，长成员再拆，成员身份由 `member_names` / `symbol_spans` 保留。

### Q3.3 为什么要混合检索？

**一句话**：语义问题靠向量，精确符号靠 BM25，单路都会漏。

**展开**

- 口语：「盒子怎么变大」→ 向量；
- 精确：「THING.Box width」「PixelLine」→ BM25；
- 纯向量会丢符号，纯 BM25 会丢口语；
- 两路各 topN 28，并行召回。

**数字**：向量 28 / BM25 28 / final 5。

### Q3.4 RRF 是什么？为什么不用加权求和？

**一句话**：RRF 只用名次，天然解决「两路分不可比」。

**展开**

- `score = Σ 1/(60 + rank)`；
- 向量分和 BM25 分不在一个量纲；多路 BM25 的原始分也随查询长度变化；
- RRF 对「短查询但名次靠前」友好——精确符号查询原始分可能低，但名次第 1，融合后能保住；
- 用的是官方 `EnsembleRetriever`，没有手写 RRF 数学。

**追问「为什么 c=60」**：业界常用默认值，衰减足够平缓；靠黄金集验证，没有专门调。

### Q3.5 精确符号召回是第三路并行吗？

**一句话**：不是。并行的是向量 + BM25，精确符号是融合后的置顶/补位。

**展开**

- 精确符号按元数据查，不参与并行候选流；
- 用途：把精确命中的类/成员放到头部，或在窗口不足时补位；
- 多类问题每个类单独一路「类名 + 构造函数 概述」BM25，采纳时按类公平窗口。

**这是最容易被追问穿的一句，务必按这个口径说。**

### Q3.6 多类问题怎么保证每类都有？

**展开**

- 主查询会把类概述挤出窗口（真实失败案例 T07）；
- 给每个类补一路 BM25；
- 融合后按类公平窗口分配，每类都有名额；
- 结果：PixelLine/FatLine 进前 8。

**讲故事**：这是「先复现失败用例 → 改 → 用门禁验证」的典型。

### Q3.7 否定约束怎么处理？

**展开**

- 「不要用 flyTo」→ flyTo 进否定成员，从查询中剔除；
- 视点特例：Camera 当 actor、目标当 target；
- position 置顶、lookAt 补位；
- 证据筛选阶段也会按 actor/target 过滤。

### Q3.8 为什么不用 ANN / HNSW？

**一句话**：2 万级数据全表扫描更快，而且 ANN 会破坏可复现性。

**展开**

- 2 万行 × 2560 维实测约 90ms；
- ANN 冷查询约 1.2s，且训练有随机性，重建后 Top-K 顺序会变；
- 评测要求逐题对比 chunk_id 顺序，随机性会污染基线；
- 10 万+ 再评估。

**防守**：不要展开讲 HNSW 参数实践，你没在生产用过；可以讲原理。

### Q3.9 中文 BM25 怎么做的？

**一句话**：官方 `BM25Retriever` 中文不可用，换成 MiniSearch + jieba。

**展开**

- 官方实现按空白分词，中文整句一个 token，Top-5 全是噪声；
- MiniSearch 负责分词、倒排、BM25 打分；jieba HMM 负责中文切词；
- 项目只做多查询合并编排（不同长度查询原始分不可比）。

**数字**：9,366 条构建约 5s、持久化 22MB、加载 0.4s、查询 7–16ms。

### Q3.10 文档更新怎么办？

**一句话**：指纹 + 子进程构建 + active 指针原子切换 + 门禁回滚。

**展开**

- chokidar 监听 md 和 assets，5s 去抖；
- 先比指纹（mtime+size + aliases 内容 hash），没变跳过；
- 变了加发布锁，子进程构建/校验/激活，父进程**加载成功才替换 runtime**；
- 配置了门禁就跑 `eval:publish-gate`，失败回滚 `active.json` 并热加载旧版；
- 多实例只让一个构建，其余轮询指针。

**数字**：去抖 5s、冷却 2.5s、门禁超时 300s、保留 5 版。

### Q3.11 增量索引怎么复用向量？

**展开**

- 文件 hash 未变的 chunk，按稳定 chunk_id 复用上一版向量；
- 切块指纹或维度不一致 → 全量重建；
- chunk_id 未变的部分，评测可以逐题对比。

**数字**：`chunkingFingerprint = md-h2-merge-h3-900-1200-v4-symbol-spans`；活动索引 9,366 chunks / 878 parents。

### Q3.12 怎么证明检索变好了？

**一句话**：100 题黄金集 + 确定性指标 + 基线 + 门禁，全量跑。

**展开**

- 指标：Class Hit@1/3/K、Member Hit@1/3、MRR、false-empty、禁止类命中；
- 按 tag 分层：class / member / colloquial / typo / mixed / negative；
- 门禁：绝对阈值 + 与基线逐项对比；子集只能排查，不能当门禁；
- 最近：94/94、Member 26/26、false-empty 0。

**防守**：「94/94 的分母是 94 道可回答题，不是 100。」

### Q3.13 生成怎么评？

**展开**

- 确定性：schema、confidence、引用合法且不指向 discarded、类/成员提及、mustMention/mustNotMention、代码块、路径脱敏、内部路径、负例、模板跳过、guard、阈值误伤；
- LLM 裁判：独立模型、温度 0、看问题/回答/引用/retrieved，打 grounded/answers/citation，判 hallucination；
- 12 条人工样本校准；
- 门禁：全量 + 裁判全覆盖，judgePass ≥ 80%、幻觉 0。

**数字**：历史通过 24/24、judgePass 95.8%；最近一次 23/24、judgePass 91.3%、幻觉 0，被门禁拦截并进入闭环。

### Q3.14 裁判会不会有偏差？怎么防？

**展开**

- 独立模型，不用被测模型；
- 温度 0、固定 prompt、12 条人工校准样本；
- judgePass 基线允许 1 个样本波动；
- 局限性主动说：仍是采样判断，不是线上全量。

### Q3.15 用户说答不出来，你怎么查？

**一句话**：先判断是召回问题还是生成问题。

**展开**

1. traceId → 阶段耗时；
2. 看 `retrieved`：正确 chunk 在不在 top-k；
3. 不在 → 切块/embedding/改写/混合检索/过滤；
4. 在但答错 → 上下文太杂、截断、prompt、模型；
5. 都正常 → 超出知识库，应该拒答；
6. 能用重放复现，能建回归用例。

**数字**：每次调用都有 trace、证据、prompt 版本；重放同一 trace 1 个、全局 2 个。

### Q3.16 怎么处理多轮？

**展开**

- HTTP 无状态，历史由客户端传（12 条 × 4000 字）；
- 有历史先用 `rewrite.yaml` 改成独立问句；
- 失败回退原问句并记录原因；
- 服务端会话历史是另一套表，用于跨浏览器恢复，不是 LangChain memory。

**追问「为什么不用 RunnableWithMessageHistory」**：契约无状态，引入服务端消息历史会和前端窗口、鉴权归属、保留周期重叠。

### Q3.17 文档冲突怎么办？

**一句话**：契约和提示词有优先级策略，但 `conflicts` 字段还没生成——这是已知限制。

**展开**

- api / editor / example / project 有优先级和并列策略；
- 当前检索链未生成 `conflicts`，是下一步；
- 不假装已上线。

## 4. Agent / LangGraph（诚实转场）

### Q4.1 你们为什么不用 Agent？

**一句话**：这是固定检索-生成链路，Agent 只会增加不确定性和延迟。

**展开**

- 文档问答的步骤是确定的：理解 → 检索 → 生成；
- 没有「需要根据中间结果决定下一步」的分支；
- Agent 的代价：多轮模型调用、成本、延迟、不可复现、难评测；
- 结论：能确定性编排就不用 Agent。

**这是反向题，答对了加分。**

### Q4.2 那你了解 LangGraph 吗？

**一句话**：了解，但不是在 ThingJS 项目里用的。

**展开**

- 核心：`StateGraph` + reducer 管理状态，条件边路由，checkpointer 持久化，`interrupt` 做人工确认；
- 我在另一个多轮业务助手里用过：Postgres checkpoint、跨重启恢复、工具调用循环；
- 这个项目没有引入 LangGraph，主链路是显式 `runChat` + LCEL；需要状态机时再按需引入，避免过度设计。

**防守**：准备好被追问 `add_messages`、`thread_id`、`get_state_history`、streaming modes；答不上就承认「细节我要查文档」，不要编。

### Q4.3 MCP 你们怎么用的？

**一句话**：把检索和问答暴露成两个 MCP 工具，Streamable HTTP。

**展开**

- `search_thingjs_docs`、`ask_thingjs_docs`；
- 会话登记到 SQLite，记录用户/部门/工具/在途数；
- `MCP_AUTH_REQUIRED` 控制鉴权；关闭时统一 closeAll；
- MCP 是「工具接入标准化」，不是 Agent 编排。

### Q4.4 多 Agent 怎么设计？

**一句话**：本项目没有；给方案 + 说代价。

**展开**

- supervisor / handoff / planner-executor / critic；
- 代价：token 数倍、错误级联、调试难；
- 只有子任务边界清晰、可并行、工具差异大时才值得；
- 不要为了架构感上多 Agent。

## 5. 工程化

### Q5.1 并发和限流怎么做的？

**展开**

- 检索 8 并发 / 队列 256；生成 4 并发 / 队列 64；
- 队列满返回 429/503，超时 504；
- 限流：检索 120/min、问答 30/min、登录 20/min；
- 模型调用重试 2 次（含首次，`RunnableRetry`），连续 5 次失败熔断 30s。

**防守**：限流是**进程内单机**，多实例要外置。

### Q5.2 客户端断开怎么办？

**一句话**：AbortController 一路 abort 到底。

**展开**

- 客户端断开 → abort 检索/生成；
- 服务关闭 → 先 abort 在途 → 关 SSE → 有界关闭 HTTP → drain 3s → 15s 强退；
- 错误码区分 `client_aborted` 和真正的失败。

### Q5.3 怎么做类型契约？

**展开**

- 服务端 Zod 定义请求/响应；
- 前端、评测平台各自校验响应形状，**不共享实现**；
- 统一 `{ ok, code, error, traceId }`；
- 错误码细分：schema / unauthorized / login_required / session_expired / quota_exceeded / rate_limited / queue_full / chat_busy / client_aborted / server_shutdown / index_not_ready / index_embedding_mismatch。

**为什么**：前端要区分登录过期、配额、限流、队列满，不能都当 500。

### Q5.4 为什么评测平台单独一个进程？

**展开**

- 服务端只负责在线链路；
- 评测需要黄金集、裁判、报告、问题队列、发布检查，生命周期不同；
- 独立进程强制「只通过 HTTP 契约」，能真正发现契约问题。

### Q5.5 有状态服务怎么扩展？

**一句话**：当前是单机，扩展路径清楚但没做过。

**展开**

- 会话、限流、队列、SQLite 都要外置到 Redis/Postgres；
- 索引对象存储 + 构建任务队列；
- 多实例共享 active 指针；
- 不要声称做过分布式。

### Q5.6 成本怎么控制？

**展开**

- 生成并发 4、队列 64，防止瞬时打爆；
- 问题上限 1000 字、历史 12×4000、引用上限 3；
- 熔断避免持续失败烧钱；
- 可以坦白：项目内没有做按租户 token 计费，这是可以补的。

## 6. 评测与可观测

### Q6.1 你们的质量体系是什么？

**一句话**：黄金集 + 确定性指标 + 独立裁判 + 基线 + 三套门禁 + 发布检查。

**展开**

- 100 题检索、30 题生成、12 题裁判校准；
- 检索门禁 + 生成门禁 + 回归门禁；
- 发布检查聚合门禁 / P0/P1 / 点踩率 / 空结果率 / P95；
- 门禁过期：索引版本、fixture hash、提示词指纹任一变化即过期。

**数字**：94/94；生成历史 24/24、judgePass 95.8%、幻觉 0，最近一次 23/24 被拦截并进入闭环；门禁确认绑定 configVersion，版本变化后 stale。

### Q6.2 线上出问题怎么定位？

**展开**

- traceId → 阶段耗时瀑布；
- 看 `retrieved / citations / discarded / answerGuard`；
- 能复现就重放（新 trace + `replayOf` 指原记录）；
- 点踩自动建问题单，指纹去重；
- 问题关闭必须有回归用例 + 验证通过。

### Q6.3 重放会复制旧回答吗？

**不会**。按原问题和历史重新检索/生成，新 trace，`replayOf` 指原记录。这样能验证「现在修好了没有」。

和旧项目比：旧项目是 `/ops/api/turns/:traceId` 只读审计 + 评测侧固定回放（历史答案和 retrieved 写进测试），没有运行时重放入口；当前项目补了 `POST /ops/api/calls/:traceId/replay`，用当前索引/提示词/模型重跑同一问题，并在详情里并排对比回答、置信度、延迟、证据和新增/消失的 chunk。固定回放防回归，运行时重放回答「现在修好了没有」。

### Q6.4 日志会不会泄漏密钥？

**展开**

- pino 脱敏 Authorization / token / API key / JWT / LDAP 密码；
- prompt 正文不进日志；
- `.env` 不提交、不打印、不写报告；
- 备份不含 `.env`。

## 7. 选型与语言

### Q7.1 为什么用 LangChain？

**一句话**：把通用能力换成成熟实现，自研只补领域缺口。

**展开**

| 能力 | 用法 |
| --- | --- |
| 文档加载 | `DirectoryLoader` + `TextLoader` |
| 切分 | `TextSplitter` 基类 + 代码围栏薄适配 |
| 模型/Embedding | `ChatOpenAI` / `OpenAIEmbeddings` |
| 向量库 | `@langchain/community` LanceDB |
| 融合 | `EnsembleRetriever`（RRF） |
| Prompt | `ChatPromptTemplate` + `MessagesPlaceholder` |
| JSON | `JsonOutputParser` + Zod + `jsonrepair` |
| 重试 | `RunnableRetry` |
| 回调 | `BaseCallbackHandler` |
| 检索接口 | `BaseRetriever` / `InMemoryStore` |

**自研边界**：`ThingJSMarkdownSplitter`、LanceDB filter 补丁、BM25 多查询编排、查询计划/别名/否定/视点、证据守卫/清洗、引用重排、父块有界回填、发布编排。

**关键句**：「每个自研都有失败用例和记录，不是拍脑袋重写。」

### Q7.2 为什么锁 LangChain 0.3 不上 1.x？

**展开**

- 0.3 的 LCEL、组件、行为是当前基线；
- 1.x 把 agent 抽象迁到 LangGraph 之上，包结构拆分，迁移面不小；
- 当前没有用到被移除的 agent 封装，但升级要重跑全部门禁；
- 结论：先锁版本保证可复现，升级作为独立迁移决策。

### Q7.3 你是 TS 为主，Python 只做过一个，怎么看？

**一句话**：按服务栈选型，训练/微调类任务单独用 Python。

**展开**

- TS 优势：Web 服务、流式、类型契约、前后端同栈、部署统一；
- Python 优势：训练、微调、评测、数据生态；
- 我们的做法：线上 TS，离线需要 HuggingFace/训练的部分单独 Python；
- 代价：两边 LangChain 版本线和 API 不完全对齐，不能照抄示例。

**防守**：不要说「TS 也能做 AI」这种空话；给具体分工。

### Q7.4 为什么不微调？

**展开**

- 文档更新频繁，微调知识会过期；
- 需要引用和可解释，RAG 天然带证据；
- 幻觉要可控，规则和评测比权重更可验证；
- 微调适合风格/格式/小模型提效，是后续补充，不是替代。

## 8. 场景与设计题

### Q8.1 如果数据涨到 100 万 chunk？

**展开**

1. 向量：全表扫描改 ANN（HNSW/IVF），接受近似排序，评测改用指标而非逐 chunk 顺序；
2. BM25：单机 MiniSearch 换外置搜索引擎或分片；
3. 索引：版本目录 + 对象存储，构建任务队列化，多实例共享 active 指针；
4. 会话/限流/队列外置。

**防守**：说「这是方案，不是实践」。

### Q8.2 设计一个流式 RAG 接口

**答法**：直接映射本项目：

```text
POST /api/chat
→ 鉴权/配额预检
→ 改写（可选）
→ 检索（意图 → 计划 → 双路 → RRF）
→ SSE: phase(retrieving) / delta / reset / done / error
→ done 里带完整 answer + citations + timings + traceId
```

### Q8.3 怎么把点踩变成改进？

**展开**

点踩 → 自动建问题（指纹去重）→ 生成回归用例 → 单题验证 → 关闭门禁（必须有回归用例 + 最近一次通过）→ 发布检查聚合 P0/P1。

**关键句**：「反馈不是一条记录，是一个有状态机的工单。」

### Q8.4 最大的难点是什么？

**答法**（建议讲「检索质量 + 可回归」）：

> 「最难的不是把链路跑通，而是让检索在口语、错拼、多类、否定这些真实问法上稳定，并且每次改动都能证明没退化。我们做了查询计划、别名、多路 BM25、RRF、精确置顶、父块，再用 100 题黄金集 + 基线 + 门禁把每一步锁住。」

### Q8.5 最大的技术债是什么？

主动列，显得可信：

- 单机限流/会话/索引；
- 提示词不热更新；
- `conflicts` 未生成；
- `minFusionScore` 未启用。

## 收尾与反问

### 收尾句

> 「这个项目对我来说最大的价值，不是把 RAG 跑通，而是把它做成了一个可回归的工程系统：每次改检索、改提示词、改文档，都有黄金集、门禁和发布检查告诉我有没有退化；线上每次回答都有 trace、证据和问题闭环可以追。」

### 反问（按岗位选）

- 「团队现在的 RAG 评测是怎么做的？有没有黄金集和门禁？」

- 「模型和检索的变更走什么发布流程？」
