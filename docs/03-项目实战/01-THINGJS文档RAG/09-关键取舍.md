# THINGJS 文档 RAG · 关键取舍
> 一句话定位：复用优先，自研只补 ThingJS 领域规则和框架缺口；每一条取舍都说清“为什么不用另一种”和代价。

## 取舍总原则

项目的硬约束是：**LangChain 0.3 官方组件能满足契约就直接用；没有现成组件，先选成熟库；只有领域规则和框架缺口才自研。**

决策记录在 `server/plans/reuse-decisions.md`，缺口记录在 `server/docs/framework-gaps.md`。

下面 16 条是实现里真正做过的选择，按“选择 → 为什么不用另一种 → 代价/边界”组织。面试时不要只报结论，要能说出被放弃方案的缺点。

## 1. 复用优先：通用能力不自研

**选择**：文档遍历/加载用 LangChain `DirectoryLoader` + `TextLoader`；Markdown 解析用 `unified` + `remark-parse` + `mdast`；文本切分用 `TextSplitter` 薄适配；Embedding/Chat 用 `OpenAIEmbeddings` / `ChatOpenAI`；向量库用 `@langchain/community` LanceDB；BM25 用 `minisearch` + `@node-rs/jieba`；融合用 `EnsembleRetriever`；Prompt 用 `ChatPromptTemplate` + `MessagesPlaceholder`；JSON 解析用 `JsonOutputParser` + Zod + `jsonrepair`；模型重试用 `RunnableLambda.withRetry`；回调/trace 用 `BaseCallbackHandler` + pino + AsyncLocalStorage；队列/熔断用 p-queue + cockatiel；限流用 express-rate-limit；JWT/LDAP 用 jose + ldapts；SQLite 用 better-sqlite3；文件锁/原子发布用 proper-lockfile + fs.rename；文件监听用 chokidar；MCP 用官方 SDK。

**为什么不用另一种**：手写 Markdown 解析器、BM25 打分、倒排索引、RRF 数学、文件遍历、重试/队列/熔断、SQLite 封装、日志框架、JWT/LDAP 协议，都会把通用问题变成自维护代码；项目真正需要自研的是 ThingJS 语义，而不是基础设施。

**代价/边界**：代码量小、升级路径清楚，但受框架版本约束；每个自研缺口必须有失败用例和记录，不能拍脑袋重写。

## 2. 自研 `ThingJSMarkdownSplitter`，不用 `RecursiveCharacterTextSplitter`

**选择**：保留一个 LangChain `TextSplitter` 薄适配，先拆「文本原子」和「代码围栏原子」，再按 900/1200 装箱，只有强制拆开同一 unit 时才 overlap 150。

**为什么不用另一种**：`RecursiveCharacterTextSplitter` 没有「先保护代码围栏再装箱」的组件。旧参数下实测会把 60 行代码块切成 4 片，中间 2 片围栏数为 0；也无法复现成员内装箱和续接规则。直接按分隔符切会把代码切断，回答里就会出现半截示例。

**代价/边界**：需要自己维护切分器和 dry-run 对比；验证手段是 `splitter-gap.test.ts` + 全量 dry-run 与旧索引 `chunk_id/parent_id/text_hash/search_text_hash/images_json` 差异 0。

## 3. 给 LanceDB 补过滤方法，不用官方 `similaritySearch` 的 filter

**选择**：继承 LangChain 官方 LanceDB 集成，复用写入、schema 推断、元数据映射；额外实现 `searchVectorWithFilter()` 和 `findByFilter()`，把过滤条件下推成 LanceDB `where`。

**为什么不用另一种**：官方 `similaritySearch` 忽略 `filter`，实测过滤后仍返回全表结果；如果直接依赖它，类名/来源过滤会失效，精确符号召回和目录文件命中都会脏。

**代价/边界**：多了一层薄封装，需要自己测过滤语义；但写入和映射仍然是官方实现，没有复制整套向量库。

## 4. 中文 BM25 换 MiniSearch + jieba，不用官方 `BM25Retriever`

**选择**：MiniSearch 负责分词、倒排、BM25 打分，jieba HMM 负责中文切词；项目只做多查询合并编排。

**为什么不用另一种**：官方 `BM25Retriever` 用 `toLowerCase().split(/\s+/)`，中文整句变成一个 token，实测 Top-5 全是噪声。中文文档检索不能靠空白分词。

**代价/边界**：分词器从旧项目的 `cjk-bigram+identifier-v1` 换成 `jieba-hmm+identifier-v1`，检索结果不保证与旧索引逐 chunk 一致；兜底是用黄金集看质量指标，manifest 如实记录 tokenizer。

## 5. 多查询融合用官方 `EnsembleRetriever` 做 RRF，不手写 RRF、不直接加原始分

**选择**：多条 BM25 查询各自打分后，用官方 `EnsembleRetriever`（`c=60`，权重全 1）做 RRF；向量 + BM25 两路也用它融合。

**为什么不用另一种**：向量分和 BM25 分不在一个量纲；不同长度查询的原始 BM25 分也不可比。直接相加会让长查询或高分路支配结果。RRF 只用名次，对「短查询但名次靠前」的精确符号查询更友好。

**代价/边界**：官方 `EnsembleRetriever` 不暴露融合分，所以 `fusionScore` 只能置 null；这一点在第 7 条单独说明。

## 6. [重点] 不建 ANN，走 LanceDB 全表扫描

**选择**：`table.query().nearestTo(query).bypassVectorIndex()` 全表扫描，不建 IVF-PQ/HNSW。

**为什么不用另一种**：旧基线索引的 IVF-PQ 训练带随机性，重建后 Top-K 顺序不可复现，评测/基线对比会漂；2 万行 × 2560 维实测约 90ms，ANN 冷查询约 1.2s。数据规模还没到必须 ANN 的量级。

**代价/边界**：数据量继续增长（比如 10 万+）时需要重新评估；到那时要接受近似排序，并改用指标而不是逐 chunk 顺序做评测。

## 7. `fusionScore` 置 null，不自研融合层补分

**选择**：保留 `fusionScore` 字段但统一为 null；`minFusionScore` 阈值不启用。

**为什么不用另一种**：官方 `EnsembleRetriever` 只返回 `Document`，不暴露融合分。为了一个诊断字段手写 RRF，会把已经复用的融合逻辑又变成自维护代码，得不偿失。

**代价/边界**：诊断字段缺失；但顺序、`discarded`、`confidence`、`emptyReason` 仍可逐题对比，评测不依赖融合分。面试时不要把它讲成已上线的阈值能力。

## 8. [重点] 父块只补标题/有界窗口，不粘整章

**选择**：用 LangChain `InMemoryStore<ParentContext>` 存父块，检索命中短片段时只回填父块标题做标签，并在同一 H2 内扩不超过 1200 字的窗口（代码上限 1600）。

**为什么不用另一种**：`ParentDocumentRetriever` 会返回完整父文档，丢失子块 `chunk_id/rank/adoptReason/finalPosition`；整章塞进 prompt 会膨胀上下文、稀释相关性，还会把无关成员带进来。

**代价/边界**：上下文更短、更聚焦；但跨段的完整语义需要模型自己从多个 chunk 组合。父块存储仍用官方 `InMemoryStore`，没有自研存储。

## 9. [重点] 不用 `RunnableWithMessageHistory`，历史由 HTTP 显式传入

**选择**：`/api/chat` 接受 `history`（最多 12 条 × 4000 字符）；服务端会话历史是另一套表（`chat_sessions/chat_messages`），用于跨浏览器恢复，不是 LangChain memory。

**为什么不用另一种**：HTTP 契约是无状态的；引入服务端消息历史会和前端窗口、鉴权归属、保留周期重叠，还会让「一次请求用了哪些历史」变得不透明。

**代价/边界**：服务端不维护 LangChain 意义上的「当前会话窗口」；多轮改写仍可用显式 `history` 完成。好处是请求可复现、可重放、可审计。

## 10. [重点] 提示词不热更新

**选择**：`server/prompts/*.yaml` 进程内缓存，`promptVersion` 是文件内容 sha256 前 12 位；改 YAML 需重启。

**为什么不用另一种**：线上静默换提示词会让行为变化不可追溯，门禁也可能跑在旧版本上。把提示词当代码变更，走重启 + 重跑生成/回归门禁，换来可追溯性。

**代价/边界**：发布检查会检查门禁是否跑在当前提示词指纹上；想热更新就得配版本化 + 门禁重跑，当前刻意不做。

## 11. [重点] 在线只跑规则守卫，不在线跑 LLM 裁判

**选择**：在线做确定性规则（禁用词、Box 构造、动画、多对象、视点、默认值、路径），违规纠错一次；LLM 裁判放在评测平台离线跑。

**为什么不用另一种**：通用模型裁判不稳定、慢、不可复现；这些是 ThingJS 领域规则，规则可单测、可在评测里复现，适合放在强约束里。裁判的语义判断放在离线质量评估。

**代价/边界**：规则覆盖不到所有语义问题；所以还要 Prompt 约束、证据筛选、确定性清洗和离线裁判共同兜底。

## 12. [重点] 引用按正文反推，不全信模型 `citations`

**选择**：`citationsFromAnswer()` 按回答正文实际提到的类/成员给证据打分，多类问题每类取一条最佳片段，最多 3 条；正文没有可用引用时，才回退模型声明并校验 `chunk_id`。

**为什么不用另一种**：模型经常「引用了没说的」或「说了没引用」；直接信 `citations` 会出现引用和正文不对齐。按正文对齐更可信，也更容易在评测里检查。

**代价/边界**：引用上限 3 条，复杂多类问题可能引用不全；这是已知限制，可按类数动态调整。

## 13. [重点] 生成失败分级降级，不把致命错误伪装成降级

**选择**：只有非中止、非网关致命错误、非队列错误才降级为「返回检索片段」；鉴权/配额/限流/队列满/超时直接报错。

**为什么不用另一种**：把 401 当成「模型不可用」会把问题藏起来，用户看到的是降级答案，运维看到的是正常请求，真实故障被掩盖。

**代价/边界**：错误码更细、前端要分别处理；但可观测性和责任边界清楚。降级次数单独计入 `degraded` 指标。

## 14. [重点] 不引入 LangGraph

**选择**：主链路是显式 `runChat` + LCEL，不是状态图；`@langchain/langgraph` 已从依赖中移除。

**为什么不用另一种**：文档问答是固定的检索-生成链路，没有「需要根据中间结果决定下一步」的分支；引入状态机只会增加不确定性、延迟和调试成本。需要状态机时再按需引入，避免过度设计。

**代价/边界**：不能讲「LangGraph 实践」；如果面试官问 LangGraph，诚实说在另一个多轮业务助手里用过，不要把 LCEL 包装成 LangGraph。

## 15. 单机 Windows + SQLite + 文件会话，不引入 Redis/Postgres

**选择**：部署形态是单机内网；状态库用 better-sqlite3（WAL），会话文件落盘 `data/sessions` 并用 `WEB_SESSION_SECRET` 加密；限流是进程内。

**为什么不用另一种**：当前规模和交付环境不需要额外的中间件；引入 Redis/Postgres/对象存储会增加部署和运维成本，收益不明显。

**代价/边界**：水平扩展需要外置会话/限流/队列/存储；多实例时是单实例限流，不是全局限流。面试时要主动交代这个边界。

## 16. 评测平台独立进程，不做成服务端路由

**选择**：`review/` 独立 TypeScript 服务（9968），只通过 HTTP 调服务端，不 import 服务端实现。

**为什么不用另一种**：评测需要黄金集、裁判、报告、历史、问题队列、发布检查，生命周期和依赖都不同；如果做成服务端路由，评测代码会和服务端实现耦合，也容易偷偷 import 内部模块，发现不了契约问题。

**代价/边界**：多一个进程、多一套配置；但换来独立运行、独立扩展，以及「评测只通过 HTTP 契约」的强制约束。

## 不要过度声称

- 不要说「用了 LangGraph」——项目没有引入，主链路是 LCEL。
- 不要说「三路召回并行」——并行的是向量 + BM25；精确召回用于置顶/补位。
- 不要说「融合分阈值」——`fusionScore` 是 null，`minFusionScore` 未启用。
- 不要说「知识冲突检测已上线」——字段和提示词策略在，检索链未生成。
- 不要说「多实例全局限流」——限流是进程内。
- 不要说「提示词热更新」——需要重启。
- 不要说「100% 无幻觉」——门禁口径是这批黄金集 0 幻觉，不是所有问题。

## 已知限制与下一步

| 限制 | 影响 | 下一步 |
| --- | --- | --- |
| `conflicts` 字段未生成 | 多来源冲突检测还没上线，提示词策略已准备 | 在检索后做同 symbol 多 corpus 检测 |
| `minFusionScore` 未计算 | 不能按融合分卡阈值 | 若框架暴露融合分或自研薄融合层 |
| 引用上限 3 条 | 复杂多类问题可能引用不全 | 按类数动态调整 |
| 父块只补标题/有界窗口 | 跨段语义依赖多 chunk 组合 | 评估有界父块正文 |
| 提示词不热更新 | 改 prompt 要重启 | 可做版本化热加载 + 门禁 |
| 单机限流/会话 | 多实例需外置 | Redis/共享存储 |
| 评测裁判有采样波动 | judgePass 允许 1 样本容差 | 多次采样/更强裁判 |
| 知识库健康 3 个 warn | 当前口径 0 error / 3 warn | 按 `kb-health.md` §10 处置 |
| 代码排错不执行代码 | 只基于文档证据推断，不能验证运行时 | 需要执行沙盒/日志接入 |
| 覆盖集仍有未覆盖类 | 204/255 类、API 100%；目录含 README/示例标题 | 按 `golden:audit` 补题 |
