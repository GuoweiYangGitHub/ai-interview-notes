# THINGJS 文档 RAG · 面试题

## Q01 用 3 分钟介绍这个项目

ThingJS 文档问答系统面向官方文档和示例代码，网页助手和编辑器通过工具协议共用一套检索、生成链路。 文档按 Markdown 结构和代码语法树切分，保留类 / 成员身份和父块；检索走**向量 + 关键词检索**，用**排名融合**把两路结果合并，再做**精确符号置顶**、类 / 成员采纳和**父块回填**；生成用 YAML 提示词 + LangChain 表达式，做证据筛选、领域守卫和引用校验。 索引按文件内容指纹增量构建，索引清单校验后切激活指针；文档改动可热更新，发布门禁失败回滚。评测有 100 题检索集、30 题生成集和 12 题自动评审校准，另加覆盖集、真实问法和代码题；三套门禁绑定配置版本。 我负责前端、检索、生成和评测。三句话：**切片不是固定长度**；**混合检索同时解决语义和精确符号**；**引用检查只能保证引用真实存在，不能保证引用支持结论**。

## Q02 用一分钟讲清这个 RAG 项目。你的工作做到了哪一层？

**答题要点**

- 面向 ThingJS API 文档；网页助手和编辑器 MCP 共用索引与检索链路。
- 我负责文档切片、混合检索、证据选择、引用检查、索引发布，以及检索与回答质量评测和请求回放。
- 例子：「摄像机看向某点」这类口语，要先找到 `Camera` 和 `lookAt`，再根据原文给出用法与引用。

**加分句**

> 我不是只做了“检索 + 调模型”，而是把索引发布、证据链、评测门禁和问题闭环都做成了可回归的工程系统。

## Q03 API 文档为什么按类和成员切片？改一个切块参数会怎样？

**答题要点**

- API 的签名、说明和示例通常围绕同一个成员组织；先按成员切，可以让这组信息留在同一片段里。
- 超过 800 字的同一成员再分段，相邻段目标重叠 200 字，尽量保持代码块完整。
- 切块参数进入指纹；参数变化后需要重新生成向量索引，因为片段内容和边界都可能变了。
- 当前活动索引已切到 target 900 / max 1200 / overlap 150；`800/200` 是旧 H3 基线。详见本题要点。

## Q04 向量和 BM25 各解决什么？为什么用 RRF？

**答题要点**

- BM25 适合匹配明确的 API 标识符；向量补足中文口语和语义接近的表达。
- 两路原始分数的含义不同，RRF 用各自的排名计算贡献，再把同一片段的贡献相加；两路都排得靠前的片段会得到更高分。
- 这个融合按排名工作，原始分数差距不参与计算；实现用 LangChain 官方 `EnsembleRetriever`，没有手写 RRF 数学。

**加分句**

> RRF 之后还要做片段选择：融合决定候选顺序，多类配额决定哪些候选最终进入模型上下文。

## Q05 用户写错了类名，为什么选择规则纠错？会不会改错？

**答题要点**

- 使用别名表和类目录做扩展与近邻纠错，可以把规则的候选范围限定在已有 API，也省去一次模型调用。
- 纠错只在编辑距离 ≤2 且唯一命中时生效；并列时不猜，短词只接受显式 ThingJS 上下文中的相邻换位。
- 评测把口语、拼写错误和点名成员分开看，避免总体分数掩盖某类退步。
- 排查误改时，比较原始问句、纠错结果、两路候选和最后采用的证据，判断是扩展带偏还是排序出了问题。

**加分句**

> 规则纠错最大的优势是可解释：每一步都能在 trace 里看到原词、候选、命中的别名或类名。

## Q06 同时问 Box、Sphere 和 Cylinder，为什么明明召回了三个类，答案还是漏一个？

**答题要点**

- 目标类可能在融合列表里，但没有进入生成上下文；直接取前几条时，高排名的某一个类可能占满名额。
- 项目对多类问题按类分配片段、轮流选取，同一类里优先保留点名成员；D 源口径是每类最多 3 条，当前实现以响应 `effectiveTopK` 为准。
- 排查时先看每一路召回，再对比融合列表和实际采用列表，确认漏在哪一步。

**加分句**

> 这是“先复现失败用例 → 改 → 用门禁验证”的典型：T07 五类创建问句暴露后，才给每个类补一路「类名 + 构造函数 概述」BM25。

## Q07 有引用就说明答案可信了吗？引用检查能保证什么？

**答题要点**

- 运行时先确认引用指向本轮真正送进模型的证据，已丢弃的片段不能被引用；这一步验证出处是否有效。
- 句子里的事实是否由该证据支持，还要对照内容检查；引用合法 ≠ 答案正确。
- 固定题集通过规则和 LLM 裁判分别检查引用、回答依据和相关性。

## Q08 什么时候拒答？模型服务挂了又该怎样？

**答题要点**

- 目录外类名等情况可以直接返回空结果；筛选后没有可用证据时，说明资料不足并跳过生成。
- 已有有效证据但生成服务故障时，可以降级返回检索片段。
- 两种情况需要分别记录，便于区分资料缺失和生成服务不可用。
- 关键边界：鉴权/配额/队列错误不伪装成降级，见本题「降级」要点。

## Q09 你说的两套黄金集是哪两套？“生成”指自动出题吗？

**答题要点**

- 按评测环节分：检索黄金集 100 题，标注预期 API 类、成员或负例，用来检查目标证据有没有找到；检索题在脚本里维护，再输出为 JSON。
- 回答生成黄金集 30 题，其中 24 道预期回答、6 道预期空结果，题目由手写维护，包含引用、必提术语、代码块或参考事实等预期。
- “生成”指模型产出的回答，不是自动出题；口语、拼写错误、成员等是各题集内部的题型标签。
- 完整夹具见本题要点。

**加分句**

> “摄像头如何看向某个物体”这类检索题要找到 `Camera.lookAt`；回答评测还要进一步核对用法有没有答对、引用能否支持回答。

## Q10 检索怎么打分？总命中率很高就能发版吗？

**答题要点**

- 类命中看预期类是否进入计分窗口；成员命中在要求成员的题里，看预期类和成员是否同时进入前 3 条。
- 误空用于发现文档有答案却返回空的情况；还会按口语、成员和拼写等分层看指标，防止总体分数掩盖某类退步。
- 报告里有不同的 Hit@K 指标；解释发版门槛时，按实际计分窗口和题目分母说明。
- 高命中率不等于能发版：还要看基线对比、生成门禁、回归、P0/P1 和发布阈值。详见本题要点。

## Q11 为什么用 LLM 裁判？怎样降低评分波动？

**答题要点**

- 结构、引用是否有效、是否包含必提内容，可以先做规则检查。
- 回答是否切题、事实是否来自证据、引用是否支持对应说法，再交给裁判模型。
- 用固定题集、参考事实、统一评分规则和低温度保持可比性；当前裁判温度 0，12 条人工样本校准。
- 遇到关键题分数变化，回看问题、证据、回答和判分理由，必要时人工核对。

## Q12 一篇文档改了，怎么增量建索引并安全发布？

**答题要点**

- 通过文件指纹识别变更，未变文件复用已有向量。
- 候选索引单独构建，构建期间服务继续使用旧版。
- `publish:index` 在构建后校验并激活候选索引，再通知服务热加载。
- 启用的检索与生成门禁随后通过服务运行；未通过时，脚本在有可用旧版本的情况下重新激活旧版并尝试热加载。
- 面试时把索引结构校验、切换和质量门禁这三个步骤分开讲；更换 Embedding 模型或切块规则时，按新配置重建。
- 完整发布流程见本题要点。

## Q13 网页和编辑器共用知识库，MCP 的 API Key 能隔离客户文档吗？

**答题要点**

- API Key 控制调用资格并按 Key 记录用量；网页和编辑器共用检索链路，网页有独立的日 token 池。
- 当前语料的来源标记用于追溯，文档级 ACL 尚未实现。
- 如果需要按客户或产品线隔离，服务端要在检索阶段强制限定可见范围，而不是只靠 Key 区分。

**加分句**

> 不要把“有 API Key”说成“有文档级权限”；当前是调用资格和用量隔离，不是语料级隔离。

## Q14 线上空答突然增加，怎么排查？评测流量算进去吗？

**答题要点**

- 先在运维页按网页、MCP 和评测流量分开看；评测调用带 `source=eval` 标记，不应混进生产空答率。
- 挑一条空答回放，检查问句分类、查询改写、候选片段、最终采用和置信状态。
- 再对照索引版本、Embedding 或生成服务的健康情况。
- 先确认空答是预期拒答、召回问题还是下游故障，再决定调整规则、索引还是服务。

## Q15 给你一份评测报告，怎么解释检索分母、负例和裁判分歧？

**答题要点**

- 先确认是全量还是子集，使用哪个题集和评分版本。
- 严格类命中按本题实际采用窗口检查预期类，多类题要看全部预期类。
- 严格成员命中只评有成员要求的题，核对同一片段上的类名和成员名是否同时匹配。
- 缺必要元数据的题单列为无法评分；负例检查是否正确拒答；HTTP 错误或坏 JSON 作为执行错误记录。
- 若人工和裁判意见不一致，先回看题目、参考事实、实际证据、答案和评分理由，再判断是裁判规则需要校准，还是系统本身有问题。

**加分句**

> 字段叫 `classHitAt8`，不能直接当严格 Top 8 指标；报告保留了旧字段，讲严格评分时要看 `effectiveTopK`、严格指标和对应分母。

## Q16 Embedding 压测写了 1024 并发，连接池为什么只有 32 条连接？整个问答也能跑到这个量吗？

**答题要点**

- 1024 指客户端同时发起的请求数，连接池最多使用 32 条长连接，其余请求在客户端排队。
- 留档中这个档位两组测试都得到 2048/2048 成功，测量范围是短中文问句调用 `Qwen3-Embedding-4B` 返回向量。
- 要评估完整问答容量，需要分别测 Embedding、双路检索和生成，再做端到端压测。
- 报告时同时给成功数、等待时限和延迟。

**加分句**

> 不要把 Embedding 的并发数字直接说成“问答 QPS”；两者测的不是同一个东西。

## Q17 磁盘上已激活新版，但热加载报错。现在到底哪一版在服务？怎么处理？

**答题要点**

- 先分别查磁盘上的 active 指针和进程当前加载的版本；指针可能已经指向新版，进程仍持有旧版。
- 用服务返回的 `indexVersion` 或运维信息确认实际版本，再结合热加载日志决定重试加载，或重新激活已知可用的旧版后再加载。
- 恢复后用实际检索响应核对；发布脚本用文件锁串行化发布。
- 若还需要保证候选索引覆盖了构建期间的新变更，要另外核对文档版本并安排重建。

**加分句**

> 门禁失败和热加载失败不是一回事：当前脚本在热加载失败时退出；质量门禁失败有单独的回滚路径，会在可用时恢复旧指针并尝试重载。

## Q18 换了 Embedding 模型但维度没变，旧向量能复用吗？服务启动时怎么检查？

**答题要点**

- 相同维度只能说明向量长度一样；换模型后，查询向量和旧文档向量的语义空间可能不一致，应该按新模型重建文档向量。
- 项目按 Embedding 模型管理索引 profile，校验时对照 manifest 与环境配置里的模型、维度和 query instruction 配置，再抽查索引里的向量与检索数据。
- 实际排查还要确认上游模型别名指向哪个模型。

**加分句**

> “维度一致”是必要检查，不是复用依据；真正的复用条件是模型、维度、切块指纹都一致。

## Q19 单机磁盘坏了，哪些数据需要恢复，哪些可以重建？怎么验收？

**答题要点**

- 先分两类：请求和回放记录在 `rag.sqlite`，需要恢复已有备份；项目备份还保存别名和激活指针。
- 索引可在有原始文档、切片配置和 Embedding 模型的情况下重建，也可以从另有留存的索引制品恢复；激活指针指向的版本必须实际存在。
- 验收先验证 SQLite 备份，再检查当前索引版本、模型配置和可用性，实际跑一条检索和一条历史回放。
- 备份/恢复命令与校验见本题要点。

## Q20 这个项目的取舍总原则是什么？

项目的硬约束是：**LangChain 0.3 官方组件能满足契约就直接用；没有现成组件，先选成熟库；只有领域规则和框架缺口才自研。**

决策记录在 `server/plans/reuse-decisions.md`，缺口记录在 `server/docs/framework-gaps.md`。

下面 16 条是实现里真正做过的选择，按“选择 → 为什么不用另一种 → 代价/边界”组织。面试时不要只报结论，要能说出被放弃方案的缺点。

## Q21 为什么复用优先：通用能力不自研？

**选择**：文档遍历/加载用 LangChain `DirectoryLoader` + `TextLoader`；Markdown 解析用 `unified` + `remark-parse` + `mdast`；文本切分用 `TextSplitter` 薄适配；Embedding/Chat 用 `OpenAIEmbeddings` / `ChatOpenAI`；向量库用 `@langchain/community` LanceDB；BM25 用 `minisearch` + `@node-rs/jieba`；融合用 `EnsembleRetriever`；Prompt 用 `ChatPromptTemplate` + `MessagesPlaceholder`；JSON 解析用 `JsonOutputParser` + Zod + `jsonrepair`；模型重试用 `RunnableLambda.withRetry`；回调/trace 用 `BaseCallbackHandler` + pino + AsyncLocalStorage；队列/熔断用 p-queue + cockatiel；限流用 express-rate-limit；JWT/LDAP 用 jose + ldapts；SQLite 用 better-sqlite3；文件锁/原子发布用 proper-lockfile + fs.rename；文件监听用 chokidar；MCP 用官方 SDK。

**为什么不用另一种**：手写 Markdown 解析器、BM25 打分、倒排索引、RRF 数学、文件遍历、重试/队列/熔断、SQLite 封装、日志框架、JWT/LDAP 协议，都会把通用问题变成自维护代码；项目真正需要自研的是 ThingJS 语义，而不是基础设施。

**代价/边界**：代码量小、升级路径清楚，但受框架版本约束；每个自研缺口必须有失败用例和记录，不能拍脑袋重写。

## Q22 为什么自研 `ThingJSMarkdownSplitter`，不用 `RecursiveCharacterTextSplitter`？

**选择**：保留一个 LangChain `TextSplitter` 薄适配，先拆「文本原子」和「代码围栏原子」，再按 900/1200 装箱，只有强制拆开同一 unit 时才 overlap 150。

**为什么不用另一种**：`RecursiveCharacterTextSplitter` 没有「先保护代码围栏再装箱」的组件。旧参数下实测会把 60 行代码块切成 4 片，中间 2 片围栏数为 0；也无法复现成员内装箱和续接规则。直接按分隔符切会把代码切断，回答里就会出现半截示例。

**代价/边界**：需要自己维护切分器和 dry-run 对比；验证手段是 `splitter-gap.test.ts` + 全量 dry-run 与旧索引 `chunk_id/parent_id/text_hash/search_text_hash/images_json` 差异 0。

## Q23 为什么给 LanceDB 补过滤方法，不用官方 `similaritySearch` 的 filter？

**选择**：继承 LangChain 官方 LanceDB 集成，复用写入、schema 推断、元数据映射；额外实现 `searchVectorWithFilter()` 和 `findByFilter()`，把过滤条件下推成 LanceDB `where`。

**为什么不用另一种**：官方 `similaritySearch` 忽略 `filter`，实测过滤后仍返回全表结果；如果直接依赖它，类名/来源过滤会失效，精确符号召回和目录文件命中都会脏。

**代价/边界**：多了一层薄封装，需要自己测过滤语义；但写入和映射仍然是官方实现，没有复制整套向量库。

## Q24 为什么中文 BM25 换 MiniSearch + jieba，不用官方 `BM25Retriever`？

**选择**：MiniSearch 负责分词、倒排、BM25 打分，jieba HMM 负责中文切词；项目只做多查询合并编排。

**为什么不用另一种**：官方 `BM25Retriever` 用 `toLowerCase().split(/\s+/)`，中文整句变成一个 token，实测 Top-5 全是噪声。中文文档检索不能靠空白分词。

**代价/边界**：分词器从旧项目的 `cjk-bigram+identifier-v1` 换成 `jieba-hmm+identifier-v1`，检索结果不保证与旧索引逐 chunk 一致；兜底是用黄金集看质量指标，manifest 如实记录 tokenizer。

## Q25 为什么多查询融合用官方 `EnsembleRetriever` 做 RRF，不手写 RRF、不直接加原始分？

**选择**：多条 BM25 查询各自打分后，用官方 `EnsembleRetriever`（`c=60`，权重全 1）做 RRF；向量 + BM25 两路也用它融合。

**为什么不用另一种**：向量分和 BM25 分不在一个量纲；不同长度查询的原始 BM25 分也不可比。直接相加会让长查询或高分路支配结果。RRF 只用名次，对「短查询但名次靠前」的精确符号查询更友好。

**代价/边界**：官方 `EnsembleRetriever` 不暴露融合分，所以 `fusionScore` 只能置 null；这一点在第 7 条单独说明。

## Q26 为什么不建 ANN，走 LanceDB 全表扫描？

**选择**：`table.query().nearestTo(query).bypassVectorIndex()` 全表扫描，不建 IVF-PQ/HNSW。

**为什么不用另一种**：旧基线索引的 IVF-PQ 训练带随机性，重建后 Top-K 顺序不可复现，评测/基线对比会漂；2 万行 × 2560 维实测约 90ms，ANN 冷查询约 1.2s。数据规模还没到必须 ANN 的量级。

**代价/边界**：数据量继续增长（比如 10 万+）时需要重新评估；到那时要接受近似排序，并改用指标而不是逐 chunk 顺序做评测。

## Q27 为什么`fusionScore` 置 null，不自研融合层补分？

**选择**：保留 `fusionScore` 字段但统一为 null；`minFusionScore` 阈值不启用。

**为什么不用另一种**：官方 `EnsembleRetriever` 只返回 `Document`，不暴露融合分。为了一个诊断字段手写 RRF，会把已经复用的融合逻辑又变成自维护代码，得不偿失。

**代价/边界**：诊断字段缺失；但顺序、`discarded`、`confidence`、`emptyReason` 仍可逐题对比，评测不依赖融合分。面试时不要把它讲成已上线的阈值能力。

## Q28 为什么父块只补标题/有界窗口，不粘整章？

**选择**：用 LangChain `InMemoryStore<ParentContext>` 存父块，检索命中短片段时只回填父块标题做标签，并在同一 H2 内扩不超过 1200 字的窗口（代码上限 1600）。

**为什么不用另一种**：`ParentDocumentRetriever` 会返回完整父文档，丢失子块 `chunk_id/rank/adoptReason/finalPosition`；整章塞进 prompt 会膨胀上下文、稀释相关性，还会把无关成员带进来。

**代价/边界**：上下文更短、更聚焦；但跨段的完整语义需要模型自己从多个 chunk 组合。父块存储仍用官方 `InMemoryStore`，没有自研存储。

## Q29 为什么不用 `RunnableWithMessageHistory`，历史由 HTTP 显式传入？

**选择**：`/api/chat` 接受 `history`（最多 12 条 × 4000 字符）；服务端会话历史是另一套表（`chat_sessions/chat_messages`），用于跨浏览器恢复，不是 LangChain memory。

**为什么不用另一种**：HTTP 契约是无状态的；引入服务端消息历史会和前端窗口、鉴权归属、保留周期重叠，还会让「一次请求用了哪些历史」变得不透明。

**代价/边界**：服务端不维护 LangChain 意义上的「当前会话窗口」；多轮改写仍可用显式 `history` 完成。好处是请求可复现、可重放、可审计。

## Q30 为什么提示词不热更新？

**选择**：`server/prompts/*.yaml` 进程内缓存，`promptVersion` 是文件内容 sha256 前 12 位；改 YAML 需重启。

**为什么不用另一种**：线上静默换提示词会让行为变化不可追溯，门禁也可能跑在旧版本上。把提示词当代码变更，走重启 + 重跑生成/回归门禁，换来可追溯性。

**代价/边界**：发布检查会检查门禁是否跑在当前提示词指纹上；想热更新就得配版本化 + 门禁重跑，当前刻意不做。

## Q31 为什么在线只跑规则守卫，不在线跑 LLM 裁判？

**选择**：在线做确定性规则（禁用词、Box 构造、动画、多对象、视点、默认值、路径），违规纠错一次；LLM 裁判放在评测平台离线跑。

**为什么不用另一种**：通用模型裁判不稳定、慢、不可复现；这些是 ThingJS 领域规则，规则可单测、可在评测里复现，适合放在强约束里。裁判的语义判断放在离线质量评估。

**代价/边界**：规则覆盖不到所有语义问题；所以还要 Prompt 约束、证据筛选、确定性清洗和离线裁判共同兜底。

## Q32 为什么引用按正文反推，不全信模型 `citations`？

**选择**：`citationsFromAnswer()` 按回答正文实际提到的类/成员给证据打分，多类问题每类取一条最佳片段，最多 3 条；正文没有可用引用时，才回退模型声明并校验 `chunk_id`。

**为什么不用另一种**：模型经常「引用了没说的」或「说了没引用」；直接信 `citations` 会出现引用和正文不对齐。按正文对齐更可信，也更容易在评测里检查。

**代价/边界**：引用上限 3 条，复杂多类问题可能引用不全；这是已知限制，可按类数动态调整。

## Q33 为什么生成失败分级降级，不把致命错误伪装成降级？

**选择**：只有非中止、非网关致命错误、非队列错误才降级为「返回检索片段」；鉴权/配额/限流/队列满/超时直接报错。

**为什么不用另一种**：把 401 当成「模型不可用」会把问题藏起来，用户看到的是降级答案，运维看到的是正常请求，真实故障被掩盖。

**代价/边界**：错误码更细、前端要分别处理；但可观测性和责任边界清楚。降级次数单独计入 `degraded` 指标。

## Q34 为什么不引入 LangGraph？

**选择**：主链路是显式 `runChat` + LCEL，不是状态图；`@langchain/langgraph` 已从依赖中移除。

**为什么不用另一种**：文档问答是固定的检索-生成链路，没有「需要根据中间结果决定下一步」的分支；引入状态机只会增加不确定性、延迟和调试成本。需要状态机时再按需引入，避免过度设计。

**代价/边界**：不能讲「LangGraph 实践」；如果面试官问 LangGraph，诚实说在另一个多轮业务助手里用过，不要把 LCEL 包装成 LangGraph。

## Q35 为什么单机 Windows + SQLite + 文件会话，不引入 Redis/Postgres？

**选择**：部署形态是单机内网；状态库用 better-sqlite3（WAL），会话文件落盘 `data/sessions` 并用 `WEB_SESSION_SECRET` 加密；限流是进程内。

**为什么不用另一种**：当前规模和交付环境不需要额外的中间件；引入 Redis/Postgres/对象存储会增加部署和运维成本，收益不明显。

**代价/边界**：水平扩展需要外置会话/限流/队列/存储；多实例时是单实例限流，不是全局限流。面试时要主动交代这个边界。

## Q36 为什么评测平台独立进程，不做成服务端路由？

**选择**：`review/` 独立 TypeScript 服务（9968），只通过 HTTP 调服务端，不 import 服务端实现。

**为什么不用另一种**：评测需要黄金集、裁判、报告、历史、问题队列、发布检查，生命周期和依赖都不同；如果做成服务端路由，评测代码会和服务端实现耦合，也容易偷偷 import 内部模块，发现不了契约问题。

**代价/边界**：多一个进程、多一套配置；但换来独立运行、独立扩展，以及「评测只通过 HTTP 契约」的强制约束。

## Q37 这个项目有哪些不能过度声称的地方？

- 不要说「用了 LangGraph」——项目没有引入，主链路是 LCEL。
- 不要说「三路召回并行」——并行的是向量 + BM25；精确召回用于置顶/补位。
- 不要说「融合分阈值」——`fusionScore` 是 null，`minFusionScore` 未启用。
- 不要说「知识冲突检测已上线」——字段和提示词策略在，检索链未生成。
- 不要说「多实例全局限流」——限流是进程内。
- 不要说「提示词热更新」——需要重启。
- 不要说「100% 无幻觉」——门禁口径是这批黄金集 0 幻觉，不是所有问题。
