# Skill 语义评审

评审一份 SKILL.md 的语义质量：它会不会在正确的时机被用上、正文有没有给出模型本来不知道的东西、照着它能不能把活干对。

只判断语义。字段合法性、命名规范、YAML 语法这类问题一律交给静态工具，本 skill 不碰。

## 什么时候用

- 拿到别人写好的 skill，要挑出写得不对、写得不够的地方
- 自己写完或改完一个 skill，发布前过一遍
- 一个 skill 明明相关却总不被触发，或总在不相干的场景被触发
- 两个 skill 覆盖同一场景，要比一比谁的写法更站得住

## 什么时候不用

- 从零创建或大改一个 skill —— 那是创作任务，不是评审任务
- 只查 frontmatter 是否合法、命名是否规范、脚本能不能跑 —— 用下面的命令
- 要测真实触发率、跑批量用例统计 —— 需要执行与统计，不在本 skill 范围

## 只查语义，不查语法

下面这些问题由其它工具判定。报告里**不要对它们下结论**，最多提醒用户去跑哪条命令：

| 问题 | 交给谁 |
| --- | --- |
| name 的字数、字符范围、保留字、与目录名是否一致 | 用户会手动执行 `python example/check_a_skill_v1.py` |
| description 的字符数上限、是否含 XML 标签 | 同上 |
| YAML 能否解析、有没有 BOM、`---` 是否配对 | 同上；或 `skill-validator/validate_yaml.py` |
| 正文行数、metadata 词数 | 同上（这两条只是官方建议值，超出只警告） |
| 脚本能否运行、返回码是否正确 | 需要真的执行；`validate_python.py` 只查语法与导入 |
| 排版、拼写、链接是否有效 | 编辑器与链接检查工具 |

用户要的是"全面合规检查"时，就这样回答：**语义部分用本 skill，格式部分跑上面那条命令**。两边结论不要混在一份报告里。

## 七个维度

| # | 维度 | 一句话判据 |
| --- | --- | --- |
| 1 | 触发语义 | 该触发时能不能命中，不该触发时会不会被误拉进来 |
| 2 | 知识增量 | 正文讲的这些，模型本来知不知道 |
| 3 | 可执行性 | 照着做能不能做对，做完知不知道算完 |
| 4 | 边界与反例 | 有没有说清不该做什么、失败时怎么办，且给了理由 |
| 5 | 自由度匹配 | 脆弱的地方有没有收紧，需要判断的地方有没有留空间 |
| 6 | 披露与资源调用信号 | 提到 references/、scripts/ 时有没有说清什么时候该读 |
| 7 | 本体表述语义 | 措辞是不是在给执行它的 agent 下指令，前后是否一致 |

每个维度按 1-5 打分，**3 分是合格线，不是失败**。总分 35。

### 1 触发语义

**看什么** —— 模型只看 `description` 就决定要不要加载，正文里写再多"什么时候用"都到不了这一步。

**检查点**
- 有没有同时说清**做什么**和**什么时候用**。只有前半句，就等着漏触发
- 有没有写进用户**真会说的说法**（口语、同义词、文件类型、领域词），而不是只写 skill 的正式名称
- 有没有反向边界：**什么场景不该用**。只写正向的 skill，在相邻任务上会被误拉进来
- 仓库里已有覆盖相近场景的 skill 时，有没有交代彼此的分工

| 分 | 判据 |
| --- | --- |
| 1 | 只有一句话且说不到点上（"帮助处理文档"），或与邻近 skill 无法区分 |
| 2 | 说了做什么但没说什么时候用；用户换个说法就命中不了 |
| 3 | 做什么、什么时候用都有，但没有反向边界，相邻场景会误触发 |
| 4 | 正向反向都写了、触发词具体；仅在同族 skill 的分工上留了含糊 |
| 5 | 该覆盖的说法都在，明确写了不该用的场景，与同族 skill 的分工一眼可辨 |

### 2 知识增量

**看什么** —— skill 的价值 = 专家知识 − 模型已经知道的。模型本来就知道的部分，只是在花上下文。

**检查点**
- 有没有"什么是 X"式的概念讲解、标准库用法、通用编程套路
- 有没有任何项目都成立的正确废话（"注意错误处理""保持代码整洁"）
- 有没有复述 description、把标题换个说法再说一遍
- 有没有把"能做这个、能做那个"当成内容 —— 能力广告不是知识

| 分 | 判据 |
| --- | --- |
| 1 | 通篇概念讲解与正确废话，整份删掉后 agent 的行为不会有任何变化 |
| 2 | 大部分是模型已知内容，只有零星一两条真正有用 |
| 3 | 一半有价值：夹着明显常识与能力罗列，但也有真判断 |
| 4 | 基本只讲模型不知道的：领域约束、非显然的取舍、踩过的坑 |
| 5 | 每段都在提供模型拿不到的信息，找不到一句可以删的 |

### 3 可执行性

**看什么** —— 读完这个 skill，agent 知不知道第一步做什么、遇到岔路怎么选、什么状态算做完。

**检查点**
- 岔路口有没有判据：列出多种输入、输出或工具时，说没说什么时候选哪个
- 有没有完成标准：做完要产出什么、怎么算过
- 有没有空话指令（"用合适的工具处理""视情况而定"）—— 这类句子等于没写
- 反直觉的关键顺序有没有点明（比如"先校验再打包，反过来会丢改动"）

| 分 | 判据 |
| --- | --- |
| 1 | 只有目标没有做法，agent 只能自己猜 |
| 2 | 有步骤但缺判据与完成标准，多处要靠猜 |
| 3 | 主流程可照做，但岔路口或收尾标准缺失 |
| 4 | 步骤、判据、完成标准都在；个别地方仍偏笼统 |
| 5 | 每一步都可判定，岔路有明确判据，完成标准可验证 |

### 4 边界与反例

**看什么** —— 专家知识有一半是"绝对不能这么做"。模型没踩过这些坑，你不写它就会踩。

**检查点**
- 有没有 NEVER 清单。整份 skill 一句禁令都没有，是最常见的缺失
- 禁令后面有没有理由。"不要用 X"和"不要用 X，因为 Y 情况下会 Z"，后者价值高一个量级
- 有没有失败路径：主办法不成立时退回什么
- 反例是不是具体（"避免错误""小心边界"等于没说）

| 分 | 判据 |
| --- | --- |
| 1 | 既没有禁令也没有失败路径，只写了理想情况 |
| 2 | 只有笼统警告，或禁令不给理由 |
| 3 | 具体禁令与失败路径只有其一，另一个缺失 |
| 4 | 禁令具体且多数给了理由，失败路径覆盖常见错误 |
| 5 | 禁令具体、理由非显然，失败与退化路径都写清了 |

### 5 自由度匹配

**看什么** —— 只有一个判断标准：**agent 做错了，后果是什么**。后果越大，写法越该收紧。

**检查点**
- 脆弱操作（改二进制或 XML、批量删除、数据迁移、发布）有没有给确定做法：确切命令、确切参数、"不要改这个脚本"
- 主观任务（写作、设计、评审）有没有给判断原则，而不是机械步骤
- 有没有摆出一排等价选项却不给默认值（"可以用 A、B 或 C"）
- 严格的规则有没有附理由，好让 agent 在规则没覆盖的边界上自己判断

| 分 | 判据 |
| --- | --- |
| 1 | 完全反了：脆弱操作靠散文描述意图，主观任务被写成死步骤 |
| 2 | 多处错配：关键操作缺确定做法，或创意任务被过度约束 |
| 3 | 大意对但松紧不均，或摆了等价选项不给默认 |
| 4 | 大体匹配；个别地方可以再收紧或再放开 |
| 5 | 脆弱处给到确切做法，主观处只给原则与判据，松紧与后果相称 |

### 6 披露与资源调用信号

**看什么** —— 附带的 references/、scripts/、assets/ 是拿来省上下文的，前提是 agent 知道**什么时候该读**。只列文件名，等于把资源扔在那里。

**检查点**
- 引用资源时有没有给触发条件（"当 X 时完整读一遍 A"），而不是光写"详见 A"
- 有没有反向限制："做这件事时**不要**读 B"，防止一股脑全塞进上下文
- 资源是不是孤儿：文件存在，但正文从没说过什么时候用
- 正文与 references 有没有大段重复 —— 两边都要维护，还会让人怀疑哪份是准的
- 需要通读的文件有没有说明"别设行数上限"，分段读会漏内容

| 分 | 判据 |
| --- | --- |
| 1 | 资源躺在目录里正文从不提，或反过来把全部内容塞进 SKILL.md |
| 2 | 只列了文件名与用途，没有任何加载条件 |
| 3 | 有加载条件，但没有"不要读"的边界，也没提通读要求 |
| 4 | 条件与边界都有，个别资源仍可能被漏读或过度加载 |
| 5 | 每个资源都在决策点被点名，条件、通读要求、"不要读"边界齐全 |

### 7 本体表述语义

**看什么** —— SKILL.md 是写给**执行它的 agent** 的指令，不是写给人类读者的说明文档。口吻不对，指令会被当成背景资料读过去。

**检查点**
- 有没有面向人类的元话语（"本文档介绍……""接下来我们会……"）
- 术语有没有漂移：同一个东西在文件里换了几种叫法，agent 会当成几个不同的东西
- 有没有会腐烂的时效断言（具体日期、价格、某个版本的现状）
- 前后有没有自相矛盾或自我重复（两条规则在说同一件事，一处写必须、一处写可选）
- 作者自己的规则有没有被自己违反（比如说"正文别超过 500 行"自己却写一千行）

| 分 | 判据 |
| --- | --- |
| 1 | 像一篇给人看的介绍文，指代不清，同一概念多个叫法 |
| 2 | 混着说明文口吻，术语不统一，或含明显会过期的断言 |
| 3 | 基本是指令口吻，仍有元话语或术语漂移，或有局部重复矛盾 |
| 4 | 指令口吻一致、术语统一；只剩个别可删的元话语 |
| 5 | 通篇是可执行指令，术语前后一致，无时效断言与内部矛盾 |

## 评审流程

1. **读全** —— 读完 SKILL.md，并读完它引用的所有文件；它有执行脚本也读。没读完不下结论
2. **先定性** —— 用一句话回答"它声称自己在什么场景起作用"。这句话说不出来，第 1 维就已经有问题
3. **逐维取证** —— 七个维度各走一遍，每条判断都要能指到具体哪一句原文。指不到的判断删掉
4. **列问题** —— 按影响排序，最多 5 条。每条给可直接粘贴的改写，不要只说"建议更清晰"
5. **出结论** —— 一句话总评 + 分档，并指出"如果只能改一处，改哪里"

## 输出格式

**一句话结论**

> <skill 名>：<它是什么><最大的一个优点><最大的一个问题>。总分 X/35。

**评分表**

| 维度 | 得分 | 一句话依据 |
| --- | --- | --- |
| 1 触发语义 | ?/5 | |
| 2 知识增量 | ?/5 | |
| 3 可执行性 | ?/5 | |
| 4 边界与反例 | ?/5 | |
| 5 自由度匹配 | ?/5 | |
| 6 披露与资源调用信号 | ?/5 | |
| 7 本体表述语义 | ?/5 | |
| **总分** | **?/35** | |

**分档**

| 总分 | 结论 |
| --- | --- |
| ≥30 | 可用。最多做点润色 |
| 23-29 | 基础不错，按问题清单改 |
| 16-22 | 多处需要重写，不只是措辞问题 |
| <16 | 建议重写 |

**问题清单**（最多 5 条，按影响排序）

```
[<维度名>] 一句话说清问题
原文：<引用原句>
为什么是问题：<它会导致什么后果>
改写：<可直接粘贴替换的文本>
```

## 常见语义病症

| 病症 | 症状 | 怎么改 |
| --- | --- | --- |
| 教程化 | 讲模型本来就知道的概念与用法 | 删。只留判断依据与非显然的约束 |
| 隐性 skill | 正文很好，但描述说不清什么时候用，永远不被加载 | 把 WHEN、触发词、反向边界补进 description |
| 什么都想接 | 描述铺得又宽又泛，在相邻任务上被误拉进来 | 收窄边界，写清 DO NOT USE FOR |
| 清单化流程 | Step 1/2/3 的机械步骤，没有判据 | 改成"做 X 之前先判断 Y"，给决策原则 |
| 空洞警告 | "注意错误处理""考虑边界情况" | 换成具体的 NEVER 清单，并给出理由 |
| 自由度错配 | 脆弱操作靠散文描述，主观任务被写死 | 按"做错了后果多大"重新定松紧 |
| 孤儿资源 | references/ 存在，正文却不说何时读 | 在决策点写清加载条件与"不要读"的边界 |

## 查不出来的

- 字段与命名是否合法（字数、字符范围、目录名是否一致）
- YAML 是否合法、有没有 BOM、脚本能不能跑通
- 真实的触发率 —— 需要跑一批用例统计
- 排版、拼写、链接有效性

以上都不在本 skill 内下结论，指向 `example/check_a_skill_v1.py` 或 `skill-validator`。

## 评审时的 NEVER

- NEVER 因为排版整齐、篇幅长、看起来很专业就给高分。这三样和内容质量无关
- NEVER 把字段合法性、YAML、行数这类问题算进分数或写进结论。越界之后整份报告就不值得信
- NEVER 写没有原文出处的判断。"整体感觉比较空"是印象，不是结论
- NEVER 给"建议更清晰一些"这类无法执行的建议。每条都要给可粘贴的替换文本
- NEVER 因为 skill 是中文或英文就放宽相关性与清晰度的判断
- NEVER 把"内容全面"当成优点。篇幅长往往意味着没做取舍
- NEVER 在有 references/ 或 scripts/ 的情况下不读完就下结论
